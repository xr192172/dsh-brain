# Agent 席位与席间协议 · 规格（2026-09-26）

> **定位**：本规格**不重复**既有两份，只补它们都没定义的那一层。
> · `docs/verification-contract.spec.md` 定义了「**验证什么**」：Subject / Verifier / Criteria /
>   Adopt / Reject 五要素 + I1–I3 三条不变量。**本规格的全部判据与不变量都继承它，不另立。**
> · `docs/skill-as-agent-spec.md` 定义了「**分身怎么造**」：不变量 I1–I4 / 裁决 D1–D10 / 计划 S0–S7。
> · ★ **本规格补的是**：【**谁**验证】拆成三个席位，以及【**席位之间怎么交接**】——
>   这两件事上面两份都没写。所以本规格里的编号（F / D / O）自成一套，**不与那两份的编号混用**。

---

## 0. 一句话

**一个不确定的执行者，必须被三个职责不同、上下文互相隔离、各自持有否决权的席位包围；
席位之间只交换「接收方能够独立复算」的最小集合，不交换过程叙述；
而席位的存在是为了吸收用户的【检查劳动】，不是替代用户的【价值判断】。**

## 2. 三个席位（F0–F6）

### F0 · 架构师席（Architect）

- **治的病**：局部合理、全局不连贯。
- **必须产出工件**（★ 只有工件能跨轮次，对话不能）：

  | 工件字段 | 内容 | 缺了会怎样 |
  |---|---|---|
  | 功能清单 | `F0…Fn` **带编号**，每条一句话 | 细节无法写回 ⇒ 偏差累乘 |
  | 不变量 | 每条写成"什么永远不许发生" | 无法判断某改动是否越界 |
  | 失败模式 | 每条功能"坏了会怎样、怎么发现" | 失败不可观测 |
  | 验收判据 | **每条功能对应一条**可执行的判据 | 自检只能照实现写 ⇒ 假绿 |

- **实现纪律**：实现阶段每一步必须写 `→ F<编号>`；**写不回去的细节删掉**；自检**照编号写**，不照实现写。
- **否决权**：**没有编号清单 + 没有验收判据 ⇒ 不许开工。**
- ★ 没有这条否决权，架构师席就是一个"会说话的摆设"（= 现在的执行者）。

### F1 · 批驳席（Adversary / 反方）

- **治的病**：执行者默认同意用户、也默认同意自己。
- **输入**：用户的**意见/要求**，或架构师席的方案，**或**执行者的交付。
- **必须对【每一条】给出定长结论**：

  | 字段 | 取值 |
  |---|---|
  | `结论` | `成立` / `不成立` / `部分成立` / **`无法判定`**（三态，不许二值） |
  | `具体后果` | 如果照这条做，会发生什么**可观测**的事 |
  | `冲突的不变量` | 与哪条 F0 不变量冲突（没有就写"无"） |
  | `怎么做才不冲突` | **可执行**的改法 |
  | `自证伪` | ★ **什么证据能让我收回这个反对**（见 D5） |

- **禁止措辞**：`可以考虑` / `建议关注` / `值得商榷` / `注意一下` —— 凡是**不能落到"改什么"**的话，
  一律视为噪音，判定无效。
- **最强形态**：★ **把反对写成可执行判据。**（原文："如果你说的对，那么撤掉 X，**Y 必须变红**。"）
  · 实例（2026-09-26 当天真的写了）：断言「**旧判据在这份正确源码上必须报假红**」——
    它把"这次改判据的理由"从一段说辞变成了一条**跑得起来的证据**。
  · 结论：**散文批驳 = 另一个观点；可执行批驳 = 证据。**
- **否决权**：它的反对要么**被证伪**，要么**方案必须改**。
  **不许被一句"有道理，但先这样"糊过去**（这正是现在会发生的事）。

### F2 · 见证席（Verifier）

- **治的病**：前两席若由同一个模型出，**共享同一套盲区** ——
  当天的假绿、假红、假否定**全部**是这么来的。
- **纪律**（继承既有铁律，不新造）：
  1. **只信可复算的读数，不信任何一方串好的因果**（读数与归因分开验）；
  2. **见红先问三句**：它探的是谁？探针够不够硬？被探对象此刻在干什么？
  3. **换通道前先证明新通道看得见阳性对照**（"看不到" ≠ "没有"；通道不可用 ≠ 读数为 0）；
  4. **核心动作是消融**：撤掉修复 ⇒ 判据**必须**变红（否则修复未被证明）；
  5. **不许为了让判据变绿而改判据** —— 见假红先证明**判据**错了，再动判据；绝不动被检对象。
- **否决权**：`不成立` 或 `无法判定` 时，Subject **不得获得写权**（继承 verification-contract 的 I1/I2）。

### F3 · 信息隔离（席位之间的**唯一**价值来源）

★ **三席不得是"同一个上下文里的三个人格"** —— 那只是同一个盲区换三种口吻。

| 隔离项 | 要求 |
|---|---|
| 上下文 | 三席**各自独立的会话/上下文**，不共享推理历史 |
| 判据可见性 | 判据/答案清单**不得**进入被审席位的读写范围（复用 R1 纪律） |
| 辩解 | 见证席**看不到**执行者的辩解，只看工件与读数 |
| 实现细节 | 架构师席**看不到**实现的便利与诱惑，只看需求与不变量 |

## 3. 关键裁决（D0–D6）

### D0 · ★★★ 被审者**不得控制审计范围**（本规格最重要的一条）

**问题**：如果"执行者决定交给批驳席什么"，那么执行者就控制了自己被审的**边界** ——
他会（不是恶意，而是**根本注意不到**）略去自己最没把握的部分。
⇒ 审计退化成一个**自报合规**流程。

**裁决**：

1. **claim 与 evidence 必须【分开送达】**：
   - 执行者交的是 **claim card**（一组带编号的断言）；
   - **原始工件与机器读数由第三者直接送达**（diff / 工件文件 / 判据输出 / 台账），**绕过执行者**。
2. **每条 claim 必须指向一个工件**。**指不到工件的 claim ⇒ 自动判 `不成立`**（fail-closed）。
3. 批驳席与见证席**可以且应当**去看 claim card 之外的东西。
4. ★ 推论：**"我总结得很好"不算交付；"我的每条断言都能指到工件"才算。**

### D1 · ★★★ 席位吸收的是用户的【检查劳动】，**不是**用户的【价值判断】

用户提出"等于你替代我的角色，然后被他审核"。**大方向对，但这条边界必须划清**：

| 可以被席位吸收 | 不可以被席位吸收 |
|---|---|
| 逐条核对、找漏洞、复算读数、追回归 | **想要什么**（目标函数） |
| 判断"是否自洽、是否有证据" | 判断"这件事值不值得做" |
| 发现"你没申报的不确定" | 判断"哪个取舍可以接受" |

**理由**：如果连目标函数也搬进闭环内部，整个系统就**没有外部真值**了 —— 会变成自我确认的闭环。
这正是项目既有的 R1 纪律（判据不能放在被测 agent 够得到的地方）在**席位层**的同一句话。

### D2 · ★★ **不确定必须是一等字段**（未申报的不确定 = 缺陷）

- 执行者的交付里，**必须**含一个"我不确定的地方"清单。
- ★ 机制上的狠处：批驳席/见证席的任务**包含"找出一条执行者【没有】申报的不确定"** ——
  只要找出一条，**无论严重度，都记为该交付的 P1 缺陷**。
- 为什么这样设计：执行者天然会写"自信的总结"。把不确定变成**强制字段**，才把
  "叙述"换成"claim + 不确定"。而"未申报的不确定"有代价，才逼出诚实。

### D3 · ★ 交接只带「接收方**能独立复算**」所需，不带过程叙述

用户说"只输出自己需要输出的内容即可，中间过程都别放进去"。**方向对**，但要精确化 ——
因为"最小"和"可独立复算"是两个不同的方向，只取"最小"会让接收方**无法验证**，退化成橡皮图章。

| 必须**砍掉** | 必须**保留** |
|---|---|
| 推理过程、"我先试了 A 又试了 B" | **claim**（带编号的断言） |
| 自我辩解、解释为什么这样做 | **工件指针**（能定位到具体文件/行/输出） |
| 礼貌语、铺垫、复述用户的话 | **原始读数**（不是我的转述） |
| "我做得很好"式总结 | ★ **验收判据原文**（不是我的意译） |
| | ★ **我不确定的地方**（D2） |

**一句话**：**交接的内容 = 接收方复算所需的最小集合。**
★ 这条同时适用于**席位之间**和**席位对用户**（同一规则，两个层面）。

### D4 · 判据 / 答案清单不进被审席位的读写范围

直接复用既有 R1：判据、题面、答案清单**不能放在被测 agent 够得到的地方**，否则区分度归零。
（本规格只引用，不重定义。）

### D5 · ★ 批驳必须带**自证伪字段**，否则会退化成"为了反对而反对"

一个没有成本的反对者 = 一个唱反调的人。⇒ 每条反对必须写明"**什么证据能让我收回**"。
批驳席的合格判据里因此包含一条：**它的自证伪字段必须非空且可检验。**

### D6 · 三席**不同上下文**；隔离即价值

见 F3。★ 允许三席由**同一个模型**担任，但**必须分属不同会话/上下文**。

## 4. 席间消息格式（三个定长 schema）

★ 用**定长 schema** 而不是自由散文，有两个理由：
① 接收方能机械处理；② **缺字段是可见的**（散文里"漏掉一项"是看不见的）。

### 4.1 `claim-card`（执行者 → 批驳席 / 见证席）

```
{
  subject:       "<这次交付是什么>",           // 一句话
  claims: [                                     // ★ 带编号
    { id: "C1", 断言: "<可判定的一句话>", artifact: "<文件/行/输出指纹>", 类型: "行为|读数|不变量" }
  ],
  fmap:          { "F3": ["C1","C2"] },         // ★ 每条 claim 写回它服务哪个功能编号（F0 纪律）
  uncertainties: ["<我不确定的地方>"],           // ★ D2：必填，可空数组但不许缺字段
  notDone:       ["<我明确没做的事>"],           // ★ 诚实清单
  criteriaUsed:  "<验收判据的原文，不是意译>"
}
```
**校验规则**（接收方第一步就做）：
- `claims[].artifact` 指不到 ⇒ 该 claim **自动 `不成立`**（D0 第 2 条）；
- 缺 `uncertainties` 或 `notDone` 字段 ⇒ **整卡退回**，不进入判定；
- `fmap` 有 claim 未覆盖、或有编号写不回 F0 清单 ⇒ 记缺陷。

### 4.2 `evidence-bundle`（**第三者** → 批驳席 / 见证席；绕过执行者）

```
{ subject_ref: "<claim-card 的 subject>",
  artifacts: [ { path, sha256, size } ],        // ★ 指纹，不是名字
  machineReadings: [ { what, value, howToReproduce } ],  // 可复算
  gateOutputs: [ { gate, exitCode, tail } ] }
```
★ **这一包不经执行者的手。** 这是 D0 的物理落地。

### 4.3 `verdict`（批驳席 / 见证席 → 执行者）

```
{
  claimResults: [
    { id: "C1", verdict: "成立|不成立|部分成立|无法判定",
      why:          "<可观测的具体后果>",
      counterexample: "<反例，或判据输出；没有就写 无>",
      fix:          "<怎么做才不冲突；可执行>",
      falsifier:    "<★ 什么证据能让我收回这个反对>" }
  ],
  undeclaredUncertainties: ["<执行者没申报的不确定 —— 出现即 P1>"],
  selfDoubt:     "<★ 我这个判定可能错在哪>",
  overall:       "通过 | 驳回 | 无法判定"
}
```

★ 三态 `成立/不成立/无法判定` 是**硬要求**：`无法判定` 既**不许当通过**（假绿），
也**不许当失败**（假红）—— 它必须被显式记录并**复探**。

## 5. 验收判据（**这三个席怎么才算合格**）

★ 每一条都必须**可执行**，且有**双向对照**（只有"能抓错"是不够的 —— 逢错必报的机器是噪音机）。

| # | 判据 | 双向要求 |
|---|---|---|
| V1 | **批驳席能抓到真缺陷** | **消融**：撤掉批驳席 ⇒ 必须能举出一个当天真实发生、且被它拦住的缺陷 |
| V2 | **批驳席不误报** | **阳性对照**：喂一个**确实正确**的交付 ⇒ 必须给 `通过`。恒报错的席 = 噪音机 |
| V3 | **批驳席能抓"没申报的不确定"** | 喂一个**故意藏了一处不确定**的交付 ⇒ 必须出现在 `undeclaredUncertainties` |
| V4 | **D0 生效** | 喂一张 **claim 无工件指针**的卡 ⇒ 该 claim **必须自动 `不成立`**，且**不许**人工补救 |
| V5 | **架构师席的否决权是真的** | 拿一个"没有编号清单"的需求开工 ⇒ 必须**被拒**（而不是"先做着"） |
| V6 | **见证席的消融纪律** | 拿一个"修复未被证明"的交付 ⇒ 必须要求**撤掉修复看判据变不变红** |
| V7 | **三席隔离可检验** | 判据文件**不在**被审席位的可读范围内（机器检查路径，不靠自觉） |

## 6. 构建顺序（按收益/成本）

| 序号 | 做什么 | 成本 | 为什么这个顺序 |
|---|---|---|---|
| S0 | **批驳席** | 低（**不需要新代码**：一条 prompt 约束 + 一个 schema + 一条"禁止无动作措辞"） | 立刻治最痛的点（执行者默认同意） |
| S1 | **见证席** | 中（复用已装的 5 个方法论 skill；缺的是"位置"不是"知识"） | 消融/双向对照是它唯一的硬本事 |
| S2 | **架构师席** | 高（要定 F0 工件格式 + 改工作流 + 把 `→ F<编号>` 变成纪律） | 收益最大，但依赖 S0/S1 已能压住噪音 |

## 7. 未闭合（O0–O5）

- **O0**：三席由**同一模型**担任时，"上下文隔离"到什么程度才算够？同一进程不同会话 vs 不同进程？
  需要一次实测（对照：隔离 vs 不隔离，抓错率）。
- **O1**：`claim-card` 的 `artifact` 指针格式要不要做成**指纹强制**（sha256），还是允许"文件:行"？
  指纹更硬但会因无关改动失效。
- **O2**：批驳席与见证席的**顺序**：串行（批驳 → 见证）还是并行？并行省钱但可能重复发现。
- **O3**：`无法判定` 的复探由谁触发、超期怎么处理（继承 verification-contract §5 的 reject 语义）。
- **O4**：D1 的"用户价值判断不可替代"——**具体哪些决定必须回到用户**？需要列一张清单
  （候选：目标函数变更、取舍取舍、对外动作、花钱、不可逆操作）。
- **O5**：本规格与 `verification-contract.spec.md` 的 I1–I3 如何**机器化对齐**（现在只是引用关系）。
