## 1. 问题（一句话）

`main.ts:382-403` 现在这样算四个值：

```ts
const home = envStr('DSH_HOME', join(homedir(), '.dsh'))
...
dshHome:     home,                                                 // ← R1 已改成显式下传
coordDir:    envStr('WORK_DIR', join(home, 'switchboard')),
workDir:     envStr('WORK_DIR', join(home, 'switchboard')),
genAssembly: envStr('GEN_ASSEMBLY', join(envStr('WORK_DIR', join(home, 'switchboard')), 'gen-assembly.json')),
```

⇒ **四个值同源于 `home`**。R1 只把 `dshHome` 变成显式入参，**其余三个仍然"跟着 home 自动走"**。

## 2. 为什么这是个真问题（不是洁癖）

### 2.1 现状是"看似一致的巧合"

臂A 的启动 env（`isolated-instance.mjs:821/867` 吐出）**只设 `DSH_HOME`，不设 `WORK_DIR`**：

```
DSH_HOME="D:/project_develop/_arms/a/dshhome"
DSH_ARM_SELF=a  DSH_ARM_DENY=...
SWITCH_PORT=33080  GEN_PORT_BASE=33081  ...
```

⇒ 臂A 的 `coordDir` 走**默认值** `{DSH_HOME}/switchboard` = `D:/project_develop/_arms/a/dshhome/switchboard`
⇒ **实测确认**该目录存在，里面就是 `gen-33082…33087` + `lease.json` + `handover-status.jsonl`。

★ **结论：今天没坏，是因为"没人设过 `WORK_DIR`"，四条线恰好都落在同一个 `{home}/switchboard`。**
**这是一致，但不是"被约束保证的一致"—— 是一致得靠运气。**

### 2.2 一旦有人设 `WORK_DIR`，立刻脑裂

设 `DSH_HOME=/arms/a/dshhome` + `WORK_DIR=D:/project_develop/dsh-brain/out/switchboard` ⇒
`dshHome` 指向臂A、`coordDir`/`workDir` 在仓库里 ⇒

- 会话在 `<home>/sessions/`（`dshHome` 决定）
- 但租约 / `handover-status.jsonl` / `gen-<port>/boot.log` 在 `WORK_DIR`（`coordDir` 决定）

⇒ **数据与日志分家**，而且**没有任何判据会报警**（两边各自都"正常"）。
这就是 R1 盘查 §2.4 说的混合态。**最坏的形态：它沉默。**

### 2.3 为什么必须在"删旁路之前"修

R2 要删掉 `arm-up → isolated-instance --force` 那条旁路，改成"换代机制自己服务别的训练场"。
到那时，"控制面 → 代"必须携带**一整套同源参数**，而不是"只带一个 home 然后指望别处也别乱设"。
⇒ **R1.5 是 R2 的前置**（同 §5 的排序逻辑：先让机制能表达，再删旁路）。

### 2.4 一个更隐蔽的口子：`isolated-instance` 会把仓库路径吸进臂

`GEN_ASSEMBLY` 默认 = `{WORK_DIR}/gen-assembly.json`。若 `WORK_DIR` 被设成**仓库内**路径，
则臂的"代装配清单"指向仓库 ⇒ **臂A 的模型接入读的是仓库里的清单** ⇒
臂与现役**共享一份 key 池配置** ⇒ 与"训练场隔离"的语义直接冲突。

⇒ 反过来说：**默认值（`{home}/switchboard/gen-assembly.json`）是对的**，
要修的不是默认值，是**"允许别人把它们分开设而没人管"**这件事。

## 3. 设计（三条，粒度依次递减）

### 方案 A（★ 采纳）：把"同源"变成**被检查的约束**，而不是**被期望的约定**

在 `main.ts` 求值处，**先算出决定性的一个值**，其余三个**从它派生**（不再各自 `envStr` 求值），
并在启动时打印一行**可核对的指纹**；若外部**显式**给了不一致的值 ⇒ **拒绝启动**（不静默接受）。

要点：

1. **单一求值点**。现在 `envStr('WORK_DIR', …)` 被求值 **3 次**（400/401/403 行），
   表达式还重复了 `join(home,'switchboard')`。改成一个 `const workDirBase = …`，三处引用它。
2. **`WORK_DIR` 若被显式设置且【不落在 home 之下】⇒ 报错退出**（给白名单式提示），
   除非显式带一个 `ALLOW_SPLIT_WORK_DIR=1` 逃生阀（对"我自己知道我在干什么"的专家开放，
   但**默认禁止静默分裂**）。
3. **启动指纹**：控制面启动时打印
   `[switchboard] home=<…> workDir=<…> genAssembly=<…>` 一行。
   ★ 判据价值：现役与臂的 `boot.log`/启动日志里**逐字**能看到这四项，
   ⇒ "臂到底看的是哪份 home" **不再需要靠推**（这正是铁律 12/15 要的"读数要有效"）。

### 方案 B（备选，粒度更大）：把四个值收进一个 `Placement` 结构体

`CoordinatorConfig` 不再散着收 `dshHome`/`coordDir`/`workDir`/`genAssembly`，
改收一个 `placement: { home, workDir, genAssembly }`（类型上**不可能只改一半**）。

- 优点：编译期强制"要么一起给，要么都不给"（同 R1 用 `required` 字段拿到编译期保障的思路）。
- 缺点：改动面大（三个 spawn 调用点 + preflight + 测试都要动），
  且**不影响任何运行时行为** —— 纯重构。
- ⇒ **不进本轮**。等 R2 真的要用"服务别的训练场"时再顺手做（那时才有第二个用例来验证它）。

### 方案 C（否决）：给每个值加 `envStr` 兜底并"尽量对齐"

即"检测到不一致就自动纠正成 home 派生值"。**否决** ——
**静默纠正比静默分裂更坏**：它让人以为设了有效，实际被悄悄改掉（同铁律 9 的"静默坏比崩更隐蔽"）。

4. 方案 B 不做 ⇒ "只改一半"在**类型层面仍可能**，只靠运行期校验兜。
   **如实记为"未闭合"**。
