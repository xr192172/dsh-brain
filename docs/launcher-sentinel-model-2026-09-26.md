## 0. 用户的三条裁决（**逐字固化，不得改写**）

### 裁决 1 —— 画布（Design Canvas / agentio）：**"做得成就做"**

> *"做不做看你吧，Design Canvas 本身目前只在 Agent 的层面用，因为人不看，你能够用好它你就去做。
> 你觉得你能看懂，或者说每次看它都是都能看同样的东西，就是不会说每次看都把它解读为不同的图吗？
> 如果你每次看都是同样的东西，也就是说它不会导致你漂移的话，那么我们的目的就达成了，
> 就是要**按图施工**嘛，它就是我们的**施工图纸**嘛，没错吧？"*

⇒ ★ **用户给的判据 = "每次看是不是同样的东西"** —— 是 ⇒ 就做；会漂 ⇒ 做了也白做。
★ **用户的目标 = 按图施工**（施工图纸 = 画布本身）。

### 裁决 2 —— 皮（管理界面）的形态

> *"我觉得要不就起一个就像是那些游戏啊什么的管理的一个界面，然后点开了之后先启动那个页面，
> 然后那个页面再本身**唤起一代 Agent**，并且在那个页面上**进行标注当前有一代**，
> 然后那个**动向**什么的都在那个 Agent 那层皮上面去显示，而且**你也可以读我也可以读**，怎么样？"*

⇒ 四要件：
1. **独立的管理界面**（像游戏启动器那样），**先起页面**；
2. **由页面去唤起一代 Agent**（页面是发起者，不是被动的展示板）；
3. 页面上**标注"当前有一代"**（代数/身份/精神状态）；**动向**显示在**这个 agent 层的皮**上；
4. ★★ **"你也可以读我也可以读"** = **同一份数据，人机同源**（不是"给人看的 UI"和"给 agent 的 API"两套）。

### 裁决 3 —— 管代数的粒度 = **哨兵节点模型**

> *"按照我刚刚描述的这个模型来说就已经很简单了吧。内部实现我不太清楚你用哪种算法最好，
> 但是像我这样的话就等于是一个**池**嘛，或者说**哨兵**，哨兵节点懂吧 ——
> 就是**提拔当前的这个为哨兵**，然后后面你开其他的哨兵，**都只是下一代**，
> 然后**只有当前这一代选择退役了之后，才提拔那个当前哨兵选定的下一代哨兵作为新的主代**。"*

⇒ 提炼成三条规则（**这就是粒度定义，Q2 已答**）：
- **R-a** 任何时刻只有**一个主代**在服役；
- **R-b** 后开的都是**哨兵（下一代）**，**不服务**；
- **R-c** ★ **只有主代退役了，才提拔**"当前哨兵选定的那个" ⇒ **提拔是被动的、由退役触发**。

★★ **用户明说"内部实现我不太清楚你用哪种算法最好"** ⇒ **算法选择交给我，但模型（上述三条）不归我改。**

## 2. 哨兵模型的形式化（裁决 3 的落地形状）

### 2.1 状态（只有这三个字段决定一切）

```
POOL = {
  primary : GenRef | null      // 唯一在服役的主代
  sentinel: GenRef | null      // ★ "被选定的下一代"（主代退了提拔它）
  others  : GenRef[]           // 其余哨兵（都是下一代候选，不服务）
}
```

★ **`sentinel` 是单数** —— 因为用户说的是*"提拔那个当前哨兵**选定的**下一代哨兵"*
⇒ 同一时刻**只有一个"已选定"**；其余在 `others` 里等着被选。

### 2.2 三个动作（**没有第四个**）

| 动作 | 前置 | 效果 | 对应 |
|---|---|---|---|
| **立哨（spawn）** | 无 | 新开一个代，**不服务**；若 `sentinel` 为空则占用它，否则进 `others` | F2 |
| **选定（designate）** | `others` 非空 | 把某个 `others` 提到 `sentinel`（原 `sentinel` 退回 `others`） | F1/F2 |
| **提拔（promote）** | ★ **`primary` 退役** | `primary ← sentinel`；`sentinel ← null`（等下一次选定） | F2 |

★★ **R-c 的精确含义**：**提拔不能由"我算出来哪个更好"触发** —— 只能由**退役**触发。
⇒ **模型里没有"算法选择最好的代"这一步**（这就是用户说"很简单了吧"的原因）。

### 2.3 与现有机制的关系（**不新造**，铁律 17）

| 哨兵模型 | 现有机制 | 差距 |
|---|---|---|
| `primary` | `lease.json` 的 `activeGen` + 前门指向 | ✅ 已有 |
| 立哨 | `?cmd=handover` 会 spawn 新代并**flip** | ⚠️ ★ **现有 handover 是"直接翻转"，不是"立哨待命"** ⇒ **这是唯一真缺口** |
| 提拔 | `?cmd=handover` 的 flip 动作本身 | ⚠️ 同上：它把"立哨+提拔"合成了一步 |
| 退役 | 旧代 `retainMs`(30s) 后退出 | ✅ 已有（但**不是"退役触发提拔"的语义**） |

★★★ **所以真正的实现缺口只有一件事**：
**把 `handover` 的"spawn + flip"拆成"立哨"与"提拔"两个可分别调用的动作**。
⇒ 这正是 `docs/r2-handover-only-design-2026-09-26.md` 已经做过的那类拆分（**R2 是拆"准备 vs 换代"，
这次是拆"立哨 vs 提拔"**）—— **同一族，有先例可抄，不是新发明。**

## 3. 皮的形态（裁决 2 的落地形状）

### 3.1 用户描述的流水（逐字对应）

```
点开图标
  → ① 先起【这个页面】        （页面自己是长服务，独立于任何一代）
  → ② 页面去【唤起一代 Agent】  （页面是发起者）
  → ③ 页面上【标注"当前有一代"】+ 动向
  → ④ 人可读 + 我（agent）可读  （同一份数据）
```

### 3.2 ★★ 关键设计点：**"你也能读"怎么实现（人机同源）**

用户原话：*"而且你也可以读我也可以读"*。

⇒ **落法**：页面**不自己造数据**，它读的是**与 `?cmd=status` 同一份源**。
具体：页面上的每个数字都必须**能通过一个 URL 拿到同样的值**（页面只是它的一个渲染）。
★ **判据（可执行）**：**页面上看到的每个值，我都能用一个 `?cmd=` 调出同一个值**；
两边不一致 ⇒ 页面在骗人。

⇒ ★ 这样**天然满足"你也可以读"** —— 我读的是同一份，不需要"给 agent 的接口"。
★ 与铁律 18（回读 ≠ 生效的是那份）一致：判据落在**同一份数据源**上，不落在"页面显示了什么"。

### 3.3 ★ 与"不许把现役搞掉"的冲突点（必须解）

★★ 裁决 2 说"**点开了之后先启动那个页面**" ⇒ 页面本身要**常驻**。
⚠️ 但现有铁律 3：**不能在工具内起长期服务**（只有 `relaunch-switchboard` 走计划任务那条通道可用）。

⇒ **两条解法（待定，见 §5-Q）**：
- **(甲)** 页面**不常驻** —— 点开时起、看时活、关了就停；**主代继续跑**（因为它与页面无关）。
  ★ 优点：不引入新的常驻体；★ 缺点："点开了才发现有一代"要每次现起。
- **(乙)** 页面**常驻**（复用 `relaunch-switchboard` 那条计划任务通道起）。
  ★ 优点：随时点开就有；★ 缺点：多一个常驻体要管（而"管常驻体"正是我们想避免的复杂度）。

★ 用户原话是*"点开了之后先启动那个页面"* —— **字面更像 (甲)**（先启动页面 = 点开才启动）。
★ (甲) 还天然满足 §3.3 的隐含担忧：**页面不在 ⇒ 主代照样活** ⇒ F4 自动成立。
