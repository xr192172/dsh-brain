# 能力库式自进化 —— 把进化单位从"整体"下沉到"能力"

> 日期：2026-09-14
> 来源：用户提案 —— 三脑换代成「设计师（出思路 + 出验收标准）+ 开发人员 + 组装厂」；
> 装配完成 → 验收 → **形成一个新 sub agent → 注册为新 sub agent**。
> 注册规则：同功能升级 = 下一代换上一代；新方向 = 重新注册；一个能顶两件事 = 合并。
> 核心论断：**「sub agent 就是它的能力；sub agent 的能力就是它的能力。这比自己给自己改好得多。」**
> 最后一条要求：**「重要的是能不能把市面上已有的 Agent 注册为 sub agent 让它调用。」**
>
> **结论：方向正确，而且这是整条线上最重要的一次"降级"。
> 机制层面 DSH 已原生支持 —— 注册表、动态注册、注销、能力声明、进程外后端、谱系树 UI 全都有。**

## 1. 为什么"sub agent 就是它的能力"是关键词

之前所有自进化方案（DGM / SEAL / 我们的三脑）都在改**一个整体**。整体自改有四个根本困难：

| 困难 | 后果 |
|---|---|
| 判据要覆盖整体 | 极贵、几乎无法写成可执行脚本 |
| 回滚粒度粗 | 一次坏改损失全部 |
| 能力无法单独演进 | 改 A 可能坏 B，且无法归因 |
| 无法与外部互操作 | 只能吃自己的产出 |

**一旦把单位换成"能力"（= 一个 sub agent），四条同时缓解**：

- **判据下沉**：只需回答"这个能力做不做得到" → 正好是《自进化总纲》§5 里的**能力门**。**这是它能写成可执行脚本的原因。**
- **回滚粒度 = 一个能力**：换错只影响一个能力
- **能力互不干扰**：这是最大收益——**A 能力升级不该动 B 能力**
- **外部能力可直接接入**：同一接口

而且你那句话在架构上是**可判定的**：

> **顶层 agent 的能力 = 它注册的 provider 的并集。**
> 于是"提升系统能力"被分解为四个可执行动作：**注册 / 升级 / 合并 / 淘汰**。

**这解决了整条线上最难的那个问题**：能力性进化的判据是什么？
→ 答案：**就是这个 sub agent 能不能通过它自己的验收标准。判据被下沉到能力级。**

## 2. 你的三角色划分 —— 两处要改

| 角色 | 评价 |
|---|---|
| **设计师**（出思路 + **出验收标准**） | ✅ **对，而且"同时出验收标准"是关键**。这正是《自进化总纲》§5.2 的两条约束之一：目标必须可验证 |
| **开发人员** | ✅ 对 |
| **组装厂** | ⚠️ **它不是一个"脑"，是一个环境 + 一条流水线** |

**为什么组装厂不该是第三个脑**：你的描述里它「进行开发 → 装配 → 验收」——**三个职责塞进一个上下文**，
这恰好是我们反复警告的"自己出题自己判卷"。它不是分工，是把三个工位叠在一起。

**建议改成**：

```
设计师（出思路 + acceptance）┐
                              ├─→ 沙箱流水线（= 组装厂，是环境不是脑）
开发人员（实现）             ┘       ① 装配  ② 跑 acceptance  ③ 跑隐藏 holdout
                                              → 全过才注册
```

**关键：验收必须是"闸"，不是"脑"。**
设计师产出的是**可执行的 `acceptance`**，由控制面机械执行，而不是由任何一个脑"看一眼说 OK"。
否则判据的独立性就不存在了（见《自进化总纲》§6.3：判据的独立性靠上下文隔离，不能靠 prompt 里写"请客观"）。

**更准确的说法**：三脑作为**架构**要退场，作为**生产线的两个工位**被保留。
"三脑"这个词承载的是旧模型（三个并列的、会自我修改的 agent）——
新模型里你要的不是三个脑，而是 **一条能力生产线 + 一个能力注册表 + 一个消费者（顶层）**。

## 2.5 ★ 决策层：多模型会议室（委派不是单人委派）

用户提案：**委派层不一定是单人委派** —— 做成"多模型会议室"：群聊，但**群员是多个模型而非多个 Agent**；
动态多模型各出方案；通过 ①人审 ②互相辩论 ③预先指定审核员 决定最终方案；再委派给子代理。
用户的类比是"**三省六部**"。

### 2.5.1 为什么"多模型"≠"多 Agent" —— 这是本质区别

| | 多 Agent（多会话 / 多角色） | **多模型（会议室）** |
|---|---|---|
| 差异来源 | **同模型 + 不同上下文**（prompt / 角色 / 工具） | **不同先验**（训练 / 后训练造成的系统性差异） |
| 多样性上限 | **采样噪声** | **系统性差异** |
| 能消除的错 | 上下文相关的错（漏看、被 prompt 带偏） | **模型本身的系统性偏见** |
| 成本 | 低（同 provider，可共享 KV cache） | **高**（跨 provider，**无法共享 KV cache**） |

> **同一个模型即使换 100 个 prompt，仍然会掉进同一类错。**
> 所以"多开几个会话"的多样性上限是**采样次数**，而对抗性检查（找人没想到的错）需要的是**先验差异**。

**这修正了 §5.5 的一个说法**：我们说"判据的独立性靠上下文隔离"。
上下文隔离消除的是"同一偏见被重复采样"；**跨模型才能消除模型本身的系统性偏见**。
⇒ **评分者独立性的强度：跨模型 > 跨会话 > 同会话换 prompt。**

### 2.5.2 "三省六部"的映射（这个类比其实很准）

| 三省六部 | 我们的对应 | 要点 |
|---|---|---|
| 中书省（草拟） | 会议室里各模型**独立出方案** | 多人独立起草，非一人定稿 |
| **门下省（审核 / 驳正）** | **审核员模型 + 判据闸** | ★ **"封驳"权 = 独立否决权，且与中书省不是同一机构** |
| 尚书省（执行） | **委派给子代理（能力库）** | 执行统筹 |
| 六部 | **能力库的各 provider** | 分工执行 |

**三省制的设计精髓就是"拟—审—行"三分，且审核方持有独立否决权** ——
这与"**判据必须独立于被判定者**"是同一条原则的古代版本。

### 2.5.3 三种裁决不是并列选项，而是按风险分档

（复用 `docs/handover-vs-restart.md` 三级策略的思路：**按"坏了会不会被立刻发现"分层**）

| 档 | 裁决方式 | 适用 | 成本 |
|---|---|---|---|
| **D1** | **单模型** | 低风险、可撤回 | 最低 |
| **D2** | **跨模型辩论 / 投票**（自动） | 中风险、有明确 `acceptance` | 中 |
| **D3** | **人审 + 隐藏 holdout** | 高风险、不可撤回、**涉及判据自身** | 高 |

### 2.5.4 三条硬约束（缺一条就退化）

1. **先独立作答，再交换意见。** 否则第一个发言的模型**锚定**后面所有人 → 趋同（consensus collapse）。
2. **异议必须记录，不能被抹平。** 与"没有理由的评分应被丢弃"同理：**被抹平的异议是有信息量的**。
   产出必须包含 `dissent: [{ model, objection, evidence }]`，而不是只留结论。
3. **审核员不能由被审者指定，也不能是被审模型自己。**
   "预先指定审核员"要改成"**由判据层指定，且与被审模型不同源**" ——
   否则"谁指定审核员"会变成新的单点（= 把旧问题搬了个位置）。

### 2.5.5 技术约束（必须提前算）

- **跨模型无法共享 KV cache**（不同 tokenizer / system prompt / 工具集）⇒ 每个参会模型都是一次**冷启动**。
- ⇒ **会议输入必须是"压缩后的任务规格"，不是整个会话历史**，否则成本爆炸。
- ⇒ **会议开在决策层，不在执行层**：
  输入 = 任务描述 + 能力清单 + **上下文摘要（外置引用）**；输出 = 方案 + 选路 + `acceptance`。
- ⇒ 会议结论要**一次落盘**（决策记录），后续委派引用它 —— 又是"**写入时外置化**"（§6 同源原则）。

### 2.5.6 它顺手解决的两件事

1. **"设计师"工位有了具体形态**：会议室**就是**设计师 ——
   产出 ① 选哪个能力（路由）② 方案的 `acceptance` ③ 能力缺口时的候选提案。
2. **§3 失败模式④（"路由判据不能靠 prompt 自由发挥"）有解了**：
   路由不再是"顶层 LLM 凭感觉选"，而是**会议室里多模型各自给出"该派给谁 + 为什么"，
   再由判据层按可执行规则裁决** —— **路由从"感知"变成"可审议的命题"。**

## 3. ★ 机制层面：DSH 原生支持"能力注册"

### 3.1 服务：`@deepseek-ai/dsh-subagent`

```js
// 公开 API（实测）
ctx.subagents.registerProvider(provider)   // ← 动态注册
ctx.subagents.getProvider(name)
ctx.subagents.providers                    // 列表
ctx.subagents.startContinuable(spec)
// 事件
"subagent/provider-added"   / "subagent/provider-removed"
"subagent/start" / "subagent/end" / "subagent/descriptor"
```

### 3.2 `SubagentProvider` 接口 —— 只有五个成员

从 `dsh-subagent-spawn-in-process` 的实现逐字读出：

```js
class SpawnInProcessProvider {
  name;
  capabilities = { outputSchema: true, depthLimit: true, toolFilter: true, persona: true };
  inheritsParentContext = false;
  start(request) { ... }
  prepareContinuable(...) { ... }
}
```

**`capabilities` 就是"能力清单作为契约"的现成挂载点**——
我们之前提议"给 provider 加能力声明"，**它本来就长在这里**。

`dsh-subagent/lib/index.js` 的注释里还有一句决定性的：

> "Provider-side vocabulary for **OUT-OF-PROCESS** subagent backends — the pieces
> ... **capability-validating asynchronous start API**."

→ **进程外后端是一等公民**。这就是"把市面上已有的 Agent 注册为 sub agent"的官方路径。

### 3.3 工具侧：`@deepseek-ai/dsh-tool-subagent`

```js
ctx.on("subagent/provider-added", (provider) => {
  if (provider.name === config.provider && disposeTool === void 0) mount(provider)   // ← 注册即挂载工具
});
ctx.on("subagent/provider-removed", (name) => {
  if (name !== config.provider || disposeTool === void 0) return
  disposeTool(); disposeTool = void 0                                                 // ← 注销即摘工具
});
const present = ctx.subagents.getProvider(config.provider);
if (present !== void 0) mount(present);
else ctx.logger.info(`subagent provider "${config.provider}" not registered yet;
  the "${config.toolName ?? "subagent"}" tool will register when it appears`)
```

**四个关键性质**：
1. **注册一个 provider → 对应的委派工具自动出现**（lazy mount，甚至可以"先配工具、后接 provider"）
2. **注销 → 工具自动摘掉**
3. **工具没有 provider 参数** → **一个 provider 一个工具名** → **工具名即路由**
4. `toolFilter { allow, deny }` / `persona` / `agentOptions{provider,model,maxTokens}` → **能力差异化是原生字段**

**这不是自创模式**——`dsh-base` 里本来就配了两个实例：

```yaml
- id: tool-subagent            # provider: spawn, toolName: subagent,      backgroundMode: continuable
- id: tool-subagent-fork       # provider: fork,  toolName: subagent_fork, backgroundMode: one-shot
```

✅ **订正（2026-09-14 实测）**：`dsh-web-app` 在 **host plane** 把那几个工具行 `disabled: true` 了，
**但这不等于「顶层没有委派能力」** —— 每个随附 preset（`code` / `standard` / `cordis`）
又在 **agent plane** 把它们挂了一遍（未 `disabled`）。**实测**：会话里模型手里确实有
`subagent` / `subagent_fork` / `list_agents` / `interrupt_agent` / `send_message`。
（`minimal` preset 是例外，它确实没有。）

⇒ **真正的分工是「host 出 registry 与 backend，preset 出工具行」** —— §3.4 引的原文正是这个意思，之前读漏了。
**判据**：想知道「模型能用什么」，读会话的 `request/header`
（`scripts/dump-request-tools.mjs`）；**不要**只看 host plane 的 `--dump-config` ——
那里看到的 `disabled: true` 不代表 agent 层也没有。

### 3.4 ★ 上游的架构分层：注册表在 host plane，委派工具属 preset plane

`dsh-web-app/cordis.patch.yml` 的注释把设计意图写得非常清楚，这段必须原文引用：

> "The subagent **registry and its backends STAY in the host plane**. `subagents` is a
> **process singleton** with a cross-session query surface (`listChildren`, `followup`)
> that the host api-proxy serves to the browser, and a provider registers under a
> **globally unique name**, so a per-session copy would both starve that host row and
> collide on the second session. **What a preset chooses is which delegation TOOLS its
> agent sees**, below."

**三个硬结论**：

1. **`ctx.subagents` 是进程单例，且带跨会话查询面** —— `listChildren` / `followup`，
   **由 host api-proxy 直接提供给浏览器**（这就是 `dsh-client-ui-subagent` 谱系树的数据源）。
2. **provider 注册名全局唯一** → 不能 per-session 复制 → **注册表天然是全局的，正好是"能力库"。**
3. **禁掉的不是注册表，是"web preset 下的委派工具行"** —— 与 `tool-bash` / `tool-pwsh` 同理，
   它们本应属于 **preset realm**。所以**启用位置在 preset 层，不是 profile 层**。

**顺带一条印证了前缀缓存分析的原文**（`dsh-base` 注释，讲为什么 `subagent_fork` 保持 one-shot）：

> "a continuable child's `report` tool and prompt section precede the inherited history a fork
> exists to reuse; one-shot fork children install neither, **keeping the parent's request prefix**."

→ **DSH 自己就在为 prefix cache 做设计取舍**（宁可牺牲 fork 的续接能力，也不动父请求前缀）。
这与 §6 的取舍是同一个原则，也说明 §6 那条不能省。

**另有设计文档可查**：`.agents/notes/implemented/architecture/2026-08-10-fork-children-stay-one-shot.md`
（本机 node_modules 里没有 `.agents/`，需从上游仓库取）。

### 3.6 ★★ 补漏：能力库必须覆盖「工具层」，不只是「委派层」

> 本节 2026-09-14 由用户提醒后补 —— **原设计漏掉了整个工具层**。

**漏了什么**：前文把「能力」几乎等同于「`SubagentProvider`」。但模型手里**大部分工具并不来自 provider**：

| 层 | 载体 | 实例 | 原设计的覆盖 |
|---|---|---|---|
| **委派层能力** | `SubagentProvider` | `spawn` / `fork` / `council-architect` | ✅ 已覆盖 |
| **工具层能力** | MCP server / 工具插件 | **design-canvas 一家 60 个工具**、`tool-evolution` 3 个 | ❌ **完全没覆盖** |

⇒ 只登记 provider 的「能力库」，给模型的是**半个答案**。
§3 的失败模式⑤（子脑自进化后顶层认知过期）**不只发生在子脑上，同样发生在工具源上**。

**而 design-canvas 其实已经在做工具层的能力管理** —— 它自带 `capability_map`：

- **6 条能力线**：`design` / `refactor` / `observe` / `harvest` / `cross` / `meta`
- 每条线有 `label` / `desc` / `tools[{name, when}]` / **`direct`（可绕过导航直调的高频工具）**
- 它自己的设计说明写得很准：
  > 「MCP 工具集扁平广播…40+ 工具一次性铺给 agent，选择噪音大、易幻觉选错。
  > 与其把全部工具塞进一个 mega 入口（schema 膨胀反噬），不如给一个**纯只读的能力线地图**：
  > agent 不确定用哪个工具前，先调它分层定位，再进入具体工具。」

**⇒ 正确处理是「对接」，不是「重复造」**：

```
我们的 list_capabilities          →  跨源总览（委派能力 + 工具能力源清单）
      └─ 点名：「design-canvas：60 工具 / 6 条能力线，细节调 capability_map」
design-canvas 的 capability_map   →  它自己内部的线级导航
```

**顺带：能力库第一次抓到真问题**

`capability_map` 的线目录是一份**手工同步**的静态表（它自己的注释承认
「能力线目录（静态事实，改动工具名/新增工具时同步此处）」）—— 手工同步必然漂移。实测：

```
注册表工具数 : 60
能力线收录数 : 55
★ 已注册但没进任何能力线（4 个；导航工具 capability_map 自身已豁免）:
    go_originals · memory_observe · memory_targets · move_symbol
```

**这 4 个工具对「靠 `capability_map` 导航的 agent」是不可见的** —— 其中包括记忆系统的两个入口。
而「**从未被选用 ≠ 没用，可能是发现失败**」正是 §5.5.3 已经写过的偏差①。

⇒ 所以能力库对工具层要做的**第一件事不是"登记"，而是"把漂移变成可检出的"**。
已内置：
- `scripts/diff-dc-capability-map.mjs` —— 单独跑，出漂移报告
- `capability-registry.mjs check` —— 每次校验都会重扫工具面并报漂移
- `list_capabilities` 的输出里也带 `[!] N 个工具未进能力线`

## 4. 你的三条注册规则 × 现成机制

| 规则 | 落点 | 备注 |
|---|---|---|
| **同功能升级 = 下一代换上一代** | `registerProvider(新)` + 注销旧的 → `provider-removed` 自动摘掉旧工具 | **必须保留 lineage**（下面 §5） |
| **新方向 = 重新注册** | `registerProvider` → `provider-added` → 委派工具自动出现 | 天然支持 |
| **一个能顶两件事 = 合并** | 注销两个 + 注册一个（工具名取新） | 合并前必须**在两个各自的 holdout 上都过**，否则是"用 A 的强项掩盖 B 的退步" |
| **（你漏了）淘汰** ⚠️ | 注销 + 归档 | **没有淘汰，能力库会膨胀到无法路由。** 判据：长期零命中 / 被他者完全覆盖 / 重叠度过高 |

**淘汰的判据建议**：让**重叠度**成为合并与淘汰的共用判据——
若两个 provider 能通过对方 holdout 的比例 > 阈值，则**它们其实是一个能力**，要么合并、要么淘汰弱者。
这同时压住了 §5 的膨胀风险和 §6 的路由退化。

## 5. ★ 能力级蓝绿：注册表替换本身就是蓝绿

这是本提案最漂亮的地方，也是它对接《换代 vs 重启》的接口：

> **注册新 provider 时，旧 provider 仍在跑**（in-flight 的 subagent 属于旧 provider 的会话）；
> **新的委派走新 provider。**
> → **"下一代换上一代"在这里是免费的** —— 不需要 switchboard，不需要换代状态机。

因为**"委派"这个动作每次都从注册表取当前值**，而 in-flight 的委派已经绑定了它的 provider。
**蓝绿不是被实现出来的，是委派语义自带的。**（呼应 `docs/single-front-brain-delegation.md` §4）

**但有两件必须补**：

1. **lineage（谱系）**：`SubagentProvider` 目前**没有版本/来源概念**。
   没有它就回答不了"现在的 X 能力是哪来的、什么时候换的、上一版为什么被换掉"，
   也无法做**谱系毒性召回**（OWASP 点出的"一次投毒永久留存"）。
   → 需要一个旁挂的 `capability-registry.json`：`{ id, version, source, acceptance, holdoutHash, registeredAt, supersededBy }`。
2. **注册门**：注册 = 采纳，必须过闸。`registerProvider` 是纯 API，**它不会替你验证**。
   → 闸放在**调用方**（Hub / 控制面），而不是 provider 内部。

**并且这个"注册门"就是《自进化总纲》§5 判据阶梯的能力级实例**：

```
L0 机械门   → provider 能启动、接口 5 个成员齐、capabilities 声明与实际一致
L1 不变量门 → toolFilter 不越权（设计者不能有生产写权）、凭据边界
L2 基线不退化 → 在既有能力集上不劣化（不抢别人的活）
L3 隐藏 holdout → 优化器看不见的用例 + 红队对抗用例
L4 反事实对照 → 与"现役同能力"shadow 对比
```

### 5.5 上层反馈：盲评、行为信号、与"信号 / 判据"的分工

用户提案：**"这个 Agent 也可以像工具商店一样，由上层（消费者）对返回结果评分 —— 满不满意 —— 然后提出修改意见。"**

比现状好在哪：现在 `tool-evolution` 是 **LLM 自评分**（`tool_score` 1–10）——**被优化者给自己打分**，
是最坏形态（既能刷高分数避免被改，也能刷分触发它想要的改动）。
改成"上层/消费者评"至少是**不同上下文**，判据独立性上了一级。

#### 5.5.1 盲评（不告诉它"你在被测"）能解决什么、不能解决什么

用户的第一个反驳：**"你只要不告诉它自己在被受测，就不会有故意讨好。"**

**能解决的（真的有效）**：

- **显式讨好**：知道在考试 → 加免责声明、拉长解释、堆自信措辞、迎合评委口味
- **应试特化**：针对"考核轮"的风格优化

**解决不了的（这才是要害）**：

1. **隐藏的是"哪一次是考试"，不是"评分这件事存在"。** 而激励来自后者。
   只要它知道"我的产出会被上层看并评价"，讨好的激励就一直在——**这不是它知不知道，是它能不能推出来**。
2. **更根本：讨好往往不是作弊，而是"正确地做被要求的事"。**
   任何 assistant 的本能目标都是"让用户满意"（DSH 的 system prompt 里就会写）。
   于是"让上层满意"与"把事做好"在**目标函数层面就重合了**——客服 agent 学会动不动就退款，
   它并没有意识到自己在被奖励，它只是在优化"让客户满意"。
   **⇒ 讨好的根源不是"知道在考试"，而是"收益函数由判据持有者的主观反应定义"。**
3. **有一个无法回避的张力**：我们要顶层**给修改意见并迭代** ——
   而"迭代"本身就是在告诉下层"**你的产出会被评价**"。
   同理，我们要求"委派详情可展开" —— **一旦它知道自己可被展开查看，这个知识等价于"会被评价"。**
   ⇒ **要迭代就必然暴露"有评价"。信息隐藏路线与迭代需求直接冲突。**

**所以盲评值得做（提高信号质量、减少噪声），但它的定位是"提高信号的纯度"，
不能把信号升级成判据。** 解药始终是：**让判据不经过任何人的主观反应**（可执行 `acceptance` + 隐藏 holdout）。

#### 5.5.2 信号有三层强度（用户的第二点指向了更强的那一层）

用户的第二个论点 —— **"不需要专门抱着测试心态，正常使用它就行；多开会话、多放几轮任务，总有用到它的时候再评分"** ——
比第一点强得多。它把"评测"从**额外流程**变成了**使用的副产品**。把这句话形式化：

| 强度 | 信号 | 性质 | 可否伪造 |
|---|---|---|---|
| **最强** | **选用 / 复用 / 弃用**（行为） | **costly signal** —— 选错要付代价 | ❌ **不可伪造** |
| 中 | 满意度 + **具体理由 + 可复现反例** | 声明 + 证据 | ⚠️ 可伪造，但有信息量 |
| 最弱 | 裸满意度评分 | **cheap talk** | ✅ 可随意伪造 / 敷衍 |

**关键洞察**：

> **"打 8 分"是声明；"下次还用不用它"是承诺。**
> 一个 agent 可以给自己打 10 分，也能让上层给它 9 分 ——
> **但它没法强迫别的 agent 下次还用它。**

⇒ **工具商店的真正改造不是"换个人来打分"，而是：
把打分降级（只作辅助证据），把行为信号升级（作为主信号）。**

用户更早说过"工具域要有一个**让 LLM 用起来顺不顺手**的指标"——**那句话本来指的就是行为信号**，
不是主观评分。现在这条更清楚了。

#### 5.5.3 行为信号的两个偏差，与解药

**偏差 ①：样本选择偏差。** 只有"被选中过"的能力才有数据。
一个能力可能因为**名字不起眼 / 描述写得差**而从不被选中 → 永远没数据。
**但"从未被选用" ≠ "没用"，而可能是"发现失败"。这两者必须区分，否则你会淘汰掉好能力。**

> **解药：探索配额。** 用一小部分委派**强制**派给低选用率的能力。
> 没有它，能力库会锁定在早期赢家上（富者愈富 = multi-armed bandit 的标准问题）。

**偏差 ②：高选用率可能是"描述过度承诺"。** 一个能力可以靠漂亮的描述被大量选中而实际平庸。

> **解药：同时记录两个指标，并看它们的差值。**
>
> | 指标 | 含义 |
> |---|---|
> | **选用率** | 发现性 / 吸引力（描述写得好不好） |
> | **复用率** | 交付之后**被再次选用**的比例 = 真实价值 |
>
> **高选用率 + 低复用率 = 描述过度承诺** —— 这是一个**具体、可检出**的失败模式，而不是模糊的"质量下降"。

**另外**：评分者之间要**互相隔离**（不共享彼此的评分），否则顶层的偏好会被下游继承，相关性污染会让"多 agent 投票"退化成"一个 agent 投票 N 次"。

#### 5.5.4 结论：信号与判据的分工

| | 提供者 | 性质 | 频率 / 成本 | 作用 |
|---|---|---|---|---|
| **信号** | **行为（选用/复用/弃用）** 为主<br>满意度 + 具体理由为辅 | 连续、软 | **高频、零边际成本**（使用的副产品） | 决定**何时值得花昂贵的判据** |
| **判据** | 可执行 `acceptance` + 隐藏 holdout | 布尔、硬 | **低频、昂贵** | 决定**是否采纳** |

> **信号决定何时花判据；判据决定是否采纳。**

**两条硬约束**：
1. **裸满意度评分应被丢弃，不采纳**——它没有成本、没有信息量。
   评分要成为有效信号，**必须附"不满意的具体理由 + 可复现的反例"**。
2. **"修改意见"的正确形态是候选提案** `{path, change, expectedGain, falsifier}` → 进注册门。
   **满意度本身不进闸。**

**对工具商店的直接推论**：它现在只有"LLM 自评分"一种东西，**既不是信号也不是判据**。
应改为：**行为信号（选用/复用/弃用）作主信号 + 可执行用例作判据**。
更彻底的形态是用户提的 —— **每个子 agent 里都装工具商店**：
不再是"一个 agent 给工具打分"，而是**一堆 agent 在真实使用中选用、复用、弃用**，
于是**反馈从"评测环节"变成"使用痕迹"**。这与"实验室阶段不设收益率门槛"是同一条原则：
**让反馈成为使用的副产品，而不是额外流程。**

## 6. ⚠️ 唯一必须量化的取舍：能力清单变化会击穿前缀

**机制**：每个 provider = 一个 `toolName` → **多一个工具 = tools 段变化**。
而 tools 段在 **system prompt / header** 里 → **注册或注销一个能力 = 一次前缀改写**。

我们实测过这条曲线的代价（`docs/context-cache-efficiency-measurement.md`）：
**一次前缀改写后 5 轮命中率 = 45.06% → 57.49% → 75.22% → 76.98% → 82.01%**，全部低于 93% 验收线。
而且这是已确认的第③类改写源（tools 数量 69→70→71 触发 header 重建）。

**一个会频繁注册/注销能力的能力库，如果直接用"一能力一工具名"，会持续击穿缓存。**

三个方案：

| 方案 | 前缀稳定性 | 路由明确度 | 说明 |
|---|---|---|---|
| **A：一能力一工具名**（官方模式） | ❌ 每次增删都击穿 | ✅ **工具名即路由**，判据可执行 | 适合**稳定核心能力** |
| **B：固定 `delegate(provider, task)`** | ✅ tools 段恒定 | ⚠️ 路由退回 LLM 自由选择 | 回到"路由判据不可执行"的老问题 |
| **C：分层**（推荐） | ✅ | ✅ | 见下 |

**方案 C（推荐）—— 按"变化频率"切开，和三级替换策略同一个思路**：

```
少数稳定核心角色（designer / builder / reviewer …）
    → 各占一个工具名（路由明确、判据可执行、极少变）
大量长尾动态能力
    → 走固定工具 delegate_capability(name, task)
    → 清单不进 tools 段，也不进 system prompt，而是 list_capabilities() 按需查询
```

这样：**动态的东西不进前缀**（符合我们反复验证的原则：外置化要在写入时 / 动态内容放尾部或按需），
而**核心路由保持可执行**。

## 7. 外部 Agent 接入 —— 你的最后一条，也是最有杠杆的一条

**接口侧**：写一个 adapter，把外部 Agent 包成 provider 只需实现五个成员：

```js
{ name: 'claude-code', 
  capabilities: { outputSchema: false, depthLimit: false, toolFilter: false, persona: false },
  inheritsParentContext: false,
  start(request) { /* 起外部进程 / 调 HTTP / 跑 CLI，返回 output blocks */ } }
```

**但有四个硬问题，必须在注册门里解决**：

| # | 问题 | 处置 |
|---|---|---|
| ① | **`acceptance` 由谁定？** | **必须由我们定**（设计师产出）。**绝不能采信外部 Agent 自报的合格声明**——否则就是接受一个"自证合格"的能力 |
| ② | **凭据与文件边界** | 明确它的可见范围（沙箱 + 凭据范围），`toolFilter` 不适用时要在 adapter 层强制 |
| ③ | **可靠性** | 外部依赖会挂/超时/**静默降级** → 能力健康状态必须上报（`dsh-client-ui-subagent` 的 `diagnostic.*` 是现成挂载点） |
| ④ | **版本追责** | 外部 Agent 会自己升级（你控制不了）→ 必须记录**接入时的版本**，且**升级视为新候选**，重跑注册门 |

**这一条的战略意义**：它把"自进化"重新定义为 **能力组合**，而不是 **自我修改**。
于是进化的瓶颈从"你自己造不造得出来"变成 **"你能不能发现并接入更好的能力"**。
——这也正是"拆掉无谓限制"的极致形式（《自进化总纲》§6.0：**限制必须能指认它防住的危害，否则就是纯能力税**）。

**并且它天然引入一个新角色：侦察（scout）**——负责发现外部更强的能力，产出**候选**
（接口 + acceptance + 来源），不产出代码。
这比"让它自己改自己"安全得多：**候选必须过注册门才能上线。**
