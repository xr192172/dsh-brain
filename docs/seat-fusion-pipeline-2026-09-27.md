# 席位融合管线（外部 agent → 我们的席位）

- 日期：2026-09-27
- 触发：用户授权「模仿它写，把里面已有的子 agent 调过来，通过我们的自进化思路把这 200 多个整合融合成少数的几个，作为自进化的第一步」
- 前置阅读：`docs/prior-art-subagent-marketplace-2026-09-27.md`（格式来源）、`seats/README.md`（目录约定）、`seats/schema.json`（判据）

---

## ★ 先说一个必须排掉的陷阱

用户的表述是「**把 200 多个整合成少数的几个常用的**」。

⚠️ **字面执行会违反铁律 28**：「**"扫全目录" ≠ "精选入口"** —— 目录倾倒把说明书降级成噪音；
**交付物要保持用户原话的粒度**」。

- **202 个 agent 的来源是"人的判断"**（`wshobson/agents` 是手工挑选 + 社区 PR）
- **我们的东西是"判据的产物"**（自进化：候选 → 评估 → 选择）
- ⇒ ★ **把 202 个按某个规则合并成 5 个，等于用一个手工规则替代判据** ——
  那不是自进化，是**把自进化降级成编辑**。

### 正确的形状：候选池 + 判据筛选，**不预设数量**

```
外部市场（MIT，可合法取）
      │  ① 取料（带 provenance：来源/许可/日期/我改了什么）
      ▼
seats/candidates/*.md        ← ★ 未融合、未上线，不参与调度
      │  ② 融合（删知识、留纪律、补契约）
      ▼
seats/library/*.md           ← 上线席位，被 SEAT_PERSONAS 读取
      │  ③ 判据筛选（"保留哪些席位"由读数决定，不由手数决定）
      ▼
数量是**结果**，不是输入
```

★ **关键点**：**"几个"是读数，不是设计目标。** 若判据说需要 9 个，那就是 9 个；
判据说 2 个够，就砍到 2 个。**预设"要 5 个"就已经不是自进化了。**

## ② 融合的具体动作（不是复制）

从 `library/` 的对照实例看（`candidates/external-backend-architect.md`）：

| 外部原文 | 融合后 | 依据 |
|---|---|---|
| 15 个能力大类，约 **12,000 字符** | **全部删掉** | 那是**知识**，应由 skill 按需加载承载（我们 skill 最大 29 KB）。若每席塞 12 KB，脸就炸了 |
| `name: backend-development-backend-architect` | `name: external-backend-architect` | 去它的插件命名空间，换我们的前缀 |
| `description` 500+ 字符，罗列能力 | 砍到 ≤260 字符，**只留触发条件** | ★ superpowers 实测：description 写能力摘要 ⇒ agent 照着摘要做、跳过正文 |
| **无** `tools:` | `tools: readonly` | 补机制层档位 |
| Core Philosophy / Behavioral Traits | **保留**（去掉散文） | 这是判断依据，是席位的价值所在 |
| **无** Key Distinctions | **补** | ★ 声明"我不做谁的活" |
| **无** Workflow Position | **补** `After/Complements/Enables` | ★ 编排顺序由席位自声明，不再硬编码在调用方 |
| **弱** Output Examples | **强化成** Output Contract（固定段序 + 三态） | 让交付形状可判定 |
| **无** Rationalization Table | **补** | ★ superpowers 的招 |
| **无** Red Flags | **补** | ★ superpowers 的招 |

★★ **一句话**：**删掉"它知道什么"，保留并强化"它怎么做事"。**
知识是可替换的（skill、检索、模型自身能力）；**纪律与契约是不可替换的**（那才是席位的身份）。

## ③ 判据筛选（"保留哪些"怎么决定）

★ **不许用"常用不常用"当判据** —— 那是主观的，不可判定（铁律 28：判据不许是同义反复）。

**可判定的筛选读数**（每条都要有）：

| # | 判据 | 怎么取数 | 阈值 |
|---|---|---|---|
| F1 | **它被调用过吗** | 历史委派记录里数"该席位的 provider 名出现次数" | 从未被调用 ⇒ 候选降级 |
| F2 | **它的产物被采纳过吗** | 它的产出进入最终变更的比例 | 长期 0 ⇒ 候选降级 |
| F3 | **去掉它判据会红吗** | ★ **消融自证**（铁律 21）：撤掉该席位，门是否变红 | 不红 ⇒ 该席位未被任何判据依赖 |
| F4 | **它和别的席位职责重叠吗** | `Key Distinctions` 的跨席对照是否互为镜像 | 重叠 ⇒ 合并，**并说明合并后谁做判断** |
| F5 | **它的边界可核吗** | `tools:` 档位与它 `Key Distinctions` 里说的"不做"是否一致 | 不一致 ⇒ ★ 散文与机制脱节（见下） |

★★ **F5 是本项目最该盯的一条**。事故先例（`packages/subagent-council/src/index.ts:151-179`）：

> `architect` 的 persona 白纸黑字写「默认只读…不要修改任何文件」，
> **但它真的往仓库里写了一个脚本**。
> ⇒ **persona 里的话只是话**；真约束是 `SEAT_TOOL_SCOPE` → `tools.restrict()`。

⇒ **融合时必须同步检查**：`tools: readonly` 与正文里写的"我不做 X"**必须一致**。
不一致 ⇒ **以机制为准，改散文**（不是反过来）。

## ④ 飞轮怎么转起来（用户说的"后面自己开飞轮"）

```
① 取料    外部市场 → candidates/（带 provenance）
② 融合    candidates/ → library/（删知识、留纪律、补契约）
③ 派活    library/ 的席位被真实调用（council 两席 / 新增席位）
④ 采数    F1–F5 的读数累积（调用次数 / 采纳率 / 消融结果 / 重叠检测）
⑤ 筛选    按读数淘汰、合并、晋升（★ 数量由读数决定）
⑥ 回流    淘汰的理由写回 candidates/ 的 provenance 或新建一份"墓碑"
   └─→ 回到 ②（下一轮融合带上上一轮的读数）
```

★ **飞轮的启动条件**：**必须先有 ④ 的读数，才谈 ⑤ 的筛选。**
现在只有 ② 做完了一步（1 份候选融合成了 1 份候选）。**④⑤ 还一个读数都没有** ——
所以**此刻不许做任何"合并成几个"的决定**。
