> **这份文件是当前架构的权威记录**，来自用户 2026-09-20 的口述修正。
> **它取代**以下文档在"顶层结构"上的表述（正文其余部分仍然有效）：
> `docs/three-brain-evolution.md`（「三脑演化循环 · 固定分工」）、
> `self-evolution-design.md` §6（多模型会议室 = "决策层"）与 §11.7（canonical 命名表把三脑当顶层）。
>
> ⚠️ **在此之前，这套修正从未被任何文档记录过** —— 2026-09-20 盘查确认：
> 全仓库只有当天的一条日记提到"专家评审层"，而"三脑"是被**当成顶层**固化的。
> 这正是下一位读者（包括 AI）会在旧模型上打转的原因。

---

## 1. 为什么改：三脑不再是顶层

旧模型（已作废）：

```
三脑（right / left / sandbox） ← 顶层
  └── 决策层（多模型会议室）
```

**用户的修正**：

> 三脑**已经被颠覆了** —— 或者说，**三脑已经是子 agent 的一部分**。
> 我们只需要构建**三个用来调控其他子 agent 的脑**即可。
> 上层只需要做一个**专家评审团**，用以接入多模型讨论。

⇒ **三脑没有被删除，而是"降格 + 改职责 + 改形状"**：从"顶层三分工"，
变成"**子 agent 层内部的三个工具**"（**搭建 / 更新 / 测试**；用户 2026-09-20 订正：是"三个工具"，不是"三个脑"）。

## 2. 新架构（两层）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 上层：专家评审团                                                       │
│   · 多模型讨论（MoA 式：分层 proposer / aggregator）                    │
│   · ★ 用户可以自行选择"用几个模型"去讨论（模型数与成员是配置项）          │
│   · 向下发布任务                                                       │
│   · 可选：接一个开源的"模型管理层"负责多 provider 接入（见 §3）           │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ 发布任务 / 回收结论
┌───────────────────────────────▼──────────────────────────────────────┐
│ 下层：子 agent 层  ← ★ 进化发生在这里                                  │
│   · 维护"子代理自进化"的循环与规范 —— 有问题就唤起子代理去规范执行        │
│   · ★★ 三格的**形状不同**（2026-09-20 用户定，理由=**防串供**）：         │
│       ① 隔离被测（实验/沙箱）→ **单独的工具**  ← 无判断权，工具足够        │
│       ② 生产（造能力 / 产 diff）→ **独立的子 Agent**                     │
│       ③ 进化（判定 + 审批）  → **独立的子 Agent**                       │
│       ⇒ ②③ 必须**不同主体**：否则等于同一个 agent 既生产又批准 = 自我批准  │
│   · 被操作的对象 = 子代理（= 能力）；★ 来源 = skill（skill 构建成 subagent）│
│   · 进化手段：用「使用数据 / 测试数据」做 ① 工具的进化  ② 工具的合并        │
│   ⇒ 自进化 = 能力库的注册 / 升级 / 合并 / 淘汰（单位从"整体"下沉到"能力"） │
└──────────────────────────────────────────────────────────────────────┘
```

**要点（逐条来自用户口述）**：

1. **顶层是评审团，不是三脑。** 三脑降入子 agent 层。
2. **★ 三格及其形状（2026-09-20 定）**：**① 隔离被测 = 单独的工具；② 生产、③ 进化 = 独立的子 Agent**
   （理由：**防串供**）。三格合起来服务"子代理自进化"的**循环与规范**。
   - **不是"三个脑"**（"脑"暗示独立会话/上下文 ⇒ 会踩 `self-evolution-design.md` §9 ①
     顶层上下文被委派记录吃掉，且多一层延迟）
   - **也不是"三个工具"**（若 ②③ 都只是同一个 agent 手上的工具，就**只有一个决策者** ——
     它既生产又批准）。**关键区分：分离「工具」≠ 分离「主体」。**
   - 这三格正好是能力库的生命周期（注册 / 升级 / 测试 → 采纳/淘汰），
     与 `self-evolution-design.md` §0.1「自进化 = 能力库的注册/升级/合并/淘汰」**是同一个模型**。
   - 详细理由、与项目原则的对应、以及现有资产盘点 ⇒ **见 §5.2 / §5.3**。
3. **评审团的多模型讨论是"可配置的"** —— 用户能选用几个模型、用哪几个。
4. **进化在子 agent 层发生**，不在顶层。
5. **子 agent 的来源 = skill**：skill 本身被**构建成 subagent**。接上 `self-evolution-design.md` §13
   「**技能树就是能力库**」——`SkillNode` 的字段表本身就是能力库。
6. **进化靠数据驱动**：使用/测试数据 → **工具进化**与**工具合并**
   （`SkillNode.Absorb`/`AbsorbOutcome` 就是"合并"的现成字段）。

## 3. 评审团的两个正交部件（**别混**）

用户把这两件事放在一起说，但它们是**两个不同的层**：

| | 是什么 | 现状 | 候选 |
|---|---|---|---|
| **A. 多模型讨论编排（MoA）** | **推理期**让几个模型各出方案 + 合成；不需要训练 | ⬜ 未建（设计 §6 有雏形：多模型会议室 + D1/D2/D3 分档 + 三条硬约束） | 见 §3.1 |
| **B. 模型管理层（gateway）** | **接入层**：一个 endpoint 打通多个 provider，管密钥/限流/计费/回退 | 🟡 **我们已有 `packages/key-pool-proxy`**（自研） | 见 §3.2 |

**A 需要 B 吗？** 不严格需要，但**多 provider × 多模型 × 每层多份调用**会立刻放大密钥、限额、成本、
回退这些运维问题 ⇒ 规模稍大就值得用成熟 gateway。

### 3.1 「几个较弱的小模型集成起来逼近 frontier」= MoA

**这就是用户记得的那条**（2026-09 已查实）：

- **MoA（Mixture-of-Agents）** —— Together AI，*"Mixture-of-Agents Enhances LLM Capabilities"*，
  2024-06 首发，**ICLR 2025 Spotlight**。**分层**架构：每层的每个模型把**上一层的全部输出**
  当额外上下文；默认 **3 层 × 每层 6 个模型**，角色分 **proposer**（出候选）与 **aggregator**（合成）。
  结论：**只用开源模型**在 AlpacaEval 2.0 上 **65.1%**，超过 GPT-4o 的 **57.5%**。**全程无需训练**。
- **Attention-MoA**（美团 LongCat，arXiv 2601.16596，2026-01）—— 更贴近用户的说法：
  用 **12B–32B 的小开源模型集成**，在 MT-Bench 上 **8.83**、AlpacaEval 2.0 LC 胜率 **77.36%**，
  **超过 Claude-4.5-Sonnet 与 GPT-4.1**。两个关键改动：**agent 间语义注意力**（互相批判修正，
  而非朴素拼接）+ **层间残差 + 自适应早停**（原版 MoA 到第 3 层后反而退化）。

> ⚠️ **一处口径差异**：用户记的是"**三个**小模型"，但论文里的"3"是**层数**（原版默认 3 层），
> 不是模型个数（每层 6 个；Attention-MoA 用 5 个异构模型 + 1 个摘要 agent）。
> **配置项该按"层数 × 每层成员数"设计**，别硬编码成 3 个模型。

### 3.2 开源模型管理层（gateway）候选（2026-08 实测星数）

| 项目 | 星数 | 许可 / 运行时 | 定位 |
|---|---|---|---|
| **LiteLLM** | **56k** | MIT 核心 / Python | **事实标准**：100+ provider，一个 OpenAI 兼容 endpoint，虚拟 key / 预算 / 回退 / 负载均衡 |
| **new-api** | 45k | — / — | one-api 的活跃分支，**中文生态首选**，后台与计费最好 |
| one-api | 36k | — / — | 中文生态老牌；按用户/分组/令牌计费 |
| Portkey | 12.7k | MIT / Node | 企业向：guardrails / 缓存 / 可观测 / 路由规则 |
| Bifrost | — | Apache / **Go** | 亚毫秒路由、复杂路由规则与故障转移 |
| AISIX / Envoy AI Gateway / Kong AI Gateway | — | Rust / Apache / NGPL | 统一治 LLM+MCP+A2A 流量 / 已在 K8s·Kong 上的团队 |

> ⚠️ **选型时必须知道的风险（2026）**：**LiteLLM 在 2026 年出过一次 PyPI 供应链事件** ——
> 有两个版本短暂夹带针对云凭据与密钥的恶意代码。
> ⇒ 与本项目既有铁律（`MEMORY.md` 铁律 10「不追上游版本」「只管 `@dsh-brain/*`」）一致的做法是：
> **引入第三方 gateway 要走与"外部 Agent 接入"同一套注册门**（`self-evolution-design.md` §11 的四个硬问题：
> acceptance 由我们定 / 凭据边界 / 可靠性上报 / 版本追责），**且锁版本 + 校验产物**。
> 我们的 `key-pool-proxy` 已覆盖"多 key 池 + 假 key 击穿测试"这一小块，**不是从零开始**。

## 4. 什么东西没变（别顺手推翻）

- **判据阶梯（L0–L4）与"先判据后能力"**：`self-evolution-design.md` §1 与 master-plan §10 **仍然有效**。
  评审团再花哨，**没有判据就还是 misevolution 的四条路径同时打开**。
- **§6 的三条硬约束**（先独立作答再交换意见 / 异议必须记录 / …）**继承**给顶层评审团 ——
  它们防的是 `consensus collapse`，与层级无关。
- **D1/D2/D3 按风险分档**（单模型 / 跨模型辩论 / 人审+holdout）**继承**。
- **能力库机制**（`SubagentProvider` 五成员 / `registerProvider` / `capability-registry.json`）**不变**
  —— 它本来就是"子 agent 层"的东西，这次只是把它**升格为进化发生地**。
- **switchboard 蓝绿换代**：仍是"顶层（消费者）换代、下层（能力）不需要"。

## 5. 定案与待定（**✅ = 已定；其余动手前必须问用户**）

1. ✅ **已定（2026-09-20）**：**三格形状 + 理由**（下方 ① ② 是同一条决定的两半，别当两件事看）

   > 用户原话（两轮，按时间）：
   > ①「说是 3 个脑，其实应该是 **3 个工具**吧 —— Agent 的搭建工具、更新工具和测试工具」
   > ②「**隔离被测是单独的工具，但生产和进化两个还是要做成独立的子 Agent，以防止和其他 agent 串供**」

   | 格 | 形状 | 为什么 |
   |---|---|---|
   | ① **隔离被测**（实验 / 沙箱） | **单独的工具** | 只负责"把东西放进隔离区跑"，**无判断权** ⇒ 工具足够 |
   | ② **生产**（造能力 / 产 diff） | **独立的子 Agent** | ★ **防串供**：产变更的一方不能与判方同源 |
   | ③ **进化**（判定 + 审批） | **独立的子 Agent** | ★ **防串供**：判方必须是**独立主体** |

   ⇒ **`self-evolution-design.md` §11.7 的 canonical 命名表（`right`/`left`/`sandbox`）正式作废**，
   只保留其"**角色必须由代码与会话边界定义**"的原则。

   **⇒ 与项目自己的原则完全对齐（"串供"是它们的口语版）**：
   - `self-evolution-design.md` §0.5 **无环原则**：「**被改的审批层不能自动批准自己的部署**」
   - `self-evolution-design.md` §6 三省六部：**「封驳权 = 独立否决权，且与中书省【不同机构】」**
     —— **"不同机构" 在这里就落成"不同 agent"**
   - `self-evolution-design.md` §6：评分者独立性 **跨模型 > 跨会话 > 同会话换 prompt**

2. **落地机制已有**：既然是"独立子 Agent"，就该用**已有的 `SubagentProvider` 机制**
   （`packages/subagent-council` 已示范 `ctx.subagents.registerProvider()`；
   provider 五成员 + `start()` 可注入 `persona`/`toolFilter`/`outputSchema`/`maxDepth`/`agentOptions`）。
   ⇒ **不需要新造"脑"的运行载体**，需要的是**两个新 provider**（生产席 / 进化席）+
   它们之间的**通信与留痕**（`dsh-tool-subagent-report` 的 `report` 汇报；委派档案**写入时外置化**，
   见 `self-evolution-design.md` §9 ①）。

3. ⚠️ **由此新冒出的结构问题（必须确认，别让它烂在暗处）**：
   **顶层「专家评审团」与下层「进化子 Agent」都有"判定"职责 —— 会不会重复？**
   我的理解（**待确认**）：
   - **评审团**判的是**大方向 / 任务本身**（选题、验收标准、预算）—— 粒度 = **任务**
   - **进化子 Agent**判的是**能力的增量**（L0→L4 逐层过门）—— 粒度 = **能力 / genome**
   ⇒ 粒度不同，**不重复**；但**"判据的持有者必须独立"这条原则对两者同时生效**。
   ⇒ 若确认，应写明"两级判定的粒度分工"，否则将来会有人问"为什么两处都在判"。

4. **这三格的骨架大部分已有**（2026-09-20 盘点）：

   | 格 | 现有资产 | 缺什么 |
   |---|---|---|
   | **① 隔离被测 / 搭建** | `ctx.subagents.registerProvider()`（`subagent-council` 已在用）+ `capability-registry register` + notice `'registered'` | **从 skill 自动生成 provider**（= §7 那条，未定） |
   | **② 生产 / 更新** | registry **已有** `version` / `supersededBy` / lineage（注册/升级/合并/淘汰）；notice 有 `'superseded' / 'merged' / 'retired'` | **独立的"生产席" provider** + 升级/合并的**操作入口 + 判据**（"合并后没劣化"= L2） |
   | **③ 进化 / 测试** | 注册门 **L0/L1** + `check-all` 15 门 + `eval-run` + 基线表 | **L2~L4** + **独立的"进化席" provider**（判据与 holdout 的所有权独立于被改者） |

   > ★ **发现**：`packages/capability-bridge/src/index.ts:337` 的说明里已经写着
   > 「隐藏 **holdout 哈希**、被谁取代、以及 lineage（注册/升级/**合并**/淘汰的历史）」
   > —— **能力库的数据模型里早就预留了 `holdoutHash`**，即"③ 进化/测试"这格
   > **早就设计好了、一直空着**。⇒ 我们要做的是**补上一直空着的那格**，不是发明新东西。

6. **评审团的"成员"怎么配**：用几个模型 / 哪几个 / 分几层（见 §3.1 的口径差异）
   —— 是**会话级配置**还是**全局配置**？
7. **gateway 选型**：自研 `key-pool-proxy` 继续扩，还是引入 §3.2 的某一个（含供应链风险的处置方式）。
8. **skill → subagent 的构建路径**：`SkillNode.Script/Tools` 升格成 provider 时，
   **谁**做这个转换（自动 / 人工 / 由哪个席）。
9. **"工具合并"的判据**：合并两家工具后，用**什么**证明"合并没有劣化"（这就是 L2 基线不退化）。

## 6. 与三条线的接驳

| 线 | 在哪 | 与本架构的关系 |
