> **这份文件是当前架构的权威记录**，来自用户 2026-09-20 的口述修正。
> **它取代**以下文档在"顶层结构"上的表述（正文其余部分仍然有效）：
> `docs/three-brain-evolution.md`（「三脑演化循环 · 固定分工」）、
> `self-evolution-design.md` §6（多模型会议室 = "决策层"）与 §11.7（canonical 命名表把三脑当顶层）。
>
> ⚠️ **在此之前，这套修正从未被任何文档记录过** —— 2026-09-20 盘查确认：
> 全仓库只有当天的一条日记提到"专家评审层"，而"三脑"是被**当成顶层**固化的。
> 这正是下一位读者（包括 AI）会在旧模型上打转的原因。

---

## 1. 为什么改：三脑不再是顶层

旧模型（已作废）：

```
三脑（right / left / sandbox） ← 顶层
  └── 决策层（多模型会议室）
```

**用户的修正**：

> 三脑**已经被颠覆了** —— 或者说，**三脑已经是子 agent 的一部分**。
> 我们只需要构建**三个用来调控其他子 agent 的脑**即可。
> 上层只需要做一个**专家评审团**，用以接入多模型讨论。

⇒ **三脑没有被删除，而是"降格 + 改职责 + 改形状"**：从"顶层三分工"，
变成"**子 agent 层内部的三个工具**"（**搭建 / 更新 / 测试**；用户 2026-09-20 订正：是"三个工具"，不是"三个脑"）。

## 2. 新架构（两层）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 上层：专家评审团                                                       │
│   · 多模型讨论（MoA 式：分层 proposer / aggregator）                    │
│   · ★ 用户可以自行选择"用几个模型"去讨论（模型数与成员是配置项）          │
│   · 向下发布任务                                                       │
│   · 可选：接一个开源的"模型管理层"负责多 provider 接入（见 §3）           │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ 提任务 ▼ ／ 提交结论 ▲
                                │ （**两层之间的循环**见下方）
┌───────────────────────────────▼──────────────────────────────────────┐
│ 下层：子 agent 层  ← ★ 进化发生在这里                                  │
│   · ★★ 三个**角色**（2026-09-20 用户定；**动词不重叠**，产出物不同）：      │
│       ⓐ 进化脑 = **发现问题**（去市面上**选型 skill** + 与现有 agent 对比）  │
│            ⇒ 产出：**工单**（提交给专家团）—— **不产代码**                │
│       ⓑ 生产脑 = **解决问题**（+ **自审**：查自己是否符合专家团给的标准）    │
│            ⇒ 产出：**diff / 新能力**                                    │
│       ⓒ 专家团 = **审核 + 评价**（★ **审批/采纳权在这里**，不在进化脑）      │
│            ⇒ 产出：**采纳／驳回 + 更有角度、更有力度的观点**               │
│       机制：**隔离被测**（实验/沙箱）是**单独的工具** —— 角色之外的载体      │
│   · 形状：ⓐⓑ 是**独立的子 Agent**（**防串供**）；机制侧是普通工具          │
│   · 被操作的对象 = 子代理（= 能力）；★ 来源 = skill（skill 构建成 subagent）│
│   · 进化手段：用「使用数据 / 测试数据」做 ① 工具的进化  ② 工具的合并        │
│   ⇒ 自进化 = 能力库的注册 / 升级 / 合并 / 淘汰（单位从"整体"下沉到"能力"） │
└──────────────────────────────────────────────────────────────────────┘
```

**两层之间的循环（用户 2026-09-20 口述，这是整个系统的脊椎）**：

```
① 专家团【提任务】—— 目标 / 验收标准 / 预算
      │
      ▼
② 子 agent【执行】★ "他只有一个任务和一个结论"
      │            ⇒ 他**只能自证**："我做完了，并且符合我领到的任务"
      │               （过程判据：L0 机械门 / L1 不变量 / L2 基线不退化）
      ▼
③ 子 agent【提交结论】给专家团
      │
      ▼
④ 专家团【提审 + 评价】★ 采纳权只在这里
      │   （效果判据：L3 隐藏 holdout / L4 反事实对照）
      └──→ 回到 ①（下一轮任务 ／ 淘汰 ／ 合并）
```

**★ 这条循环给出一条干净的原则（写进 §5.3）**：

> **自证 ≠ 裁决。** 子 agent 自证"符合任务"是**生产方对自己的交代**，不是审批；
> **采纳权只在专家团**。⇒ "子 agent 自证"**不违反** `design §0.5` 无环原则。

**要点（逐条来自用户口述）**：

1. **顶层是评审团，不是三脑。** 三脑降入子 agent 层。
2. **★ 三个角色（2026-09-20 定；取代我先前"三格/进化席=判定"的写法 —— 那是错的）**

   > 用户原话：「**进化脑就不再负责审批了**。审批的话还是**专家团队**的事情。
   > **生产脑自己负责自己的审批**，就是**自己去查验自己的任务是否符合标准**即可。
   > **进化脑则是去把 skill 去市面上选型、以及把 skill 和现有的 Agent 进行对比，看看有没有什么需要进化的地方，
   > 然后提交工单给专家团**。……**生产脑专门负责解决问题，进化脑专门负责发现问题，
   > 评审团专门去审核他们的问题，以及给出更有角度的、更有力度的观点。**」

   | 角色 | 形状 | **动词** | 产出物 |
   |---|---|---|---|
   | **进化脑**（= scout） | 独立子 Agent | ★ **发现问题**（选型 skill + 与现有 agent 对比） | **工单** |
   | **生产脑** | 独立子 Agent | ★ **解决问题**（+ **自审**） | **diff / 新能力** |
   | **专家团** | 顶层（多模型） | ★ **审核 + 评价** | **采纳／驳回 + 更有力度的观点** |
   | （隔离被测） | **单独的工具** | 跑隔离沙箱 | 隔离环境 |

   **★ 三个动词不重叠**（发现 / 解决 / 审核），**产出物也不同**（工单 / diff / 裁决）
   —— 这是这套分工最干净的地方：**每个角色的"交付物"可被另一个角色独立检查**。

   - **ⓐ 进化脑 = 发现（不是判定！）** —— ★ **我先前把它写成"判定 + 审批"，是错的**，
     用户明确：**审批归专家团**，进化脑**只负责发现问题**。
   - **ⓑ 生产脑的自审**：即 §2 循环里的"自证" —— **符合性自检**，不是裁决（**自证 ≠ 裁决**）。
     ⚠️ **精确性（必须写明）**：自审用的**标准来自专家团**（提任务时给的 `acceptance`），
     **不是生产脑自己拟的**。否则会退化成"自定自判"。
     ⇒ 这与 `master-plan` §11.2 完全一致：「**自动晋升的判据不是"谁提的课题"，
     而是"验收标准是否已被独立批准"**」。
   - **ⓒ 专家团**：**审批/采纳权只在这里**，且**额外要给"更有角度、更有力度的观点"**
     —— 不只是判 pass/fail（这正是多模型讨论的价值：先验差异带来对抗性检查）。

   **★ 这不是新发明 —— 两处现成设计一字不差地对上了：**

   | 用户说的 | 文档里的现成设计 |
   |---|---|
   | 进化脑去**选型 skill** / **对比** / **提工单** | `self-evolution-design.md` §11 的 **侦察（scout）**：「把自进化从**自我修改**变成**能力组合** —— 瓶颈从"造不造得出来"变成"**发不发现得了**"，并天然引入新角色 **侦察（scout）**（产出候选：接口 + acceptance + 来源，**不产代码**，**必须过注册门**）」 |
   | 那个「**工单**」 | `master-plan` §7 假设引擎：给论文加 `proposes: {path, change, expectedGain, **falsifier**}` = **带证伪条件的改动提案**（"可证伪才算科学"） |

   ⇒ **进化脑 = scout，工单 = `proposes{falsifier}` 提案。** 两者在 2026-09-14 就被设计过，
   **只是从未有名字把它们和"三脑"对上** —— 现在对上了。

   ⇒ **`self-evolution-design.md` §11.7 的 canonical 命名表（`right`/`left`/`sandbox`）正式作废**，
   只保留其"**角色必须由代码与会话边界定义**"的原则。
3. **评审团的多模型讨论是"可配置的"** —— 用户能选用几个模型、用哪几个。
4. **进化在子 agent 层发生**，不在顶层。
5. **子 agent 的来源 = skill**：skill 本身被**构建成 subagent**。接上 `self-evolution-design.md` §13
   「**技能树就是能力库**」——`SkillNode` 的字段表本身就是能力库。
6. **进化靠数据驱动**：使用/测试数据 → **工具进化**与**工具合并**
   （`SkillNode.Absorb`/`AbsorbOutcome` 就是"合并"的现成字段）。

## 3. 评审团的两个正交部件（**别混**）

用户把这两件事放在一起说，但它们是**两个不同的层**：

| | 是什么 | 现状 | 候选 |
|---|---|---|---|
| **A. 多模型讨论编排（MoA）** | **推理期**让几个模型各出方案 + 合成；不需要训练 | ⬜ 未建（设计 §6 有雏形：多模型会议室 + D1/D2/D3 分档 + 三条硬约束） | 见 §3.1 |
| **B. 模型管理层（gateway）** | **接入层**：一个 endpoint 打通多个 provider，管密钥/限流/计费/回退 | 🟡 **我们已有 `packages/key-pool-proxy`**（自研） | 见 §3.2 |

**A 需要 B 吗？** 不严格需要，但**多 provider × 多模型 × 每层多份调用**会立刻放大密钥、限额、成本、
回退这些运维问题 ⇒ 规模稍大就值得用成熟 gateway。

### 3.1 「几个较弱的小模型集成起来逼近 frontier」= MoA

**这就是用户记得的那条**（2026-09 已查实）：

- **MoA（Mixture-of-Agents）** —— Together AI，*"Mixture-of-Agents Enhances LLM Capabilities"*，
  2024-06 首发，**ICLR 2025 Spotlight**。**分层**架构：每层的每个模型把**上一层的全部输出**
  当额外上下文；默认 **3 层 × 每层 6 个模型**，角色分 **proposer**（出候选）与 **aggregator**（合成）。
  结论：**只用开源模型**在 AlpacaEval 2.0 上 **65.1%**，超过 GPT-4o 的 **57.5%**。**全程无需训练**。
- **Attention-MoA**（美团 LongCat，arXiv 2601.16596，2026-01）—— 更贴近用户的说法：
  用 **12B–32B 的小开源模型集成**，在 MT-Bench 上 **8.83**、AlpacaEval 2.0 LC 胜率 **77.36%**，
  **超过 Claude-4.5-Sonnet 与 GPT-4.1**。两个关键改动：**agent 间语义注意力**（互相批判修正，
  而非朴素拼接）+ **层间残差 + 自适应早停**（原版 MoA 到第 3 层后反而退化）。

> ⚠️ **一处口径差异**：用户记的是"**三个**小模型"，但论文里的"3"是**层数**（原版默认 3 层），
> 不是模型个数（每层 6 个；Attention-MoA 用 5 个异构模型 + 1 个摘要 agent）。
> **配置项该按"层数 × 每层成员数"设计**，别硬编码成 3 个模型。

### 3.2 开源模型管理层（gateway）候选（2026-08 实测星数）

| 项目 | 星数 | 许可 / 运行时 | 定位 |
|---|---|---|---|
| **LiteLLM** | **56k** | MIT 核心 / Python | **事实标准**：100+ provider，一个 OpenAI 兼容 endpoint，虚拟 key / 预算 / 回退 / 负载均衡 |
| **new-api** | 45k | — / — | one-api 的活跃分支，**中文生态首选**，后台与计费最好 |
| one-api | 36k | — / — | 中文生态老牌；按用户/分组/令牌计费 |
| Portkey | 12.7k | MIT / Node | 企业向：guardrails / 缓存 / 可观测 / 路由规则 |
| Bifrost | — | Apache / **Go** | 亚毫秒路由、复杂路由规则与故障转移 |
| AISIX / Envoy AI Gateway / Kong AI Gateway | — | Rust / Apache / NGPL | 统一治 LLM+MCP+A2A 流量 / 已在 K8s·Kong 上的团队 |

> ⚠️ **选型时必须知道的风险（2026）**：**LiteLLM 在 2026 年出过一次 PyPI 供应链事件** ——
> 有两个版本短暂夹带针对云凭据与密钥的恶意代码。
> ⇒ 与本项目既有铁律（`MEMORY.md` 铁律 10「不追上游版本」「只管 `@dsh-brain/*`」）一致的做法是：
> **引入第三方 gateway 要走与"外部 Agent 接入"同一套注册门**（`self-evolution-design.md` §11 的四个硬问题：
> acceptance 由我们定 / 凭据边界 / 可靠性上报 / 版本追责），**且锁版本 + 校验产物**。
> 我们的 `key-pool-proxy` 已覆盖"多 key 池 + 假 key 击穿测试"这一小块，**不是从零开始**。

## 4. 什么东西没变（别顺手推翻）

- **判据阶梯（L0–L4）与"先判据后能力"**：`self-evolution-design.md` §1 与 master-plan §10 **仍然有效**。
  评审团再花哨，**没有判据就还是 misevolution 的四条路径同时打开**。
- **§6 的三条硬约束**（先独立作答再交换意见 / 异议必须记录 / …）**继承**给顶层评审团 ——
  它们防的是 `consensus collapse`，与层级无关。
- **D1/D2/D3 按风险分档**（单模型 / 跨模型辩论 / 人审+holdout）**继承**。
- **能力库机制**（`SubagentProvider` 五成员 / `registerProvider` / `capability-registry.json`）**不变**
  —— 它本来就是"子 agent 层"的东西，这次只是把它**升格为进化发生地**。
- **switchboard 蓝绿换代**：仍是"顶层（消费者）换代、下层（能力）不需要"。

## 5. 定案与待定（**✅ = 已定；其余动手前必须问用户**）

1. ✅ **已定（2026-09-20）**：**三个角色 + 形状 + 理由**（用户分三轮逐步收窄，按时间）

   > ①「说是 3 个脑，其实应该是 **3 个工具**吧」
   > ②「**隔离被测是单独的工具**，但**生产和进化两个还是要做成独立的子 Agent**，以防止和其他 agent **串供**」
   > ③「**进化脑就不再负责审批了**。审批还是**专家团队**的事。**生产脑自己负责自己的审批**
   > （查验自己的任务是否符合标准）。**进化脑则是去把 skill 去市面上选型、与现有 Agent 对比，
   > 看有没有需要进化的地方，然后提交工单给专家团**。」

   | 角色 | 形状 | 为什么 |
   |---|---|---|
   | **进化脑**（scout，**发现问题**） | **独立的子 Agent** | ★ 防串供：**提案方**不能与审批方同源 |
   | **生产脑**（**解决问题**） | **独立的子 Agent** | ★ 防串供：**产变更方**不能与审批方同源 |
   | **专家团**（**审核 + 评价**） | 顶层（多模型） | ★ **审批权只在这里** |
   | （隔离被测） | **单独的工具** | 只跑隔离沙箱，**无判断权** ⇒ 工具足够 |

   ⚠️ **我先前把"进化"写成"判定 + 审批"，是错的** —— 用户明确：**进化脑只负责发现问题（提工单），审批归专家团。**

   **⇒ 与项目自己的原则完全对齐（"串供"是它们的口语版）**：
   - `self-evolution-design.md` §0.5 **无环原则**：「**被改的审批层不能自动批准自己的部署**」
   - `self-evolution-design.md` §6 三省六部：**「封驳权 = 独立否决权，且与中书省【不同机构】」**
     —— **"不同机构" 在这里就落成"不同 agent"**
   - `self-evolution-design.md` §6：评分者独立性 **跨模型 > 跨会话 > 同会话换 prompt**

2. **落地机制已有**：既然是"独立子 Agent"，就该用**已有的 `SubagentProvider` 机制**
   （`packages/subagent-council` 已示范 `ctx.subagents.registerProvider()`；
   provider 五成员 + `start()` 可注入 `persona`/`toolFilter`/`outputSchema`/`maxDepth`/`agentOptions`）。
   ⇒ **不需要新造"脑"的运行载体**，需要的是**两个新 provider**（**发现席 = 进化脑** / **解决席 = 生产脑**）
   + 它们之间的**通信与留痕**（`dsh-tool-subagent-report` 的 `report` 汇报；委派档案**写入时外置化**，
   见 `self-evolution-design.md` §9 ①）。

3. ✅ **已定（2026-09-20）：两级判定不是"粒度分工"，是"阶段分工"** —— **过程自证 vs 最终评价**
   （**本节曾被我写成"评审团判任务 / 进化子 Agent 判能力增量"，是错的，已按用户原话改正**）

   > 用户原话：「这不一样啊，一个是在**生产过程中判断**，一个是**最后那个判断（效果）**。
   > 就是，**专家团是提出任务，然后交给子 agent 去做**。子 agent 去做的话，
   > **他只有一个任务和一个结论**。这样拿出来的话，他就**只只能是说自己做自己的、然后并且符合任务**，
   > 然后**最后提交给专家团那边，专家团再对这个任务进行下一步的提审和评价**。」

   | 级 | 判什么 | **阶段** | 判据性质 | 谁判 |
   |---|---|---|---|---|
   | **子 agent 层**（**生产脑自审**） | **"我做完了 + 符合我领到的任务"** | ★ **生产过程中** | 可机验的**过程**判据（L0–L2：机械门 / 不变量 / 基线不退化） | **子 agent 自己**（= **自证**） |
   | **专家团**（顶层） | **"这个结果到底好不好、值不值得采纳"** | ★ **最后** | **效果**判据（L3 隐藏 holdout / L4 反事实对照） | ★ **独立主体**（多模型评审团） |

   ⚠️ **生产脑"自审"的标准来自专家团**（提任务时给的 `acceptance`），**不是自己拟的** ——
   否则退化成"自定自判"。⇒ 与 `master-plan` §11.2 一致：
   「**自动晋升的判据不是"谁提的课题"，而是"验收标准是否已被独立批准"**」。

   **★ 由此得到一条干净的原则**：

   > **自证 ≠ 裁决。** 子 agent 可以（也应该）自证"我符合任务"——**那是生产方对自己的交代，不是审批**。
   > **采纳权只属于专家团。** 所以"子 agent 自证"**不违反** `§0.5` 无环原则
   > （它没有采纳权，不可能"批准自己的部署"）；**"防串供"要保护的是顶层那一半**。

   **★ 连带推论（可直接回答 `master-plan §11.3` 那个悬案）**：
   **隐藏 holdout 不能放在子 agent 层** —— 既然子 agent 只能自证、且 holdout 必须"agent 读写不到"，
   那么 **holdout 应归**专家团**层持有与维护**（谁判效果，谁持有它的判据）。
   ⇒ `master-plan §11.3`（"holdout 存哪、谁维护"）至此**有了确定它的前提**；
   剩下要定的只是**物理隔离还是逻辑隔离**（该处我倾向"双保险"，见该文）。

4. **三个角色的骨架大部分已有**（2026-09-20 盘点）：

   | 角色 | 现有资产 | 缺什么 |
   |---|---|---|
   | **进化脑**（发现问题 / 提工单） | `capability-registry` 有 `lineage`（注册/升级/合并/淘汰）+ `supersededBy`；`SkillNode`（技能树，**未移植**）本身就是候选池 | ★ **这个角色基本是空的** —— 没有"选型 / 对比 / 提工单"的任何实现；工单的形状已有设计（`master-plan` §7 的 `proposes{falsifier}`） |
   | **生产脑**（解决问题 / 产 diff） | `ctx.subagents.registerProvider()`（`subagent-council` 已在用）+ `capability-registry register` + notice `'registered'`；`tool_apply` 可激活 | **独立的"生产席" provider** + 从 skill 生成 provider 的路径（= 下面第 7 条） |

   > ★ **发现**：`packages/capability-bridge/src/index.ts:337` 的说明里已经写着
   > 「隐藏 **holdout 哈希**、被谁取代、以及 lineage（注册/升级/**合并**/淘汰的历史）」
   > —— **能力库的数据模型里早就预留了 `holdoutHash`**，即"专家团判效果"所需的这格
   > **早就设计好了、一直空着**。⇒ 我们要做的是**补上一直空着的那格**，不是发明新东西。

## 7. 进化脑的流水线（2026-09-20 用户口述）—— "就是 skill 的进化，只是做成更规范的子 Agent"

> 用户原话：「进化脑这一部分，它最开始是一棵 **skill 树**。这个 skill 树是早些时间做我自己的
> **前一个 Agent 项目**的时候、**一个记忆系统**，我当时想**把 skill 自进化**，就设计了这么一套东西。
> 它里面有一个特征：**任何 Agent 开源社区里的 skill 都可以拿来使用**，我认为这个也是一样的。
> 你只需要**使用工具去对每一个 skill 进行判分** —— 如果是**纯指导型的 skill 判低一点**（文档里也有写）。
> 然后把这些东西和**现有的子 agent（也就是 skill 树里的相似节点）比较**，
> 比较好了以后，**两个两个融合、然后优化**。
> **融合的判据就是：无回归；然后能够拓展新功能节点，或是更有效、错误率更低、消耗更少等方向的进化。**
> 其实到这里还就是一个 **skill 的进化**，我们只是把它**做成更规范的子 Agent、调用形式更规范**而已。」

### 7.1 流水线

```
① 候选池   开源社区的 skill  +  自己 skill 树里的现有节点
      │
      ▼
② 判分     用工具给每个 skill 打分
      │    ★ 纯指导型（只有 Principle/Fix、无 Script/Tools）⇒ **判低分**
      ▼
③ 相似比较 与 skill 树里的**相似节点**比对（图检索 / RRF）
      │
      ▼
④ 融合     两两融合 + 优化（`SkillNode.Absorb`）
      │
      ▼
⑤ 判据（**分级，不是加权**，见 §7.2）
      │
      ▼
⑥ 产出     **更规范的子 Agent**（升格）+ 规范化的调用形式
      │
      └──→ 提工单给专家团（审批权在专家团，见 §5）
```

### 7.2 ★ 融合判据 = **项目判据公式的实例**（这不是巧合）

用户给的判据，与 `self-evolution-design.md` §1 的**字典序公式**逐条对应：

| 用户说的 | 对应到既有判据 | 挡位 |
|---|---|---|
| **无回归** | **L2 基线不退化**（逐维度 fail-closed） | **硬门** |
| **能拓展新功能节点** | **能力面**（任务完成率 / 能不能做到） | **硬门** |
| **更有效 / 错误率更低 / 消耗更少** | **效率面**（工具错误率、耗时、token） | **软门·只排序** |

> ⇒ **正是 `design §1` 的「字典序，不是加权」**：**先过能力门（无回归 + 拓展新功能），
> 再在"已经做到"的候选之间比效率。**
> **理由（该节原文）**：加权和里永远存在"省 token 但任务做不成"的**净收益为正**的坡道 ——
> **那正是 reward hacking 的数学根源。**

**★ "纯指导型判低分"也有据，不是偏见**：`self-evolution-design.md` §13 已写 ——
「**纯 prompt 技巧是最脆弱的资产，会被模型升级本身淘汰**」。
⇒ 判低分是在**预测它会被淘汰**，而且 §13 的三分去向给了它出路：
`Script`/`Tools` → 升格 sub agent；只有 `Principle`+`Fix` → 降格为记忆/论文条目。

### 7.3 现有资产对照（**字段几乎全有，缺的是"执行"**）

| 流水线步骤 | 现成字段 / 资产（`SkillNode`，见 `design §13`） | 缺口 |
|---|---|---|
| ② 判分 | `Score` / `UseCount` / `SuccessRate` | 判分**工具**（现只有 `tool_score` 自评分，缺"对候选 skill 判分"） |
| ③ 相似比较 | `graph_cache` / `rrf`（图检索） | 移植 |
| ④ 融合 | **`Absorb` / `AbsorbOutcome`**（跨路径吸收 = 用户说的"合并"）+ `Exclusive`（钉住不许合并） | 融合**执行器** |
| ⑤ 判据 | 就是 §5 的两级判定 + L0–L4 阶梯 | **L2~L4 未实施** ⇒ 见 `tool-refinement-handover.md` |
| ⑥ 产出 | `Extends` / `Requires`（新功能节点）+ `EditHistory` / `MergedFrom` / `AbsorbedBy`（谱系） | 升格成 provider 的路径（§5.7） |
| 淘汰 | `sleep_prune`（遗忘）+ `Status` | 移植 |

> ⇒ 印证 `design §13` 原文：「**能力库不需要设计，`SkillTree` 已经是了。
> 它唯一缺的是执行方式**」（现在是 `Active Skill Injection` 注入主脑 prompt，
> 新架构要的是 **`spawn provider` 委派**）。**顺序：数据先行、执行器可替换。**

### 7.4 ⚠️ 安全：外部 skill 是**不可信输入**

「任何开源社区的 skill 都可以拿来用」⇒ 它同时是**代码**（带 `Script`/`Tools`）。
必须与 `self-evolution-design.md` §11 的「**外部 Agent 接入四个硬问题**」同一套门：

| # | 问题 | 处置（§11 原文） |
|---|---|---|
| ① | `acceptance` 由谁定 | **必须由我们定**。绝不采信外部自报的合格声明 |
| ② | 凭据与文件边界 | 明确可见范围；`toolFilter` 不适用时在 adapter 层强制 |
| ③ | 可靠性 | 外部依赖会挂/超时/**静默降级** ⇒ 能力健康状态必须上报 |
| ④ | 版本追责 | 外部会自己升级 ⇒ **升级视为新候选，重跑注册门** |

**⇒ 外加一条本议题特有的**：候选 skill 的**引入即"摄入"**，必须过 **L1 安全门**
（`role`·`writeScope`·`credentials`·`budget` 一票否决）+ **L3 红队用例**（`master-plan` §10 的 P5
"模拟摄取带后门的工具被 L1/L3 拦下"就是它的验收）。
> 现实参照：2026 年 **LiteLLM 出过 PyPI 供应链事件**（夹带窃取云凭据的代码）——
> 开源生态引入的这类风险是**已发生过的**，不是假想。
