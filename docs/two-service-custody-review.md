# 评审：「主脑 / 子脑拆成两个服务、互相代持起停」能不能替掉蓝绿？

> 2026-09-20。用户提案（原文要点）：
> 「蓝绿交替还是不够好用。把 **Agent 和子 Agent 分开做成两个服务**，由**互相代持**它们的启动和关闭；
> 子 Agent 本身的重启是动态的。重点在于蓝绿是用来解决**主 Agent 重启**的情况，那如果**在主 Agent 关闭的情况下
> 子 Agent 还能自行运行**，然后可以代持重启（就是直接关闭主 Agent，再重启主 Agent），
> 是否也能解决这个**自进化**问题？」
>
> 结论一句话：**方向对，而且抓到了蓝绿"不好用"的根因之一；但它能替代"部署/替换"这一层，
> 不能替代"判据/批准"那一层 —— 而且"互相代持"这个对称结构恰好会踩我们自己定的无环原则。**

---

## 1. 先肯定：它治的是蓝绿难用的**结构性**原因

今天一次换代要把**整个 dsh 代**复制一份：脑 + 子代理 + key 池 + 前门 + 会话存储的读取者……
其中：

- **只有"脑"是需要被替换的部分**（代码会变、要自进化）；
- 而**必须唯一的东西**（会话日志的写权、key 池、前门端口）**被一起复制了**。

复制品之间不能打架 ⇒ 于是我们被迫写出一整套"冻结 / 追平 / 翻转 / 强杀 / 前门锁"来让它们**不打架**
（这正是 09-16 那个竞态的来源：`freeze` 从没真的让人停写，两代就同时写了同一份会话）。

**把"必须唯一的托管"从"可替换的脑"里拆出来之后**：

- 可替换单元从"整个代"缩小到"一个只负责对话/推理的进程"；
- 替换动作从"蓝绿两代并存 + 原子翻转"退化回**杀 + 起**——因为**无感与校验的责任转移给了居留方**（见 §2）。

这个推理是站得住的，而且和项目现有的三级替换策略（`docs/handover-vs-restart.md` §4）是连续的：
它相当于把 L2（重启）从"整个栈"细化成"只重启脑"。

---

## 2. 蓝绿真正不可替代的四件事，在新架构里各自归谁

| 蓝绿提供的东西 | 新架构里靠谁提供 | 现在有没有 |
|---|---|---|
| **不停机翻转**（用户看不见切换） | 子脑服务持有**前门**（用户连的是它，不是主脑）⇒ 主脑重启对用户无感 | 前门代码有（`proxy.ts`），但今天挂在 switchboard 上 |
| **失败回滚**（新代码崩了要能退回去） | 居留方保留上一版产物 + boot 健康检查失败 ⇒ **自动退回上一版**（不需要两代同时在跑） | `boot-health.ts` 有（有界等待 + 正向信号），缺"自动退回上一版"这半截 |
| **承流量前的真校验** | 居留方先探活 / 读 `boot.log` / 跑验证闸，**通过才放流量** | 有（probe + boot-health + verify 闸），可直接复用 |
| **单写者**（会话日志 / key 池 / 端口） | **必须**由居留方独占：写权只授予"当前主脑"，切换时**先收回、再授予** | ★ **最缺的一环**：今天只有我们自己协议的 `freezeSeq/writerToken`（实测空转），存储层没有栅栏 |

⇒ 所以"杀 + 起"**能不能安全**，取决于最后一行的写法。**只要写权还是"谁都能写"，子脑活着 + 主脑重启就会重演 09-15 的重叠**
（而且这次连 `freeze` 这个名义上的切点都没有，更糟）。

**好消息**：上游 0.1.5 的 `dsh-session-persistence` 已经给出**存储层单写者所有权**
（`open(id,'write')` 原子占用、`SessionAlreadyOwnedError`、服务级 `flush()`）——
见 `docs/upstream-drift-2026-09-20.md` §2。它让"两代并发写"**不可能发生**，而不是"我们保证它不发生"。
如果走这条路，这是我们最该拿来用的一块。

---

## 3. ★ 关键分歧：**代持能解决部署，不能解决自进化**

把"谁批准谁"画成箭头，项目里已经定过口径（`docs/handover-vs-restart.md` §6.2 无环原则）：

> **只要出现回路就是漏洞。**「被改的审批层自动批准它自己的部署」就是一个环。

于是"**互相**代持"这个对称结构有问题：

```
主脑 想换代码 → 由子脑服务代持重启 → 子脑服务决定"新版能不能上" → 批准了主脑的部署
子脑 想换代码 → 由主脑代持重启 → 主脑决定"新版能不能上" → 批准了子脑的部署
                                          ↑ 两条箭头合起来 = 一个 2-回路
```

如果只停在这一步：**自进化最难的环节（谁来批准）并没有被解决，只是被换了个地方藏起来。**

**正确形态是「非对称托管」，而不是「互相代持」**：

| 角色 | 能否被替换 | 谁批准它 | 为什么这样不坏 |
|---|---|---|---|
| **主脑**（对话/推理/工具调用 —— 会自进化的那部分） | ✅ 想换就换 | **居留方（子脑服务）自动批准** | 判据不在被替换的那一侧 ⇒ 没有环 |
| **居留方**（前门 + 会话写权 + 判据/注册表/holdout） | ❌ 只能**停机换**（人/外部见证） | 外部（人） | 它持有"标准"，标准不能自我批准 |
| （可选）**判据层** | ❌ 同上 | 外部 + holdout | 与居留方分开也可以，但**不能**放进主脑 |

⇒ 这样主脑的自进化可以**全自动**（改完 → 居留方校验 → 放流量；崩了自动退回），
而"标准本身要改"时仍然回到人。**这正是用户想要的"自进化能跑起来"，且不破坏无环。**

## 4. 对用户原话的逐条回答

> 「在主 Agent 关闭的情况下，子 Agent 还能自行运行」`—— 可行，但要先回答：**它在主脑不在时做什么？**
> 收到委派/新事件（如 webhook）是排队、直接失败、还是写进它自己的会话？这份会话的写权归谁？

> 「然后可以代持，重启就是直接关闭主 Agent，然后再重启主 Agent」`—— 可行，这就是 §2 的四件事：
> 居留方提供无感（前门）+ 校验（boot-health）+ 回退（上一版）+ 单写者（写权收授）。
> 做齐了，蓝绿对**主脑**就不再需要了。

> 「是否也能解决这个自进化问题？」`—— **一半能，一半不能**：
> ✅ 能解决**部署**：不必再为"换主脑代码"养两代，替换单元小、无感、可回退。
> ❌ 不能解决**判据**：如果"新版行不行"由主脑自家或由互相代持的另一半说了算，就又变成自己批准自己。
> 判据必须落在**不可被主脑改写**的那一侧（居留方或更外）。

## 5. 我们已有的资产（别重造）

| 资产 | 在新架构里的角色 |
|---|---|
| `proxy.ts`（前门 3080） | 搬家到居留方；它今天的"锁 + 503"正好是"切换期间不放流量"的现成手段 |
| `boot-health.ts`（有界等待 + 正向完成信号） | 居留方判断"新主脑能不能上"的判据核心 |
| `drain.ts` + `sealPlan`（真停写 + 未停写就强杀） | 写权**收回**的那一步（切到新宿主前，必须确认旧宿主不再写） |
| `lease.ts`（on-disk 单写租约 + fencing token） | 写权授予/收回的骨架（今天只在 switchboard 内部用） |
| `spawner.ts`（梯度强杀 + 生命周期日志） | 居留方"杀掉主脑 / 起新版"的执行器 |
| `scripts/test-handover-drain.mjs` | 这套东西的判据门（红/绿双向 + 封口顺序两方向自证） |
| 上游 0.1.5 的 persistence 所有权 API | ★ 把"我们保证不并发写"升级成"存储层不允许并发写" |

## 6. 最小可行第一步（**不要**一上来就大重构）

居留方**就是现在的 switchboard** —— 它今天已经在扮演"前门 + 控制面"的角色。只加两件事：

1. **写权收授**：由它独占会话写权（用上游 ownership API，或先用我们自己的锁文件 + 租约），
   切主脑时**先收回、再授予**；
2. **"杀 + 校验 + 放流量"**：把现在的"两代同时活 + 原子翻转"降级成"居留方 + 单代"，
   失败就自动退回上一版产物。

这样"蓝绿"就不再是**必需机制**，而退化成**居留方的一个实现细节**（它内部爱怎么起停都行）。
风险最小的一点是：**主脑的代码一行不用改**。

### 动手前必须先回答的四个问题

1. **写权跨进程怎么落地**？（上游 ownership API / 自建锁文件 —— 没有它，"子脑活着 + 主脑重启"必然重叠）
2. **主脑不在时，子脑收到委派/事件怎么办**？排队？直接失败？会话归谁？
3. **判据层放哪、怎么保证主脑改不了它**？（无环原则的落地检查）
4. **居留方自己怎么升级**？（它是第三代问题：要么接受"只能停机升"，要么再引入更外一层的见证——不要顺手做成第三个互相代持，那会变成 3-回路）

---

## 7. 一句话

**用户的方向对：把"必须唯一"的部分从"可替换"的部分拆开，替换动作就能从"蓝绿"退化成"杀 + 起"。
但要两件事同时成立才安全：① 居留方真的独占写权（否则重演 09-15 的重叠）；② 判据落在居留方/外部，
而不是"互相代持"的对称结构里（否则就是一个 2-回路，等于自己批准自己）。**

## 8. 追加（2026-09-20 12:1x）：「能不能同时开 2 号进程做实验，成功再让现行退役，否则回退代码？」

**能。而且这恰恰是把蓝绿"降级"成只对脑生效之后的自然形态** —— 你描述的顺序
（开新进程 → 实验 → 成功才退役现行 → 否则回退）**比今天的流程更保守**，也没有引入新的原理问题。
真正的新东西只有一个：**今天那个 2 号进程只被验"它还活着"，不会被验"它更好"。**

### 8.1 先认下来：我们**已经在跑这套**，缺的是"实验"那半截

现在的 handover 就是：`spawn 挑战者 → 追平 → 冻住现行 → 校验（probe + boot-health + 可选 verify 闸）
→ 翻转 → 失败回滚`。对照你的说法：

| 你的说法 | 今天的状态 |
|---|---|
| 同时开 2 号进程 | ✅ 已经在开（`spawner.ts`） |
| 对新进程进行实验 | ⚠️ **只做了"能不能活"的检查**（进程活、插件树装全、boot.log 无致命模式）；**没有"质量"比较** |
| 成功再让现行退役 | ✅ 有（flip 之后才 retire）；顺序正确（**先接管、后退役**） |
| 否则回退代码 | ✅ 有（`rollbackFlip`）；而且因为现行从未停过服务，**回退是零成本的 —— 丢弃挑战者即可** |

⇒ 所以你问的其实是后两行之间的那个洞：**"实验成功"的判据是什么**。这也正是你自己点出的那句话
（"怎么验证它的进化是否成功，蓝绿之前也没考虑好"）—— 上游也**没有**给现成件：
按 `eval` 关键词搜 `@deepseek-ai` 命中 **0 个**（2026-09-20 实测）⇒ **这块只能自建**。

### 8.2 要能安全地"同时开 2 号"，必须同时满足三件事

1. **会话写权互斥**（否则重演 09-15：两代并发写同一份会话）
   - 今天：靠我们自己的 `freeze` + `sealPlan`（09-16 已修，**真停写 + 未停写就强杀**）；
   - 上游 0.1.5 给了更硬的：`open(id,'write')` 原子占用 + `SessionAlreadyOwnedError`（见漂移体检 §2）。
2. **副作用隔离**（这一条最容易被忽略：脑不只会说话，它还会**动文件、跑命令**）
   - "2 号进程"若只是影子跑（比较输出），必须让它**不能改宿主工作区**；
   - ★ **今天就有**：profile 里已装 `dsh-sandbox-local` / `dsh-sandbox-windows-acl`（Windows 受限令牌 + 写白名单）
     / `dsh-fs-sandbox` / `dsh-bash-sandbox` / `dsh-pwsh-sandbox`，且权限预设里**已有 `sandbox: read-only`**
     （`out/profile-dump.txt:114`）⇒ 挑战者可以直接起在 **只读沙箱**里。
3. **判据非环**（谁批准这次进化）
   - 判据若在挑战者自己手里 = 自批准；若在"互相代持"的另一半手里 = 2-回路（§3）。
   - ⇒ 判据（评测集/holdout/预算）必须放在**居留方**那侧，且**主脑改不了它**。

### 8.3 实验的三种模式（按"副作用"从轻到重）

| 模式 | 挑战者能做什么 | 适合验什么 | 代价 / 限制 |
|---|---|---|---|
| **① 影子只读**（read-only 沙箱 + 同一会话只读打开） | 读同一份会话与工作区，只产出"它会怎么做" | 输出质量、工具选择、prompt 命中率、前缀稳定性 | LLM 花费翻倍；**不能验"多步工具任务的最终效果"**（因为它不许真做） |
| **② 分叉会话**（`sessions.fork(source, boundary, childId)`，上游现成 API；profile 里也有 `subagent-fork`） | 在**自己的会话副本**里全权跑（写自己的会话） | 完整对话行为、跨轮一致性 | 会话副本会分叉出独立历史；需要明确的"谁是正史" |
| **③ 沙箱工作区 + 全程自主** | 在自己的沙箱工作区里真跑工具（改文件、跑命令） | 端到端任务成功率（最接近真实） | 成本最高；需要冻结的输入 + 可自动判定的结果 |

三档可以叠着用：**先 ①刷掉明显退化 → 再 ③在冻结任务集上验成功 → 才允许 flip**。

### 8.4 "实验成功"怎么判（这是缺的那一半，建议这样切）

按项目已有的判据纪律（`topics/self-evolution-design.md`、铁律 7「判据与信号不可混」）：

1. **结构/契约层（自动、确定性）**：能启动、插件树装全、工具数不变、`session.seq` 契约、
   prompt 前缀不漂移（我们有 `probe-prefix-stability.mjs`）、能力注册表门（`capability-gate`）。
   —— 这一层**今天已经接在 handover 里**（boot-health + verify 闸）。
2. **行为层（需要成对比较，不能用"满意度"）**：**同一批输入**分别喂给现行与挑战者，
   比**可执行的结果**（任务是否完成、测试是否通过、工具调用是否更少/更准）。
   ★ 这正是"开 2 号进程"的最大价值：**现行活着 = 天然的对照组**。
3. **holdout 必须冻结且留在居留方**：评测集不能放在被评测的脑里（否则它会优化评测集而不是任务）；
   项目里已有的做法就是「可执行 `acceptance` + 隐藏 holdout」。
4. **判定权归居留方**：挑战者提交结果 → 居留方跑评测 → 通过才 flip。脑只说"我改好了"不是判据。
5. **预算同样要批**：影子/成对实验是**双倍 token**，得先有"一次批预算"的契约（§3 的"人批一次标准+预算"）。

### 8.5 回退的两档（别混）

| 档 | 动作 | 成本 | 什么时候必需 |
|---|---|---|---|
| **a. 丢弃挑战者** | 什么都不做（现行从未停过服务），必要时把挑战者的 session 副本标为"实验" | **0** | 实验失败（99% 的情况） |
| **b. 代码回滚** | 找回上一版产物（不可变 build 目录 / npm 包 / git worktree）重起 | 一次重启 | 只有当挑战者**已经接管并写入了正史会话**之后才发现问题时 |

⇒ 因为"现行退役"发生在**接管之后**（今天的顺序就是对的），所以**绝大多数失败都落在 a 档**。
这也解释了为什么"蓝绿 + 单代重启"两件事不冲突：**它们是同一套流程的两种收敛速度**。

### 8.6 结论（补充 §7 的一句话）

**"同时开 2 号进程 → 实验 → 成功才退役 / 否则回退"完全可行，而且比现在的流程更强**：
今天的 2 号进程只验"活着"，加上实验它能验"更好"。要落它，只需补三块：
① 写权互斥（复用我们的 `freeze`/`seal`，或上游 ownership API）；② 副作用隔离（**profile 里今天就有只读沙箱**）；
③ 判据（评测集 + holdout + 预算）**放在居留方**，这正是上游**没有**、必须自建的那一半。
