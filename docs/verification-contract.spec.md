# 验证契约 · Verification Contract（规格草案，待 DSH 审）

> 本规格把「三脑 sandbox（会话内验证）」与「switchboard verify（代际验证）」统一到同一份
> 实现无关的验证契约上。二者不合并代码，但都遵守同一契约与同三条不变量。
> 定位与来源：对齐 ai-base/agent-shell 迁移路线图的思路 #2（三脑）+ 我们在 switchboard 上的
> verify 闸工作；参照 `ai-base/.trae/documents/ds-brain-dsh-migration.md` 第 1 表。

## 0. 一句话
**任何"由不确定的 Agent 产生、要替换当前现役态"的变更，必须先经过一个独立、隔离的验证者确认
"没变坏、确实可用"，验证通过才采纳；验证不通过时，现役态必须无损、且验证路径本身不能成为新的死路。**

## 1. 它管什么、不管什么（边界）
- 管：变更何时算"可采纳"（验证通过）；验证者与被验证者如何隔离；写权如何唯一迁移；失败的兜底。
- 不管：验证者内部用什么具体方法跑测试/采样（那是实例细节，本规格只定契约与不变量）。

## 2. 五个契约要素
1. **Subject（验证谁）**：一个"待采纳的变更"——会话内是"一段改进/一次决策"，代际是"一个新 gen（staging）"。
2. **Verifier（谁验证，必须独立）**：验证者 ≠ 被验证者，且不依赖被验证者自报 ok 的诚实性。
   - 会话内实例：三脑 `sandbox`（隔离验证）+ `right`（审计）。
   - 代际实例：switchboard verify 钩子（由 coordinator 派生的独立进程/脚本，读 JSON 判定）。
   - 不变量：验证者自身有独立存续能力——它挂了，系统仍能留在现役，不因"验证者与被验证者同生共死"而卡死。
3. **Criteria（判什么通过）**：至少满足"回归门"（不能更差），可选"改进门"（确实更好）。
   - 生存：probe / 调用可响。
   - 回归：测试通过率 ≥ 现役基线，且关键用例全绿。
   - 指标：内存（RSS/heapUsed）、启动耗时、错误率，相对现役基线不劣化（阈值可配）。
4. **Adopt（通过才采纳）**：验证通过，才把 Subject 提升为现役（会话内=采纳该决策/改进；代际=flip + retire）。**验证通过前，Subject 不得获得对共享写资源的写权。**
5. **Reject（失败不损坏现役）**：验证失败（或验证路径不可达）→ 回退/维持现役，绝不让系统停留在"旧的已停、新的也不行"的不可用态。

## 3. 三条不变量（本规格的核心，契约的实现都必须满足）
- **I1 · 写权唯一且延迟**：共享资源（会话日志 / 生产状态）的写权在任一刻只属于一方；
  Subject 在**验证通过前不获得写权**；写权从现役迁移到 Subject 是显式、且发生在"旧侧已停写"之后。
  （防的正是已发生的 `seq gap in committed region`：两 gen 并发 resume 写同一会话。）
- **I2 · 通过才采纳**：任何"替换现役"的动作都必须被验证闸门；无闸门的替换即便成功也视为违规。
- **I3 · 无死路线回退**：任何一步都不允许进入"现役已停、候选不可用、且无在场决策者"的状态。
  → 现役在验证通过前保持如常服役；验证者独立存续可决策；存在明确的回滚目标与回滚动作。

## 4. 两个实例（同契约，不同档）
| 维度 | 会话内（三脑 sandbox） | 代际（switchboard verify） |
|---|---|---|
| Subject | 一段改进/一次决策 | 新 gen（staging） |
| Verifier | sandbox + right（审计） | coordinator 派生的独立 verify 钩子 |
| 频次/粒度 | 小、快、每次推理 | 大、慢、每次换代 |
| 采纳 | 采纳决策/合并改进 | flip + retire |
| 回滚 | 保持现役决策栈 | rolled-back（swap 回旧 active） |
| DSH 落点 | `subagent / plan / workflow` | switchboard verify 闸（verifyCmd 钩子） |

两者共享：Criteria（回归门≥现役基线）、I1–I3、同一份"判定→采纳/回滚"的语义。

## 5. 判定模型（"指标怎么算"的统一口径）
- 基线 = 现役未被扰动的稳态快照（内存/测试/延迟），作为"没变坏"的参照。
- 硬门（回归，必须全过，缺一 reject）：存活；测试通过率 ≥ 基线；关键套件全绿；内存/错误不劣化超阈值。
- 软门（改进，可选加分）：某目标指标确实更好（如内存降、某用例更快），用于"自进化"判"变好"。
- 任何"待测项自身不可达/自报不可信/验证者不可达"都按 reject 处理，并进入 I3 回退。

## 6. 与现有工作的衔接（不重复实现，只对齐）
- 三脑：`ai-base/agent-shell` 的 `brain_manager.go`（启动独立 brain 子进程）、`docs/proposal-subagent-parallel.md`（独立 subagent 验证）。
- 代际：switchboard `coordinator.ts` 的 verify 阶段 + `verifyCmd` 钩子方案；`memory_observe`/`daemon`（代际指标采样）；front-door 遮罩（已挡 HTTP 写，I1 的 HTTP 一侧）。
- 会话写权唯一（I1）当前缺口：DSH 新 gen 启动会 auto-resume persisted 会话 → 与现役并发写全局会话日志 → 已致 `seq gap`。本契约要求补齐"验证通过前 Subject 不获取写权"，其实现有赖 DSH 对 resume/写权的可控性（需单独查：能否禁用/延迟 auto-resume，或会话隔离+显式迁写）。

## 7. 待定 / 请 DSH 审
1. 契约五要素 + 三条不变量是否完备/过简？缺不缺关键不变量（如验证幂等、并发验证、超时语义）？
2. I1（写权唯一）在 DSH 无"禁写"开关时，最可行落地是哪条：会话隔离+显式迁写，还是 DSH launcher 加控制？
3. 回归基线从哪取最稳（现役实时采样 vs 固化基线文件）？首代无基线时怎么办？
4. 验证者独立存续（不随被验证者同死）具体怎么达——coordinator 已是独立进程，足够吗；三脑 sandbox 的独立子进程是否也需同样保证？
5. 有无应纳入契约但没提的失败路径。

## 8. 验收标准（契约实现合格的最低判据）
- 一次"待采纳变更 + 验证失败"的实验后，现役保持可用且可回滚，且不会要求"先停现役再验证"。
- 任一时点，共享写资源只有一个写者；不存在新旧双方同时写同一会话。
- 验证通过前，候选不具备写权；通过后写权显式、串行迁移。
