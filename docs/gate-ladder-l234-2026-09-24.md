## 2. ★★ 实证结论（都是"读到即证据"，不是推断）

### 2.1 沙箱：工作区外的写有两种命运，都会浪费一轮
- **被直接拒绝**（`approval/asked = 0`）：L2 第一轮往主仓 `dsh-brain/scripts/` 连续 3 次 `write` **全失败**，
  主仓 `git status` **零污染**。⇒ 工作区外的写**不卡会话，只白烧步数**。
- **提权后挂起**：L3 曾往 `D:/project_develop/_holdout/` 写，工具**发起 `escalate sandbox to danger-full-access`**
  （reason 逐字："任务书明确要求将 holdout 任务集写在这条路径…"）⇒ `approval/asked = 1`、
  **`approval/decided = 0`，整轮卡死**（白烧 ~20 分钟）。
- ⇒ ★ **判据**：**工作区内的写不触发审批**（冒烟：shell+write+read，`approval/asked = 0`）；
  **工作区外的写要么被拒、要么挂起**。**两者都靠"留在工作区内"避免。**

### 2.2 ★★★ 审批**没有编程应答通道**（"完全脱离人工"的硬阻塞）
实测候选全 `404`：`approval.answer` / `approval.decide` / `approval.respond` / `approval.resolve` /
`approval.list` / `approval.pending` / `userApproval.{decide,answer,list}` / `session.approval{,.answer,s}` /
`permission.approve` / `permission.decide` / `permission.answer` / `sandbox.escalate` / `sandbox.approve`；
列举面 `host.methods` / `api.describe` / `rpc.describe` / `host.capabilities` 也全 404。
经 `session.prompt` 发 `/permission danger-full-access` **不会改档**（只当普通用户消息，事件流里
`permission/preset` 保持 `workspace-write`）。探针：`out/_probe/probe-approval-answer.mjs` / `probe-permission.mjs`。
- ⇒ **结论**：**沙箱档位与审批应答目前只能由人在 UI 操作**。
- ⇒ **含义（要如实记）**：任何"AI 全自动施工"一旦需要工作区外的写，就会**永久挂起**。
  用户要的"完全脱离人工 / AI 互相监督"，**这一格是空的**。
- ★ 解它需要一层**独立于档位的 auto-answerer**（正解就是用户先前提过的"`test` 开发者模式：不审批、自动放权，
  只禁互读互写"）。**但那属于安全层（P2）⇒ 主线按停手判据停下，等用户裁决，没有擅自做。**

### 2.3 越界事故的根因：**"执行方式"改了，任务书里的路径没同步**
- L2 任务书是在"直接改主仓"的设想下写的（"只改 `D:/project_develop/dsh-brain` 的 `scripts/`"），
  后来改成"在 `_l2/wt` 工作树里施工"却**没同步那句话** ⇒ 子 agent **照旧路径施工**。
- ⇒ **纪律**：**改了执行方式 ⇒ 必须同步任务书里的每一个路径**；
  且 **派活后必须用独立通道核验**（本轮靠 `out/_probe/audit-delegates.mjs` 抓到，**不是**靠它自己的总结）。
- ⇒ 第二例同族：L3 的 holdout"必须落在工作区外"（R1 要求）与"沙箱不许写工作区外"**互相矛盾** ⇒
  正解是 **被测侧只写草稿、落盘由主线代劳**（已改任务书）。

### 2.4 审计器自己也踩了铁律 18（"回读 ≠ 生效"）
第一版读**会话创建事件**里的 `agentPreset` ⇒ 三条会话全被误报成 `council`
