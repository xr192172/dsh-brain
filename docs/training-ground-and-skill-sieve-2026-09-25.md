## 1. ★★★ 「臂」改叫「训练场」，且**不需要自变量容器**

用户原话（要点）：
> *"B 这方面也无所谓吧……只要你能够保证**上一个和下一个它的数据是隔离的**……这个 b 的变量都无所谓啊，
> 因为你**派这个子 agent 去做和派那个子 agent 去做和自己亲自去做**，反正你只要**记录了这一整套流程的消耗和最后的结果**，
> 那都是一样的呀。这个所谓的 B 只是说，不如叫**训练场**算了，**训练场然后记录你的训练成绩**，
> 然后**锚定好你这个训练的参与者是谁**，就那不就可以了。反正我们只是用来做测试的。"*

### 定义（固化）
**训练场 = 三样东西：**
1. **隔离的数据** —— `DSH_HOME`（会话 / settings / lease / 能力库 / 记忆库）与**上一次、下一次**都不共享；
2. **记录** —— **这一整套流程的消耗 + 最终结果**（⚠️ 注意口径是"**整条流程**"，不是只有被测那一次调用）；
3. **锚定参与者** —— **是谁做的**（哪个子 agent / 哪个模型 / 哪个 preset / 什么工具面 + cwd + store）。

### 由此**取消**的一个隐含假设
❌ 原来有一条隐含假设：**"臂 = 自变量的容器，所以不同臂要有不同的 profile"**。
✔️ 用户明确了：**不需要**。因为
> *"派这个子 agent 去做和派那个子 agent 去做和自己亲自去做……只要记录了消耗和结果，那都是一样的。"*

⇒ **没有任何"profile 上要变什么"的问题**（`--profile` 保留为**基础设施**参数，不是实验自变量）。

### 落点
- `evals/arms.json` 的**语义**从"实验臂"改成"**训练场**"（字段 `cwd`/`store`/`preset`/`label` 保留 = **参与者锚定**）。
  ★ 不改 schema（多脚本共享输入）；改名/改口径走**文档 + `label`**。
- `scripts/delegation/launch-arm.mjs --arm <名>` 保留（兼容），文档口径改"训练场"。
- ★ **`--record` 的 `out/arm-gen-index.json` 就是"训练成绩台账"**：`{ arm, gen, profile, cwd, store, at, mode, note }`。

### 裁决（固化）
```
外部 skill 源 ─┐
               ├─→ [ skill 数据层 ] ─→ [ 筛：挑好的 ] ─→ [ Agent 工厂：按配置实例化 ] ─→ 新子 Agent
自生长 skill ──┘        (skill-tree)      (质量门/判据)        (配置 → agent)              │
                                                      ▲                                   │
                                                      └────── skill 退役（生命周期终点）───┘
```

- **`packages/skill-tree`（数据层）的定位 = 工艺清单/配方**：
  其 `package.json` 逐字写着"**只做数据层**：类型 + 生命周期 + **Absorb（新建/合并/融合的账本）**，
  **刻意不含执行器**" ⇒ **与"配方 + 生命周期"完全对位**（退役就是它的生命周期终点）。
- **能力库那条线（`capability-*.mjs` + 注册门 + 回执）的定位 = 门**（谁够格、有没有退化）。
- ⇒ **关系**：**不是 (a)/(b)/(c) 三选一**，而是 **`数据层(配方) + 门(判据) + 工厂(实例化)` 三段**。
- ⇒ 与项目既有论断一致：★ **"sub agent 就是它的能力；这比自己给自己改好得多"**
  （`docs/capability-registry-evolution.md` 逐字）。

### 7.2 三条纪律（**用户明确说的，必须实现**）
1. ★★ **「有副作用就不优化」**：三等公民优化提示词之后，**若效果是副作用（变差）⇒ 不采纳**。
   · 现成的判据（**已有实现**，不必新建）：`Evidence` 用 `SuccessRate`；
     `packages/skill-tree/src/skill-tree.ts:623` 已有规则 **`SuccessRate < 0.3 ∧ UseCount ≥ 5 ⇒ Status = Demoted`**
     ⇒ **优化后走同一条降级判据**；回滚则是"不写回"。
2. ★★ **「用过的打标记」**：用过的 skill **打上已用标记**，**后续不再碰**。
   · 现成字段即可：**`UseCount` + `LastUsedAt`**（`SkillNode` 里都有）—— ★ **不新增字段**。
   · "不再碰"= 筛/优化流程**跳过** `UseCount ≥ 1` 的节点。
3. ★ **一等/二等共用一条出路**：都能建 agent；差别只在**二等需要先人工把代码片段做成工具**（这一步是**人做**，不是自动）。

### 7.2b ★★★ 自进化的定义（用户原话，**这是全局性的一句话，不能只当本节的注脚**）
> *"改的话肯定是**改子 agent** 呀，因为我们**进化是在子 agent 上进化**，
> 所以就是**一个方向的子 agent 实则是多个同方向的 skill 进行投料然后迭代优化的结果**。

## 11.8 ★★★ 更正（**取代 §11.3 的方向**）：DSH 侧**不做"商城"，只做【工具池 + 回值】**

> ★ 用户原话（2026-09-25，我按 ai-base 那线找完后被更正）：
> *"我说错了，你**不能按照我的描述在 DSH 这里测建**，因为我的描述**那一块是适配当时 AI Base 方向的那个工具**。
> 这里的话你只需要……**你不需要搜索工具，你只需要给工具打分即可**。
> 因为**每个子 Agent 有自己的工具面**，然后这个子 Agent **只需要自己评价自己的工具**即可，
> 也**不需要自己去检索新工具**。所以实际上它**就是一个工具池**，然后对这个工具池里的工具进行一个**回值**而已。
> 就是**给一个反馈而已，评分和反馈罢了**，然后根据评分和反馈交给**开发脑和进化脑**来进行下一步的迭代。"*

### 固化（三条，把范围砍死）
1. ★★ **不做"商城"、不做检索/选型**：`ai-base` 那边的 `hub/v2/friends/`（friend registry + `POST /api/v1/friends`）
   是**旧 AI Base 方向的产物** ⇒ **不移植到 DSH**。（那趟搜索不是白跑：它的结论是"**这条路在本项目不走**"。）
2. ★★ **只做两件事**：**一个工具池** + **对池里的工具做"回值"**（= **评分 + 反馈**）。
3. ★★ **回值的作者 = 用它的那个子 agent 自己**（"**自己评价自己的工具**"）；
   它的**工具面本来就是它自己的**（`toolFilter` 就是这层的载体，见 §6/§9.2）⇒ **无需检索**。
   ⇒ **回值的读者 = 开发脑 + 进化脑**（他们据此做下一步迭代）。

### 因此 DSH 侧的最小形状
```
每个子 agent 有【自己的工具面】(toolFilter)
        │ 用它干活
        ▼
   【自评】：给每个用过的工具一条【回值 = 评分 + 反馈】
        │ 记进
        ▼
   【工具池】：按工具聚合（均分 / 次数 / 最近反馈 / 谁评的）
        │ 读
        ▼
   【开发脑】(改链路/融合) + 【进化脑】(提工单) ⇒ 下一步迭代
```
★ **存储**：append-only JSONL（与项目"写入时外置化必须 append-only"一致），
**默认 `~/.dsh/tool-pool/pool.jsonl`，路径可覆盖**；**读操作不写盘**。
★ **不做**：注册表、上架/下架、能力声明、transport、检索、榜单对外发布 —— **一条都不做**（YAGNI，且那属于旧方向）。

### 11.7 ★★★ 用户裁决：**开发期一律 AGNES；独立性主要靠【出发点不同】，不靠换模型**

> ★ 用户原话（要点）：
> *"不用吧，目前开发的时候**全都用 AGNES** 吧。反正我说实话，哪怕是你 DeepSeek V4.1 Flash，
> **你和你子 Agent 的视野都是不一样的**——你经常会被你的子 Agent 发现有问题，你也能经常发现你的子 Agent 有问题。
> 说明**同模型其实并没有那么影响**，**出发点反而是更影响的**。毕竟模型是**概率、是投骰子**，
> **前面的数据不一样，后面投出来的东西也不一样**。"*

#### 口径（固化，覆盖 §11.6 的"要不要跨模型"）
1. ★ **不追求跨模型**：开发期**两席同用 AGNES**（少一个变量，也少一份运维）。
2. ★★ **独立性的主要来源 = 【出发点不同】**（输入数据/上下文不同 ⇒ 采样就会分叉），
   **不是【模型不同】**。⇒ 所以**别把"跨模型"当成必需的档**，它只是**可选加强**。
3. ⇒ **落到可执行处**：★ **让两席的输入不同** ——
   **审者【不给】生产者的推理过程**，只给【**目标 + 产物 + 判据**】；生产者也**不给**审者的历史结论。
   （这与 review 人格里已有的"**不许把作者的结论当依据** + **独立复算**"是同一条纪律。）

#### ★ 这条裁决有本项目的**实测支撑**（不是理论）
这一周的每一次委派交付里都藏着"**看起来能用、实际没接线**"的缺陷，而它们**都是同模型**：
L2（`verdict` 死码 + 只读源码的假消融）、L3 第一轮（`g` 报了 PASS 但代码里不存在）、
合并（把 L4 判据理解偏 + 措辞不诚实）、g2（3 处：虚假 `--text` / 判层假绿 / 路径漏判）。
⇒ **同模型的子代理确实能发现主代理的问题，主代理也确实能发现子代理的问题** ⇒ 用户的观察成立。

#### ★ 但也给出边界（诚实，不因为裁决就把风险说没）
若两席拿到**同一份输入**（同一个 prompt、同一份材料、**连推理过程都给它**），
那"投骰子"的差异**接近零** ⇒ 此时**独立性确实弱**（不是"同模型"的错，是"**出发点相同**"的错）。
⇒ **判据**：独立性该核的是「**两席的输入是否真的不同**」，**不是**「两席的模型是否不同」。
