# dsh-brain · 思路规格（实现无关）

> 本文档把 agent-shell（Go，位于 `d:\project_develop\ai-base\agent-shell`）里值得保留的**工程理念/不变量**抽成实现无关规格，作为在 DSH（Cordis 插件体系）上重新干净实现——而非迁移代码——的唯一依据。所有"怎么跑 DSH"的实现细节一律不进入本文档。
> 语言：中文。每节：意图 / 不变量 / 边界 / 验收标准。

## 1. 传送带上下文（conveyor-context）—— 旗舰

**意图**：让 LLM 上下文在"信息密度最大化"与"前缀稳定最大化（复用 KV-cache）"之间达到最优。动态内容与稳定内容物理分离，折叠采用非破坏方式，保证可回滚。

**不变量**
- **I1.1 稳定前缀优先**：常驻层（系统知识）+ 摘要目录层 + 段落队列层的文本，在任务进程中尽量不改变 head；所有每步都有可能变化的内容（工具结果、当前轮、检索注入）只能追加在尾部，禁止改写前缀。前缀一旦变化，其后 KV-cache 全部失效。
- **I1.2 分层固定顺序**：上下文物理顺序恒为 `L0系统知识 → SummaryZone摘要目录 → SectionQueue段落队列 → CurrentRound当前轮 → DynamicInjection动态注入`。任何实现都要守住这个 order 并让每层可独立、可选地关闭。
- **I1.3 非破坏折叠**：某段被折叠时，其完整原文必须冷存（可回滚/可复核），上下文中只保留摘要；不能原地覆写覆盖原文。
- **I1.4 摘要目录只追加、低频斩断**：目录是追加式、低频批量更新（避免 head 频繁变化）；超限时整段斩断，且斩断跟随折叠窗口期，最大化缓存重叠。
- **I1.5 动态注入可摘除**：动态段凡是"对上一步之后的决策无普适必要"的内容，本轮结束即摘除；需要跨轮保留的关键事实，用显式标记（如 `[[KEEP]]` / `<keep>` 容器）升格进摘要层，其余原始内容不留。
- **I1.6 折叠阈值驱动**：折叠不是每次摘要都做，而是段数/token 达到阈值，或容量超限时统一触发；token 超限时应先"提示尽快摘要"而非即时强断。

**边界**：本规格只约束"上下文如何切分/折叠/注入"，不约束推理循环本身；L0 里具体系统知识的措辞、模型能力描述，属于内容不属于结构。

**验收标准**
- 长会话中，前缀（L0+摘要目录+段队列）的 token 串在多轮间保持一致，仅尾部增长；
- 触发折叠后，可展开回滚到折叠前全文；
- 工具返回的大块原始数据不会滞留尾部超过本轮，只保留决策痕迹 + 关键事实；
- 一个 40+ 轮的长任务不因上下文爆炸而退化/卡死。

## 2. 三脑架构（three-brain）

**意图**：把"行动(在线)"、"研究与审计(离线)"、"隔离验证(沙盒)"三个职责分离到三个可热切换的脑，安全地让离线侧进化后再切换上线。

**不变量**
- **I2.1 职责分离**：left=直接服务执行；right=多轮检索/复盘/决策支撑；sandbox=隔离试错、验证后才回灌。
- **I2.2 可装配/可卸载/可回滚**：每个脑按"组件"注册（BrainRegistry），可热插拔；切换不崩运行状态，且可回退到上一稳定脑。
- **I2.3 冷热隔离**：sandbox 的改动不直接上线，须验证通过才替换；shadow/影子模式对比后再热切换。

**边界**：脑之间的具体协议（消息/数据）由实现定；本规格只约束"分开 + 可切换 + 验证后回灌"。

**验收**：可动态新增一个脑、热切换、并在其失败时回滚到原脑而不中断会话。

## 3. 工具自进化（tool-evolution）

**意图**：工具的"正确性"不靠静态证明，而靠"适应度 = 成功率 + token/时间消耗"；失败即变异；好的沉淀、坏的淘汰。

**不变量**
- **I3.1 打分来源**：LLM 每次用工具后对工具打分 + 评分依据，积累为可靠性档案（不是靠外部静态评测）。
- **I3.2 适应度指标**：适应度以可量化信号为准：成功率、平均 token/耗时、失败模式与回退路径。
- **I3.3 失败即变异**：工具失败不推倒重来，拆其内部失败步骤，局部修改新版本，先在隔离区验证再替换；旧版保留可回退。
- **I3.4 描述锚定实现**：重写工具描述必须基于 Schema 骨架 + 行为测试对 + 结构化变更日志（"描述是编译产物，不是总结产物"），不得从聊天历史/早期比喻摘抄，防止语义漂移。

**边界**：工具生态的合并/吞噬/GC 属于实现层；本规格约束"打分信号 + 变异闭环 + 描述防漂移"三条。

**验收**：同一类任务二次出现时 token 显著下降或成功率上升；描述重写后误路由率不上升。

## 4. 护栏与资源治理（guardrail）

**意图**：对危险操作与资源消耗设确定性边界，宁可拒绝也不让 LLM 副作用失控。

**不变量**
- **I4.1 分级审批**：操作按危险度分级，触发相应的审批策略（不全是放行/拒绝，支持中间态）。
- **I4.2 资源阈值**：上下文、单轮消息、草稿、工具执行时间/重试、并发达标时统一处理（拒绝/降级/告警），不静默超限。
- **I4.3 一致错误格式**：一切错误响应统一 `ok / error.code / error.message / error.detail`。

**边界**：具体阈值数值属配置；本规格约束"分级 + 阈值治理 + 一致错误"。

**验收**：危险操作被正确挡在审批；超阈值时行为符合既定策略而非崩溃。

## 5. LLM 路由与用量账本（llm-router）

**意图**：所有 LLM 调用统一走路由，按用途分流到配置的池子，并记录每一次消耗（成本可用）。

**不变量**
- **I5.1 统一路由**：任何 LLM 调用不得直连裸客户端，必须走 Router（按 TaskType/用途路由到池）。
- **I5.2 全量记帐**：每次调用一条账目（task/池/model/token/耗时/成本），落盘可审计。
- **I5.3 多 key 轮换**：池支持多 key，按"缓存感知"策略轮换（有缓存命中时同 key 退避优先，无缓存或认证失效才切换）。

**边界**：具体池定义/model 名属配置。

**验收**：每次调用在账本可见；多 key 在限流时能合理轮换而非全部失败。
