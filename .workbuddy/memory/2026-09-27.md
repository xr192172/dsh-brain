# 四、R4「管理面不许阻塞事件循环」（`6be53af`）

## 4.1 事故形状（铁律 34 已记账，这轮修掉）

`mgmt.ts` 的 `execAction` 用 `spawnSync` ⇒ **同步阻塞事件循环**；
而**控制面与前门是同一个进程**（实测 pid 相同：19524 / 18772）
⇒ 管理面一跑长命令，**前门的代理转发一起被拖住**。
实测病征：`n=90 ok=83 err=7`，`p95=0.66s` 但 **`max=8.23s`**（长尾全是这一段阻塞）。

## 4.2 修法：`execActionAsync`（**安全属性一个字不动**）

仍 `argvFor()`（数组 ⇒ 无注入面）+ 仍 `childEnv()`（剔臂身份）+ 仍**不经 shell**（显式 `shell:false`）
+ 仍有超时（900s，且**超时留可读证据**，比同步版的静默 kill 更好）+ 返回**同形** `{code,stdout,stderr}`。
`main.ts` 两处调用点都换成 `await mgmt.execActionAsync(...)`（`experiment` 分支原本就异步，也一并换掉）。

## 4.3 门：`scripts/switchboard/test-mgmt-nonblocking.mjs`（15 passed / 0 failed）

**行为判据**（不是会假绿的文本判据）：真起忙 1200ms 的子进程，量**等待期间事件循环 drift**。
- 同步 **1228.9ms**（病征复现）⇒ 异步 **12.2ms**（修复达成）⇒ **消融 1234.1ms**（非同义反复）
- 另有：B 组用**真 action**、C 组同步/异步**对拍逐字相同**、D 组安全四条、E 组接线（含"不许有 execAction 残留"）。

★★★ **本门自己踩过一次假红（如实记录）**：第一版 `done()` 在 `spawnSync` **返回之后**立刻收口
⇒ 心跳在同一瞬间被清掉、**从没观察到阻塞** ⇒ 同步版读数 **0.0ms**（"同步阻塞 1.2s"却测出 0ms，物理上不可能）。
⇒ 正是**铁律 15**（判据读不到差别 ≠ 没有差别）。修法：**递归 setTimeout** 量"排队延迟"
+ 测量窗口**跨完整时间跨度**（跑完再等 3 个窗口让积压心跳补跑）。

## 4.4 运行时实证（**两条，强弱分明 —— 如实标注**）

**① 打现役（`out/_r4-runtime-verify.mjs`，4/0）**：管理面跑 161ms 期间打前门 40 次 ⇒ `max=8ms`（基线 12ms）无差别。
★ **但这条判据弱**：现役所有 mgmt action 只有 **50~60ms**（brief 61 / verdict 58 / tasks 52）
⇒ **live 侧造不出长负载窗口**（铁律 24：别用最小端样本证明关于大端的命题）。

**② 受控对照（`out/_r4-concurrent-ab.mjs`，6/0）—— 这条才是强证据**：
同进程起**真 HTTP 服务**（复刻"控制面+前门同进程"），用**真实导出**跑忙 1500ms 的子进程：

| 跑法 | 期间服务处理请求数 | max 延迟 |

# 五、关于「秘书席」（用户提议）—— 我的分析

用户问：*"要不要增加一个秘书席…记录整理归纳整个对话，专职和其他 Agent / 其他席位沟通，
把整个 agent 系统构建成公司系统，每个部分专门处理每个部分的问题，有问题就转交给对应部门。是不是更好？"*

## 5.1 先摆现状：**机制层今天不支持"席位之间对等沟通"**

核过上游源码（`node_modules/@deepseek-ai/dsh-subagent/lib/index.js`）：
`report` 工具解析的是 **"the reporting child's live direct parent"**（`direct parent is not live;
report was not delivered` / `PARENT_UNAVAILABLE`）。
⇒ **通信只在【父 ↔ 直接子】之间**，方向是**向上汇报**。
**没有同层对等通道**（两个兄弟席位不能直接互相发消息）。

已有能力（`docs/subagent-nesting-and-toolfilter.md` 实测）：
- 子代**能再委派**（`maxDepth` 默认 3，第 4 层被运行时拒）；
- `toolFilter` 能裁专项工具面（103 → 3 / 98 / 1，任意可裁）；
- 子代**继承父 preset** ⇒ 有委派行就能继续下探。

⇒ **"公司"这个形状里，"部门"（= 席位）确实存在，"转交"也能做 —— 但只能【沿树】做（我→你→它），
不能【平级转交】（你直接把活递给隔壁部门）。**

## 5.2 所以"秘书席"有两种落法，代价差很多

**落法 A（机制内，代价小）：秘书 = 父会话 / 一个编排位。**
它天然就在"所有沟通的中心"（所有子代都是它派出去的、所有 report 都回到它这里）
⇒ 你说的"记录整理归纳整个对话 + 有问题转交给对应部门"**正是父会话已经在做的事**。
⇒ **不需要新席位**；需要的是把"转交"变成**显式、可审计**的动作（把判断从 prompt 挪进机制）。

**落法 B（真造一个平级秘书席位，代价大）：**
今天做不到"平级转交"⇒ 要么给它**委派权**（它当中间层：秘书 → 各部门），
要么**改上游**加对等通道（违背铁律 10"不追上游"）。
⇒ 前者可行但要小心：**多一层就多一次信息损耗**（用户级记忆 §4 正是这条教训：
"你给 WorkBuddy 子 Agent 放一遍、子 Agent 又转交一遍，中间信息会损耗，还会重复做同一个动作"）。

## 5.3 我的判断（诚实版）

- **"公司隐喻"本身是好比喻**，而且**已经部分实现了**：architect（架构）/ dev（施工）/ review（评审）就是三个部门，
  且 review 与 dev **出发点不同**（用户 2026-09-25 裁决的"独立性看出发点是否不同"）。
- **但"秘书席"现在加，收益不明确、风险明确**：
  · 收益："整理归纳"是**上下文压缩**问题 —— 我们**已有** `conveyor-context`（压缩后端契约，铁律 8）在做这件事；
  · 风险：多一层转发 ⇒ **信息损耗 + 重复动作**（用户自己踩过），且"转交给对应部门"这句话里
    **"对应"是个判断** —— 判断落在哪一层，就是**又一处可以假绿的地方**。
- **★ 真正缺的不是"秘书"，是两件更硬的事**：
  ① **席位之间没有对等通道** ⇒ 若要做"部门间协作"，得先**明确**走"树"还是"改建机制"（这是设计岔路，需要你定）；
  ② **"转交"的判断必须可审计**（否则就是"我看了一眼觉得该给它"⇒ 无法判对错）。
- ⇒ **建议顺序**：先把**现役唯一在跑的 architect 一席**扩成真正的"部门"（dev/review 上线，
  方法已记在 §2.8），让"多部门"先**真的存在**；**再**讨论要不要一个专职协调位。
  否则是给一个**只有一个人**的公司设"秘书岗"。

★ 若你要推进，我建议下一个可做的具体件是：**给父会话的"转交"落一个显式、可审计的记录**
（谁把什么活转给了哪个席位、依据是什么）—— 这是"秘书"里**唯一不能靠 prompt 解决**的那部分。
