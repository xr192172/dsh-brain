## 二、★★★ O8 修复：席位「只读」从 persona 里的话变成机制层的约束

> 用户："可以。值得做我觉得都无所谓……这个价值倾向也按照你自己来。开始吧。"
> ⇒ 我选 O8 优先，理由：**它影响后面所有席位工作的可信度** —— 如果被审对象能被随便改，"审计"就不成立。

### 2.1 事故（现场证据）

`architect` 席的 persona 白纸黑字：「默认只读。…不要修改任何文件」「你【只做设计与判断】，不写实现代码」。
**但它真的往仓库里写了一个脚本**：`scripts/seats/_analyze-personas.mjs`
（已留证 `out/seat-wrote-this-_analyze-personas.mjs`，并在 `46a53b6` 从仓库移除）。

⇒ **写在 persona 里的约束不是约束。**

### 2.2 根因（核过上游源码，不是推的）

`node_modules/@deepseek-ai/dsh-subagent/lib/index.js:570-585` `applyChildComposition`：
子代理权限范围在**委派边界固定**：
- `sandboxMode` = `captureDelegatedPolicyOverrides(parent)` ⇒ **父会话的显式沙箱覆盖**
  —— provider **改不了**（也不该有入口：那会让子代理绕过父的沙箱）
- `approvalPolicy` 一律钉 `'never'` ⇒ 席位**不可能自己提权**
- **但** `composition.toolFilter` 会经 **`childCtx.tools.restrict(toolFilter)`** 应用
  ⇒ **工具面是 provider 能改的那一层**

★ 附带结论：`scripts/delegation/dsh-delegate.mjs` 注释里的既有结论
「**权限档位没有 RPC 通道**（12 个候选名全 404）」与此**互相印证** ——
改沙箱档位这条路本来就不通。

### 2.3 复现（离线、可复算）

`out/_o8-repro.mjs`：
- 父会话（council preset）工具面 **102 个**，其中**写类 16 个**
  （`write`/`edit`/`pwsh`/`tool_apply`/`mcp__design-canvas__edit_code`…）
- 席位源码里**没有任何有效 restrict**（只在注释里说"若某席位要限制，可补 toolFilter"）
- ⇒ 席位继承全部写工具 ⇒ **能写**，与 persona 直接矛盾

### 2.4 修法：改**工具面**，不改沙箱（沙箱是上游的地盘）

```
SEAT_TOOL_SCOPE = {
  architect: "readonly",   // persona: "默认只读…不写实现代码"
  review:    "readonly",   // persona: "你不写实现、不改文件（默认只读）"
  dev:       "full",       // persona: "你只做施工" ⇒ 必须能写（阳性对照）
}
未知席位 ⇒ readonly（fail-closed）
```

只读名单 = **7 个**：`read` / `glob` / `grep` / `read_image` / `web_search` / `ask_user_question` / `todo_write`

★★ **为什么用 `allow`（白名单）而不是 `deny`（黑名单）**：
`dsh-tools/lib/index.js:2531` 的 `admits()` 语义 = 「allow 表里没有 ⇒ 拒」。
- 黑名单是 **fail-open**：design-canvas 哪天加个 `edit_xxx`，席位立刻又能写了
- 白名单是 **fail-closed**：新工具**默认不在名单里** ⇒ 默认关
只读集合小而稳 ⇒ 白名单天然合适。

★ 白名单里**故意保留** `ask_user_question`：席位遇歧义时的**唯一**正确出口是"问"，不是"自己猜着改"。
★ **故意排除** `subagent`/`subagent_fork`/`workflow`/`ralph`：席位**不再向下委派** ——
否则"审阅席又生了一层子代理"，独立性彻底不可核对。
