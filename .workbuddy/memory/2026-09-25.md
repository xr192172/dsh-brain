## ★ 用户提问："这个 Auto 是什么意思？"

回答要点（对话里已展开）：**auto-answerer** = 审批请求的**自动应答者**。
- DSH 的沙箱有两档旋钮：**沙箱档位**（read-only / workspace-write / danger-full-access）与**审批策略**（ask）。
- 工具要越过沙箱时，harness 写一条 `approval/asked`，然后问**应答者**；本机**唯一的应答者是浏览器 UI**（人去点）。
- 实测：**17 个候选 RPC 全 404** ⇒ **没有编程应答通道**；而提权请求**挂起后永远等不到 `approval/decided`**
  ⇒ **任何 AI 自动施工一旦需要工作区外的写，就永久卡死**（L3 已实测白烧 20 分钟）。
- auto-answerer 就是**补上那个"应答者"位**：来了请求，按**规则**自动 allow/deny，不再等人点。
  这正是用户先前说的"`test` 开发者模式：换代不审批自动走 + 沙箱自动给权限，只禁互读互写"的落地形态。

## ★★★ §9：能力源不限于 skill（MCP 同路）+ **元工具 vs 链路工具**（commit `aa5485a`）

用户问："**外置 MCP 我们将其做成工具，然后绑定成 Skill，其实是不是也是一样的呢，你说。**"

流水线同一条：**源 → ToolDef → 绑进 skill → 升格成 agent**，只是源形态不同。
★★ **必然结论**：纯 MCP 来源**缺"指导"（`Principle`）那一格** ⇒ 按 §7 判据**是二等**（要我们补一句
"什么时候该用它、怎么用"）。说得通：**MCP 是"能做什么"，指导是"什么时候该做"**。

### ★★★ 用户点出的设计原则（之前一直没落到文档里）
**元工具 vs 链路工具**（本机实测对上）：
- **元工具** = `design-canvas-bridge` 注册的 **55 个** `mcp__design-canvas__*` ⇒ **零件**；
  让 agent 自己组织 = **把编排负担丢给模型**，而且**每次都要重新组织**（不稳定、耗 token）。
- **链路工具** = 同文件里自写的 **`safe_rename`**（`:558-671`，深度注入 `kernelDir`）+ `move_symbol`（`:673`）
  ⇒ ★ **一个工具 = 一整条链路，不需要 agent 自己去组织**。
⇒ **原则：能力的粒度是【链路工具】，不是【元工具】**；"把 MCP 绑成 skill/agent"时**绑的粒度应是链路工具**。
⇒ **目标形态（用户原话）**：*"做成一个像 SAFE RENAME 那样的、一个工具包含整个链路、不需要 Agent 自己去组织的工具"*。

### ★ 由此暴露的判据缺口（如实记，**口径等用户给**）
§7 判据**只数"有没有工具"**，**数不出"元工具还是链路工具"** ⇒
