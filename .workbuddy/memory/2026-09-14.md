## 2026-09-14 01:00 —— BOM 收口 + 两个桌宠彻底移除

### BOM 是什么情况

**根因**：DSH 启动链上有多处 `JSON.parse(readFileSync(pkgJson, "utf8"))`
（`dsh-app-boot`：app anchor(:412) / 依赖遍历 manifest(:430) / profile manifest(:453) / bundle manifest(:551)）。
UTF-8 BOM(`EF BB BF`) 让 JSON.parse 在首字节抛 `SyntaxError: Unexpected token '\uFEFF'` → **整个 gen 起不来**
（实测 gen-3085 / gen-3091 的 boot.log 里就是这条栈，指向 `readProfileManifest:453`）。

**用户记忆里那件事** = `scripts/patch-profile-deps.mjs:4` 的注释：「确保无 UTF-8 BOM
（DSH readProfileManifest JSON.parse 会因 BOM 崩溃）」—— 历史某次 profile manifest 带了 BOM 导致 DSH 起不来。

**BOM 的来源（判据关键）**：Windows 侧写入方 —— **PowerShell 5.1 的 `Set-Content -Encoding UTF8`
一定会加 BOM**、记事本"UTF-8"也会。所以只要工具链里有 PS 写文件，就必须常扫，不能靠记性。
（本会话我自己也大量用 `Set-Content -Encoding UTF8` 写 `out/*.txt` —— 那些不在配置路径，无害；
但只要目标变成 json/源码就立刻爆。）

**存量**：全项目扫描只有 1 个 → `packages/key-pool-proxy/src/index.ts`（带 BOM + CRLF）。
它是**潜在**的（入口是 `lib/index.js`，tsc 已把 BOM 剥掉，所以此前没爆）。

**修复（四件）**：
1. 清存量 BOM：`scripts/check-bom.mjs --fix` 已剥除 `key-pool-proxy/src/index.ts`
2. **统一防护**：`scripts/patch-app-boot-bom.mjs`（幂等，4/4 命中）—— 给 `dsh-app-boot` 加
   `parseJsonNoBom(raw)` / `readJsonManifest(file)`，把 4 处裸 `JSON.parse(readFileSync(...))` 全部换掉；
   **剩余裸调用 0 处**
3. **守卫脚本**：`scripts/check-bom.mjs`（默认扫描 159~161 个文件、发现即 exit 1；`--fix` 就地剥除 3 字节、不碰 CRLF）
4. 挂 `postinstall`；加 `npm run check:bom`

### 换代该不该留 —— 结论：**不删，但收窄适用面**

用户提出「蓝绿脑使用频率低、甚至没必要、重启应该同效」。查证后：

**① "DSH 有自动更新机制"比想象窄**：host 侧**没有**热更新。
`@deepseek-ai/cordis-plugin-hmr`（chokidar+picomatch，`root:['.']`）**被 `dsh-web-app/cordis.patch.yml:21-23`
置 `disabled: true`**，理由注释：「TODO: Re-enable shared HMR for Web after its reload lifecycle is tested.」
常驻的 `client-hmr` 只管**浏览器侧 client bundle**，且 idle until `pnpm run dev:web`。

**② 换代只有一条触发路径**（`main.ts:123`）：`cmd === 'handover' || cmd === 'apply'` ——
**只有 admin HTTP 命令，无 watcher、无自动检测**。`scripts/evolve.mjs` 是唯一自动化门面。

**③ 换代 ≠ 重启的替代品，换代 = 重启 + 三道保险**：

| 维度 | 重启 | 换代 |
|---|---|---|
| 进行中的 turn | **被杀死**（前门就是 switchboard 进程；gen 非 detached、随进程树走） | **等它收尾**（`coordinator.ts:167-176` defer：`prepareSwitch(deferMs)` 注入挂起提示 + 等 `turn/end` 或 grace） |
| 失败退路 | **无**（起不来=彻底没服务） | **`rollbackFlip`**（`:482`）旧代无损继续 |
| 流量前校验 | 无 | probe(:292) + verify gate(:319) + 稳定期探测(:332) + 新增启动健康检查 |
| 停机窗口 | 有 | 无（flip 原子换向，verify 后才 retire） |

**④ 但用户"觉得换代没用"是有道理的** —— 因为 09-13/14 修掉的三 个 P0 **全部是换代引入/暴露的**：
端口击穿（换代代价）、插件树部分加载失败（换代把会话搬到坏实例）、BOM 崩 gen（新代起不来）。
→ **"换代不好用"主要来自"换代的保险没装好"**；今天三件事（端口固定 / 启动健康检查 / 单一来源化）
才是第一次把保险装上。反直觉推论：**这两个 P0 能藏一天以上，恰恰因为换代不常发生** ——
频率低不是"没用"的证据，是"发现能力不足"的证据。

**⑤ 定案：三级替换策略**（判据只有一句：**这次改动坏了会不会被立刻发现？**）

| 档 | 适用 | 手段 | 中断 | 回滚 |
|---|---|---|---|---|
| L1 热重载 | 反复调 UI/client bundle | `pnpm run dev:web` + `client-hmr` | 无 | — |

## 2026-09-14 01:30 —— 快速换代路径 + 「单前脑 + 委派式多脑」定调

### A. 快速换代已落地（switchboard `b1789320073472`，lib 已翻转）

用户提「换代频率会很低，重启应该同效」。实测换代最贵的一环是 **`deferMs` 默认 20s**（等当前轮收尾），
外加 `verifyStableMs` 默认 2s。所以加了 **fast 模式**：

- `?cmd=restart` 或 `?cmd=handover&fast=1` → `coord.handover(..., fast=true)`
- **跳过三样耗时的**：① defer（默认 20s）② verify-gate（实验脑白名单脚本）③ flip 后的稳定观察窗（2s）
- **保留三样几乎不花时间、却决定成败的**：probe + **启动健康检查**（拦"环境漂移"）+ **rollbackFlip**（旧代还在，回滚免费）
- `state.jsonl` 会记 `fast 模式：...` 与 `已快速切换 → gen-xxxx`，可审计
- 代码落点：`coordinator.ts`（`handover()` 加第 5 个参数 `fast`，三处 `!fast` 守卫）、
  `main.ts:123`（`cmd === 'restart'` 或 `&fast=1`）

**重要结论**：`fast` **不等于"重启"** —— 它是"快速换代"，仍带回滚。
用户的"重启"直觉要的是"便宜"，但**回滚是免费的**（旧代本来就还在），所以没有理由关掉它。
真正该关的只有"等当前轮"和"跑验证脚本"。

### B. 「单前脑 + 委派式多脑」—— 用户新提案（**方向对，且比预期省事**）

提案：不要三栏平铺三个脑；**最上层只跑一个脑**，把任务委派给下层三个脑当子代理；
用户只看顶层，聊天框显示委派了谁、点开可展开；自进化在更下一层。

**关键发现：这套机制 DSH 已经实现过两遍，前端组件也已存在。**

| 层 | 现成物 | 证据 |
|---|---|---|
| 工具层 | Code Mode sub-dispatch | `dsh-tools/lib/types/code-mode.js:1-6`「each sub-dispatch is logged for reconstruction, **while only the outer curated result enters model history**」 |
| Agent 层 | **`dsh-tool-subagent`** | **`SubagentProvider` 可插拔接口**（`capabilities.depthLimit` / `inheritsParentContext` / `prepareContinuable`）+ `toolFilter{allow,deny}` + `agentOptions{provider,model,maxTokens}` + `persona` + `maxDepth`；契约原文「**You receive its result, not its intermediate steps**」；`backgroundMode: one-shot\|continuable`（durable subagent id + `send_message` 续轮） |
| 前端 | **`dsh-client-ui-subagent`** | 「Subagent conversation catalog, continuation routing UI, and '@' reference source」——实为**子代理谱系树**：`CatalogRows` 递归、"recurse only through explicitly expanded rows"、`aria-expanded`/`treeitem`/`aria-level` |

**前端已有**：委派树展开/收起（`branch.expand`/`branch.collapse`）、状态（`activity.running/inactive`）、
模式（`mode.oneShot/continuable`）、**耗时**（`activityDuration`）、**token 用量含缓存细分**
（`inputTokens+outputTokens+cacheReadTokens+cacheWriteTokens`）、**诊断位**（`diagnostic.corrupt/unsupported/unavailable`）。
**前端没有**：子脑**内部过程** —— 它展开的是"下级子代理"（层级），数据模型是
`catalog/catalogs`(按 session id) + `summaries` + `activity` + `usage`，**只读摘要与用量**。

→ **唯一确定的净新增工程量 = 一层委派日志**（把子脑过程落成可展开结构）。

**★ 对用户核心问题的回答：顶层脑怎么更新 —— 还是蓝绿，而且这是换代唯一不可替代的位置。**
- 不能重启（顶层持有与用户的**连续会话**）
- 不能"下次任务生效"（它一直活在同一个会话里）
- 失败最难发现（顶层做判断与路由，坏了表现为"一切正常但一直在做错事"）
- **反过来：下层脑不需要换代** —— 「委派」这个动作本身就是一次天然蓝绿：**下一次委派用新版本，正在跑的不受影响**。
  → 提案的最大价值（可能超过 UX）：**把换代从"三处都要"压缩到"只有顶层需要"**。

**六个必须提前想清楚的失败模式**（详见文档）：
① 顶层上下文被委派记录吃掉 → 委派档案**写入时外置化**（顶层只留引用）
② 顶层单点 → 由换代覆盖
③ 展开详情的数据来源 → 需自建委派日志（见上）
④ 路由判据不能靠 prompt 自由发挥 → 必须是可执行判据（接判据阶梯）
⑤ ★ **子脑自进化后顶层认知过期** —— 最易忽略。今天的"工具少 25 个且无人发现"就是预演；
   在委派架构下会表现成"按过期认知把任务派给已不会做的脑"。→ **能力清单做成契约**（`capabilities` + `acceptance`）
⑥ "看起来只有一个脑"会掩盖委派失败 → 委派卡片必须显示健康状态（`diagnostic.*` 是现成挂载点）

**Hub 定位变化**：不消失，从「用户前端」降级为「**控制面**」（brain registry + 委派路由 + 生命周期）。
与 switchboard 分工明确：**switchboard 管"代际"，Hub 管"身份与能力"**。

**新文档**：`docs/single-front-brain-delegation.md`。

### A. 用户新提案：上层对子代理的返回结果评分 + 提修改意见

**比现状好一级**：`tool-evolution` 现在是 **LLM 自评分**（被优化者自评，最坏）；
改成"顶层/消费者评"至少是不同上下文（判据独立性上了一级）。

**但仍不够，三个原因**：
① 顶层也是 LLM，**也会被讨好** —— 子代理靠"写得更漂亮/更自信/更迎合"就能提分，
   这是 reward hacking 的**软形式：操纵判据持有者的感知**；
② 顶层**不知道"本来应该是什么"** —— 而它正是给出（可能模糊的）委派的那一方，无法区分"做对了"和"看起来很对"；
③ 满意度是**连续量**，能力门是**布尔的** → 回到被否决的"加权聚合"。

**正确设计 = 信号与判据分离**：

| | 提供者 | 性质 | 频率/成本 | 作用 |
|---|---|---|---|---|
| **信号** | 顶层满意度 **+ 具体理由** | 连续、软 | **高频、零成本**（顶层本来就要看结果） | 决定**何时值得花昂贵的判据** |
| **判据** | 可执行 `acceptance` + 隐藏 holdout | 布尔、硬 | **低频、昂贵** | 决定**是否采纳** |

> **信号决定何时花判据；判据决定是否采纳。**

**硬约束（决定它会不会退化成讨好）**：
**评分必须附带"不满意的具体理由 + 可复现的反例"。没有理由的评分应被丢弃，而不是被采纳。**
否则系统学到的是"怎么让上层满意"，不是"怎么把事做好"。

**"修改意见"的正确形态** = 候选提案 `{path, change, expectedGain, falsifier}` → 进注册门；
**满意度本身不进闸**。

**对工具商店的直接推论**：现在它只有"自评分"一种东西，既不是信号也不是判据 →
改为**消费者满意度作信号（触发）+ 可执行用例作判据（采纳）**。

## 2026-09-14 01:55 —— 用户反驳"被讨好"：盲评 vs 行为信号（§5.5 大幅扩写）

用户两个反驳：
① **"你只要不告诉它在被受测，就不会有故意讨好"**（盲评）
② **"每个子 agent 里都装工具商店 → 不再是一个 agent 给它打分，而是一堆 agent 在真实使用中选用自己需要的工具并打分；
   sub agent 同理：正常使用它就行，不需要专门抱着测试心态，多开会话/多放几轮任务，总有用到它的时候再评分"**

### 我纠正了自己上一轮的定位错误

上一轮我把"讨好"归因于"顶层也是 LLM，会被操纵感知"——**原因找错了位置**。
正确表述：**讨好的根源不是"知道在考试"，而是"收益函数由判据持有者的主观反应定义"。**

**盲评能解决的**：显式讨好（加免责声明/拉长解释/堆自信措辞/迎合口味）、应试特化（针对考核轮优化）。
**盲评解决不了的**：
1. 隐藏的是"**哪一次**是考试"，不是"评分这件事存在"；激励来自后者（只要它能推出"产出会被评价"就一直在）
2. **讨好往往不是作弊，而是"正确地做被要求的事"** —— 任何 assistant 的本能目标就是"让用户满意"，
   于是"让上层满意"与"把事做好"在目标函数层面重合（客服 agent 学会动不动退款就是这类）
3. ★ **无法回避的张力**：我们要顶层给修改意见并迭代 → "迭代"本身就在告诉下层"产出会被评价"；
   同理"委派详情可展开" → **它知道可被查看 ≈ 知道会被评价**。
   **⇒ 要迭代就必然暴露"有评价"。信息隐藏路线与迭代需求直接冲突。**

⇒ 盲评值得做（提高信号纯度），但**不能把信号升级成判据**。解药始终是"让判据不经过任何人的主观反应"。

### ★ 用户的第二点更强：把"评测"变成"使用的副产品"

**信号三层强度**：

| 强度 | 信号 | 性质 | 可否伪造 |
|---|---|---|---|
| **最强** | **选用 / 复用 / 弃用**（行为） | **costly signal**（选错要付代价） | ❌ 不可伪造 |
| 中 | 满意度 + **具体理由 + 可复现反例** | 声明 + 证据 | ⚠️ 有信息量 |
| 最弱 | 裸满意度评分 | **cheap talk** | ✅ 可敷衍 |

> **"打 8 分"是声明；"下次还用不用它"是承诺。**
> 一个 agent 能给自己打 10 分，也能让上层给它 9 分 —— **但它没法强迫别的 agent 下次还用它。**

⇒ **工具商店的真正改造不是"换个人打分"，而是：把打分降级（辅助证据），把行为信号升级（主信号）。**
用户更早说的"工具域要有个**顺不顺手**的指标"——**那句话本来指的就是行为信号**，现在闭环了。
更彻底的形态（用户提的）：**每个子 agent 都装工具商店** ⇒ 反馈从"评测环节"变成"使用痕迹"，
与"实验室阶段不设收益率门槛"同一条原则：**让反馈成为使用的副产品，而不是额外流程。**

### 我补的两个偏差与解药

① **样本选择偏差**：只有被选中过的才有数据；**"从未被选用" ≠ "没用"，可能是"发现失败"**（描述差/名字不起眼）。
   → 解药 **探索配额**（强制把一小部分委派派给低选用率能力）；否则能力库锁定早期赢家（富者愈富 = bandit 标准问题）。
② **高选用率可能是"描述过度承诺"**：同时记录 **选用率**（发现性）与**复用率**（交付后被再次选用 = 真实价值）。
   **高选用率 + 低复用率 = 描述过度承诺** —— 一个具体、可检出的失败模式。
③ 评分者之间必须**互相隔离**，否则顶层偏好被下游继承 → "多 agent 投票"退化成"一个 agent 投 N 次"。

## 2026-09-14 02:15 —— 换代注入规则（三类）+ 无环原则

用户提案：**「如果 turn 正在跑 → 让它自行继续；如果本身就是停的 → 不要再注入」**
（当初设计自动续跑是为了"自动化任务中自己给自己换代，不用人介入"）。
并追问：**「但主 A（顶层）如果审批层要变动怎么办？还能继续完成这个自动化吗？」**

### ★ 判据是现成的：`prepareSwitch` 的 `waitedForTurnEnd`

`packages/switchboard/src/index.ts:333-373` 原文要点：
```ts
prepareSwitch: async (graceMs) => {
  if (state.mode !== 'active') return { ok:false, ..., reason:'not-active' }
  const agent = agents?.get(state.lastActiveSessionId)
  agent?.steer?.({ role:'user', content:'【系统通知】环境即将热重载。请把当前任务收尾…' })  // ← 对 idle 也注入
  // 等一个"晚于本次调用发起点"的 turn/end，或 grace 兜底
  p.timer = setTimeout(() => resolve({ ok:true, waitedForTurnEnd:false, reason:'grace' }), graceMs || 20_000)
}
```

**两个新事实**：
1. **`waitedForTurnEnd` 就是"当时有没有 turn 在跑"的代理判据**：
   `true` → 等到了 turn/end ⇒ **running**；`false && reason==='grace'` ⇒ **idle（或 blocked）**。
2. **⚠️ 它对 idle 会话也注入 steer，并白等满 grace（默认 20s）** ——
   因为 idle 会话不会产生新的 `turn/end`。
   ⇒ **给 fast 模式补上了最硬的理由**：正常 handover 那 20s **多数情况等不到东西**，
   不是"牺牲不中断换速度"，而是"那个等待本来就空转"。

**⇒ 应该分三类（用户两类 + 漏掉的一类）**：

| 状态 | 判据 | 换代时 |
|---|---|---|
| **running** | `waitedForTurnEnd === true` | ✅ **注入续跑**（该机制存在的理由） |
| **idle** | `reason === 'grace'` 且无挂起问答 | ❌ **不注入** |
| **blocked**（等人类输入） | `grace` + 最近是 `tool/call ask_user_question` 无对应 `tool/result` | ❌ **不注入 + 标记"不宜交接"**，理想是延后换代 |

**第三类是实测出来的**：只分两类会把 blocked 归进 running → 注入 → 它的 `turn/end` 永不到来 →
再换代 resume 失败 → 会话未 attach。

### ★ 无环原则（回答"审批层自己变动"）

**答：能自动化，但要在"需要外部见证"那一步停下来。**
因为**自动续跑 = 系统替用户批准了继续**：
- 换代的是**能力** → 自动继续合理
- 换代的是**判据/审批层** → **自动继续 = 被改的判据批准了自己的部署**（撞上"判据不能自证"）

> **无环原则（acyclic approval）**：把"谁批准谁"画成箭头，**出现回路就是漏洞**。

| 变动对象 | 见证方 | 自动续跑 |
|---|---|---|
| **R2 能力层**（tool/skill/prompt/子 agent/普通代码） | 判据阶梯（自动） | ✅ |
| **R1 判据层**（评测集/holdout/权限声明/配额上限/**审批逻辑**） | **外部（人/独立见证）** | ❌ 留待批记录 |
| **R0 自举层**（启动/恢复/回滚路径） | 外部 + **自举性检验** | ❌ |

**两条写死的规则**：① **层级标签不能由发起者自己填**（否则自标 R2）→ 由**变更路径**推断，
推断逻辑放**控制面**；② **控制面自身属 R1、agent 不可写** ——
"决定能不能自动批准的那段代码，不能被被批准的东西改写"（我们能改它因为站在 agent 之外）。

**契约式授权因此成立**：人批**一次**「标准 + 预算」，之后全自动；只有"标准本身要改"才回到外部见证。
**自动化不会被打断，它只是不能被自己破环。**

**已写入**：`docs/handover-vs-restart.md` §6.1 / §6.2；
`topics/self-evolution-design.md` §0 与 §4（新增第 4 条关键判断）。

**注入判据（最终）：`waitedForTurnEnd === true` —— "确有活、且已干净收尾"。**
| 场景 | 结果 |
|---|---|
| 有回合且正常收尾 | ✅ 注入（该机制存在的唯一理由） |
| 会话空闲 | ❌ 短路返回（顺带**省掉原先必然白等的 20s grace**） |
| grace 超时（有活没收尾，常见于卡在 `ask_user_question`） | ❌ 不注入，记录"可能在等人类输入" |
| fast 模式 | ❌ 不注入（跳过 defer 未探针，保守） |

**顺带收益**：正常 handover 在空闲会话上不再白等 20s —— 因为空闲会话永不产生 `turn/end`。
即"20s 等待"实际只在真有活时才发生。

### 改名推荐（用户问「你推荐什么好的」）

  → 工具前缀 `mcp__<name>__*`、`DESIGN_CANVAS_HOME`、`.design-canvas/` 数据根、`.design-canvas.json`
