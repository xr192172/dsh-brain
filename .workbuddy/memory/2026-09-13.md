## 补充（19:50）— 判据的第一原则改为「能力性 vs 效率性」

用户提出（并确认这是他更本质的框架）：**所有自进化最终只回答一个问题——能不能做到。**

- **能力性进化**（确定性指标：能不能完成某任务）→ **布尔门，硬门，一票否决**
- **效率性进化**（token 利用率 / 有效记忆留存率 / 工具错误率…）→ **软门，只用于排序择优**

**⚠️ 由此修正了老文档的一处设计**：`ai-base/docs/discussion/2026-08-06-llm-context-awareness.md:92`
原写「每个维度一个分数（0-100），**加权聚合为架构健康度总分**」——
加权和的致命处是"省资源"的边际成本远低于"做对任务"，必然存在"省 token 但任务做不成"的上坡路，
**这就是 reward hacking 的数学根源**。改为**字典序（lexicographic）**：先过能力门，再在达成者之间比效率。
这也让 `verification-contract` 的 I2「通过才采纳」有了精确含义：**"通过" = 能力门通过**。

### 四域 × 两类指标（沿用原文档的 6 类，合并为 4 域）

### 2) holdout 的真威胁模型（用户的核心质疑，已采纳）

用户质疑：**留本机的考题，锁也会被绕开**（能力强的 agent 可读内存 / dump 进程 / 改二进制 / 挂调试器）。

**结论**：目标从"让它读不到"改成"**让它即使读到也作弊不了**"。三机制叠加：
1. **哈希承诺（主）**：holdout 明文可留本机，但 `hash(holdout_vN)` 由**人签名并外发**；

2. **远程判题服务（辅）**：题与判据在远程，本机只持单向 `submit(candidate)->score` + token + **调用配额**
   （防暴力试答案）——这才是"进化税"的真实用途。
3. **隔离**：判题脑 = 独立进程 + 独立 OS 用户 + 只读挂载（可复用 `dsh-sandbox-windows-acl`）。

**用户的"QQ 号存考题 + 人管密码"方向对（外置 + 人握钥匙），但三个坑**：
① 登录凭据若在本机则外置失效（必须手机扫码、本机不落凭据）；
② 只外置题、没外置判题 → 仍可伪造判题结果（**题与判题必须一起外置**）；
③ 每次人要贴题 → 进化速度被人力封顶。

**命中率算法**：`cacheRead / (inputTokens + cacheReadTokens + cacheWriteTokens)`。
`TokenUsage` 三字段 **disjoint**（`dsh-llm/lib/types/types.d.ts:118-129`）；实测 cacheWrite 恒为 0。

### ★ 三个前缀改写源（这是全部根因）

**改写后的恢复曲线**（161 个事件）：第1轮 45.06% / 第3轮 75.22% / **第5轮 82.01%**
→ **一次改写，之后 5 轮回不到 93%。**

1. **`compaction/summary`（压缩）** — 必要代价，用户已接受。
   28f50f57：2049 轮 / 100 次 → **干净轮 93.14%（刚好达标！）**；受损轮 74.83%（369 轮）拉低到 90.09%。
   **→ 93% 是可达到的，差距全在改写频率。**
2. **`compaction/prune`（工具结果裁剪）** — 可消除。
   `tool-result-pruner` 默认 `thresholdChars:8192`，**当前 profile 配的是更激进的 4096**。
   **每个 tool/result 单独替换**（非批量）→ 读一个大文件 = 一次前缀改写。
   证据：design-canvas 19 轮 prune 6 次 → **44.04%**；13 轮 prune 7 次 → **35.99%**。10/16 会话的受损轮与 prune 有关。
3. **`request/header` 重建 + 工具模式切换** — 最致命且**与压缩无关**。
   `brain/fd6d7819`：**0 次压缩，命中率 71.64%**，13 个骤降点。
   形态指纹两种：`system=1789|tools=69`（Native/Dual）vs `system=75429|tools=1(run_code)`（**Code Mode**）
   → **两形态前缀完全不兼容，切换即全 miss**；另有 tools 69→70→71 的**动态注册**触发 header 重建。
   `前缀形态切换次数: 7/15`；13 个骤降点全部对应前置 header（距离 70~180 seq）。

### ⚠️ 配置疑点（P0 待验证）

`settings.yaml` 写 `contextWindow: 512000`，但**所有会话的 `request/context` 都是 128000**。
取值链 `dsh-llm-pi-ai/lib/index.js:639`：`entry.contextWindow ?? base?.contextWindow ?? request.defaultContextWindow`
→ 压缩阈值 `floor(contextWindow × thresholdRatio)`：128K→~102K vs 512K→~410K，**差 4 倍**。
**这批会话可能创建于配置改动之前；新开一个会话即可验证。**

### 来源追溯（用户问"是从 ai-base 还是 DSH？是我们手写引入的吗？"）

| 机制 | 归属 |
|---|---|
| `tool-result-pruner` | **DSH 官方原生包**（`github.com/deepseek-ai/deepseek-harness`，`packages/compaction/compaction-tool-result-pruner`，被 `dsh-base` 依赖） |
| 其中 `thresholdChars: 4096` | **我们手写的覆盖**（官方默认 8192） |
| 工具模式切换 Native↔Code | **DSH 官方原生机制**（`dsh-tools/lib/types/code-mode.js` + `dsh-agent-presets`）；我们只设了 `agent-presets.default: code` |

**ai-base 里没有这两个东西**，它的对应物是另一套（见下）。

### ★ 更好的同类设计（三个层次，最好的一层就在系统里）

**① `dsh-spill-policy`（DSH 原生，已在用）** —— 与 pruner 职责重叠但**时机相反**：
- 它是 **`tools/post-execute` 结果转换器** → **写入历史前**替换 → 写入的就是小消息 → **append-only → 不击穿**
- 且**存全文到 `spillStore`**，返回值带 **locator + retrieval guidance**（可召回）
- 而 pruner 是**事后** `surfaceOp: {op:"replace"}` 改已有节点 → **必击穿** + **原文丢弃不可召回**
- **⇒ 关掉 pruner、保留 spill-policy**
- 注意：spill-policy **明确跳过 `read`**（避免 read→spill→read 循环）→ 大文件读取这个最大输出源靠 **Code Mode** 兜

**② `ai-base` FileBuffer / SidecarBuffer（用户自己写的，更完整）**
`internal/context/file_buffer.go:16-26`：`path→内容` 覆盖更新、跨轮持久、`file_recall` 工具召回、
`IndexSummary()` **注入 DynamicInjection（尾部，不击穿）**。
比 pruner 多：path 去重覆盖 / 召回工具 / 索引走尾部 / 跨轮持久。**值得移植。**

**③ Code Mode / subagent（最彻底）**
`dsh-tools/lib/types/code-mode.js:1-6` 原文：**"only the outer curated result enters model history"**
→ 工具在程序内调用，**只有程序输出进历史**，读 10 个文件也不灌 10 份正文。
ai-base `design.md:721` 也识别过 subagent 隔离（"Claude Code 正是通过 Subagents 实现这一点"）。
**⇒ "根本不产生大内容"比"产生了再外置"更好。**

### ★ 本轮最重要的架构原则

> **外置化/缩减必须发生在「写入时」（append-only），不能发生在「事后」（replace）。**
> 写入时决定 → 前缀不动 → 零击穿；事后修改 → 前缀改写 → 击穿整个缓存。

方案排序（越靠左越好）：
`① Code Mode/子代理（0 代价）` > `② spill-policy（0，可召回）` > `③ FileBuffer（0，可召回+去重）` > `④ pruner（击穿+不可召回）`
