### 答「洪水填充为什么还有缝隙」

用户的模型**对了一半**：拼图的"形状"确实是一次划定的，但拼图存的是**内容**（符号/边），
而内容的**新鲜度**会漂 —— 缝隙不是"形状没画对"，而是三类**时间性**问题：

1. **圈定之后才出现的文件**（新文件不在任何块里）；
2. **上次填充被预算截停**（`maxFiles`/`maxMs` 撞上限 ⇒ `noExpand` 终点）；
3. **块内内容过期**（文件被改，块的"形状"没变但"内容"旧了）—— 这才是最主要的，
   也是五层保障（L1a/L1b/L2/L3①②/L4）在解的事。
⇒ 所以"缝隙"分两种：**覆盖缝**（边界扩展要解）与**时效缝**（保鲜五层要解）。别混。

### 答「能力自述」

= P10：工具要**如实说清自己对每种语言能解析到什么粒度**。

## ★★ 本轮最重要的发现：一次排查修掉 6 个既有测试红

### 排查方法（可复用）

**逐工具计时 + 边跑边落盘 + 单工具超时**：
之前一把梭跑全工具循环，一挂就什么都看不到；改成每跑一个就 append 到 jsonl，
被 kill 也留证据。这一步直接把"神秘 5 秒"定位到具体工具。

### 根因 ①：Windows 上 spawn **不在 PATH 上**的命令 = 白等 ~5.1 秒（不是"立刻失败"）

实测（逐工具）：`run_tests` 120103ms（无参=跑全量套件，工具自身职责）/
`harvest_from_url` 5183 / `harvest_decisions` 5169 / `find_references` 5189 / `move_symbol` 5171。
后四者共同点：`resolveProjectRoot` → `gitRootOf` → `execSync('git rev-parse ...')`。
单独测 `resolveProjectRoot(cwd)` = **5112ms**，其余原语 10~35ms ⇒ 铁证。

**修法**：新增 `src/tools/exec_guard.ts`
- `findOnPath(cmd)`：**纯 fs 查 PATH**（微秒级，一次 spawn 都不发）
- `commandAvailable(cmd)`：确认存在才 spawn 一次 `--version` 复核；结论**每进程记忆化**（含否定结论）
- `gitRootOf` 改 **① 向上找 `.git`（目录或文件，O(深度) existsSync）→ ② 走查落空才 spawn**
- `harvest_decisions.gitLogEntries` / `harvest_from_url.gitOk` 同样过闸
实测：`resolveProjectRoot` **5112ms → 1ms**；三个工具 ~5.2s → ~0ms。
★ 踩坑：`exeExts()` 在 Windows 上多了个空扩展名 ⇒ `path.join(dir,'')` === dir 本身
⇒ `findOnPath('')` 把**目录**当成"命令存在"。空串只能给 POSIX 用。

### 根因 ②：`find_references` 的**召回回归**（跨语言引用静默漏报）

`indexCandidateFiles` 只走 import 反向闭包；"没有 import 边的引用"——最典型是**跨语言**
（Go/Python 直接调 TS 导出函数名，磁盘上不存在任何 TS import 边）——**永远进不了候选集**。
零前置冷启让索引从"空"变"非空"之后，快路径接管、原先的"全闭包回退"被绕过 ⇒ 漏报。
代码注释还写着"绝不再回退全闭包逐文件即时解析"（性能取舍），**不该以静默漏报为代价**。

**修法**（正是已设计好的"两级索引"）：
候选集 = import 反向闭包 **∪ 文本提及补召回**（`refs_text.scanTextMentions`，
有界 `TEXT_SCAN_MAX_FILES=3000`）；真引用仍由细层（AST/文本探针）判定；
**召回边界如实上报**：`candidateScan = {closureFiles, textAdded, textScanned, textBounded}`，
截断时绝不假装完整（对应"不撒谎"不变量的"标注"半边）。

    "LLM 马上要读到的"现状，**那是另一种撒谎**

## 根因（带 git 的环境实测复现）

`git clone "file:///C:/Users/.../brick-repo-x"` ⇒ `fatal: '/C:/Users/.../brick-repo-x' does not
appear to be a git repository`。Git for Windows 解析 `file://` URL 时把路径部分当 **POSIX 路径**
（剥 `file://` 剩 `/C:/...`），Windows 语义下必失败。

## 修复（`src/tools/harvest_from_url.ts`）

- 新增 `fileUrlToLocalPath(url)`：`file:///C:/foo` → `C:/foo`（decodeURIComponent；其余形式返回 null
  原样走 URL 分支）。
- `shallowClone`：本地路径直接 clone（**不带 `--depth`** —— 本地克隆走硬链接，`--depth` 本就被
  git 警告忽略）；远程 URL 分支保持 `--depth 1`。
- 验收：`harvest_from_url.test.ts` **11/11 全绿**；`project_root.test.ts` 带 git 环境 31/31
  （此前报错纯因测试进程 PATH 无 git，代码无错）；tsc 0 错；dist 已重建验证。

## P1-7「修复 → 规则沉淀」落地（design-canvas `340e476`）

**定位**：把**一次实际修复**沉淀成可复跑规则。这是自进化落到代码改造的形态。

### 与 Grit/GritQL 的对齐与差异（设计校准的产物，别丢）

**采纳四项**（实读 docs.grit.io 校准）：
1. **md 载体**：规则 = 一个自包含 `.md`（frontmatter + 说明 + ```pattern /
   ```replace / `##` 夹具段）⇒ **测试即文档**，可整文件复制到别的仓。
2. **$hole 元变量**：占位代码片段，改写按名回填同一实参。
3. **CI 棘轮**：`baseline.json` 存存量命中 ⇒ **只在"新增命中"上 fail**。
   这样"先启用一条当前就失败的规则"不会炸 CI，而新引入的问题立刻被拦。
4. **todo() 半修**：三态 applied / todo（歧义即插 TODO 注释，不失败）/ clean。

**坚持两项差异（我们的独有）**：
- ★ **反例夹具**：Grit stdlib **零反例**；缺阴性对照就无法证明"只在该改的地方改"。
- ★ **萃取动作**：Grit 的 pattern **全靠专家手写**（无自动萃取）⇒ 我们让 agent
  现场从改动本身长出规则，这是"自进化"的关键一环。

**v1 有意不做**：完整 GritQL（bubble / or / 正则绑定 / join）—— 匹配层复用 P0-4 模糊级联。

### 文件拓扑（design-canvas）

| 文件 | 职责 |
|---|---|
| `src/tools/rule_tokens.ts` | 行/token 归一化小工具（**口径单源**，与 P0-4 L2/L3 同源） |
| `src/tools/rule_library.ts` | md 载体：parse / serialize / load / write + 合法性判据 |
| `src/tools/rule_match.ts` | $hole 匹配核（空白归一 / 同一 hole 同一实参 / `...` 跨行 / 唯一才动） |
| `src/tools/rule_extract.ts` | 萃取：diff 变化窗口 → 标识符抽象 → 自动夹具 → 三关校验 → **逐级放宽梯子** |
| `src/tools/rule_apply.ts` | 三态应用 + 棘轮 baseline + 夹具自检 + 目录遍历（排除派生物） |

**工具（3 个，refactor 线）**：`export_rule` / `apply_rules` / `check_rules`
（走 `wrapData`，不是 `wrap` —— 后者会 **丢掉 data**，结构化结论必须能返回）。
规则库位置：`<project>/.design-canvas/rules/`。

### ★ 核心机制：逐级放宽梯子（"泛化的度不靠猜"）

泛化不是越多越好（抽象多了规则过宽，会把不该改的也改了）。
**从"最多抽象"开始试**，每级用**验收三关**裁决；通过就采纳该级；全败则退化为
纯字面量规则，并如实标 `degraded` + `no_hole` warn。`attempts` 记录每级裁决。

**验收三关**（落盘前的机器判据）：
1. **出生回归**：pattern 必须命中 fixture.before，且改写结果 == after（复现不了这次修复 = 没萃取到）。
2. **反例不命中**：每条 negative 夹具都不得被命中。
3. **幂等**：把规则应用到 after 上不得再命中。

⇒ **三关不过时，即使 `dry_run=false` 也绝不写盘**（"绝不先写了再说"，已单测）。

### ★ 本轮修掉的 4 个真 bug（**都由新写的测试/验证器抓出来** —— 验证器的价值证明）

1. **夹具 scope 错位**：pattern 从"**变化行窗口**"泛化，夹具却用**整份输入**
   ⇒ 1 行 pattern 去改 3 行文本 ⇒ 必然误报 `birth_regression_diff`。
   **修**：pattern / replace / 夹具三者**同 scope**（走 delLines/insLines）。
2. **同行只报最左一处命中**：`f(); f();` 只报 1 处 ⇒ 就会去改第一个
   ⇒ **直接违反"唯一才动、歧义即停"**（会静默改错）。
   **修**：起点从"仅 0"改为"逐字符试"，同行两处都报 ⇒ 上层判歧义 ⇒ 转 todo。
   ★ 教训：**"唯一才动"必须建立在"能看见全部命中"之上**，否则纪律是假的。
3. **缩进补两次 / 漏补**：命中区间是否含行首缩进，必须与实际补缩进
   **恰好互补一次**（补重 ⇒ 2 空格变 4 空格；补漏 ⇒ 整块左移）。
   **修**：新增 `RuleMatch.absorbsIndent` 作为**唯一判据**；并把"命中是首行首个
   非空白内容 ⇒ 行首缩进并入区间"做成归一化（否则同一处命中会以两种 span 报两次 ⇒ 假歧义）。
4. **`diffLines` 的 `kind:'change'` 是死分支**：LCS 把"改一行"拆成 del + ins，
   原 `push` 只合并同类 ⇒ change 永不出现，`diffBlocks` 计数虚高。
   **修**：相邻 del+ins **合并为 change**。

# 2026-09-15（下午·续）verify-boot-health 漏判：根因定位（**已坐实，非猜测**）

## 事故重放（全部来自磁盘证据，无推测）

| 时刻 (UTC) | 事件 | 证据来源 |
|---|---|---|
| `08:25:31.328` | `===== BOOT gen=gen-3083 =====` 写入 | `gen-3083/boot.log:599` |
| `08:25:34.072` | switchboard 记 **`result:success`** · 已切换 → gen-3083 | `handover-status.jsonl` |
| `08:25:34.709` | **boot.log 最后写入（mtime）** ← 崩溃文本落盘 | `statSync` |
| `08:25:34.737` | **`gen EXIT code=1`** | `gen-3083/lifecycle.log` 末行 |

⇒ **崩溃文本比 `success` 晚 637ms 落盘**，进程比 `success` 晚 665ms 退出。

## 根因（两个，叠加；**不是**"正则漏了"）

**★ 先排除的假设**：`plugin tree failed to load` / `failed to apply loader entry include`
**本来就在** `FATAL_BOOT_PATTERNS` 里。所以不是模式缺失。跑 `findFatalBootErrors(整段)`
今天读那个文件**会命中**。⇒ 盲区在**时机**，不在**判据**。

1. **★ 时序竞态（主因）**：`verify` 阶段读 boot.log 时，崩溃文本**还没写到磁盘**
   （写发生在 637ms 之后）。⇒ 读到了一个"看起来干净"的段 ⇒ 判 ok。
   这与 2026-09-14 修过的 `verifyStableMs` 是**同一类病**，但那次只修了"进程存活"，
   **没修"文本可见性"** —— 稳定窗再探一次 `probe`，只证明进程还活着（此刻确实还活着！），
   不证明"日志已 flush"。**而且 `fast` 模式把稳定窗整个跳过了**，
   这次事故恰好是 `已快速切换` ⇒ **fast 路径 = 零观察窗**。
2. **★ 缺"正面证据"要求（结构性）**：检查是**纯否定式**——"没命中 6 个致命模式 ⇒ 健康"。
   但"还没写出来"与"写了但没命中的干净启动"**在观测上完全同形**。
   ⇒ 必须要求一个**只有在真正成功启动后才会出现**的正向标记（"引导完成"信号），
   观测不到就**不允许判健康**（宁可回滚，不可放行）。

## 结论（写进后续实现的判据）

> **否定式判据无法区分「干净」与「还没写完」。** 必须叠加正向完成信号；
> 且健康检查必须在**有界等待**内**重读**日志，而不是读一次就定论。

1. **有界等待 + 重读**（`verifyBootHealth`，窗口默认 **6s** = 实测 3.41s 的 1.75×）；

## 2026-09-15 傍晚：P4 设计前讨论 —— 能力清单「追加 + 压缩时物化」

用户提案：工具注入改为动态 —— 初始化注入当前清单；之后卸载/加载各**追加一条指令**；
压缩时对加载/卸载做**零和运算**（抵消），只保留当前状态 = 相当于刷新一遍。问对缓存是否更友好。

**结论：方向对，且比原方案 C 更强；但有一条硬约束决定它能否成立。** 已写入
`docs/capability-registry-evolution.md` **§6.1**（+ §9 的 P4 行）。

### 为什么方向对（是本项目已验原则的外推，不是新赌注）

`prompt-cache.md` 已固化：**外置化/缩减必须在「写入时」append-only，不能事后 replace**；
推论「动态的东西不要放前缀，放尾部或按需」。用户方案逐条对上：
init 清单 = 写入时基线｜变更 = 追加尾部｜压缩时物化 = **借 ①「压缩」那次必要重写**（边际≈0）。

### ★ 硬约束：`tools` 是结构化 header，不是文本

`request/header` 就是发给 LLM 的真实 header（system + tools）；形态指纹 `(system 字符数 | tools 数)`，
Native/Dual 实测 `1789|69~71`。
⇒ **模型能调用什么由 header 的 tools 清单决定；追加一行文字不能让未声明的工具变得可调用。**
（强行调用会被 API 拒 → 模型白烧轮次重试 → **比不提供更坏**。）

⇒ 「追加」只对**通过稳定通用工具可达**的东西成立 ⇒ 仍然需要 `delegate_capability(name, task)`：
- **调用入口**（schema）在 `tools` 段里，**恒定**
- **地址集合**（有哪些名字）走尾部追加，随时变

⇒ **追加方案不取代方案 C，而是补全它**，且强两点：
① 原 C 只管"长尾不进前缀"，追加法连**核心集合变动**也便宜（加通知而非重写 header）；
② 它给了一条**「推」的通道** —— 模型不必先问就知道有什么。
这与刚定下的教训直接相关：**"不知道去哪发现"是最坏的一类失败**（连坐标都没有）。

### ★ 「零和运算」这个提法必须改写：加减**不可交换**

```
+X, -X  ⇒ 最终无 X   ← 净零，可丢
-X, +X  ⇒ 最终有 X   ← 净"非零"；成对相消的手法会把它**错判成零**
```
所以正确形态不是"抵消成对事件"，而是**「上次物化状态 M + append-only diff」**：
判据 = **当前集合 == M?** 是 ⇒ 整段 delta 可丢（更强也更简单）；否 ⇒ 物化一次。
物化时机：① 压缩时（已在付重写代价）② delta 超阈值。
= **op-log + snapshot / 定期物化**（LSM compaction、CRDT op-log 压缩同源），成熟做法。

### 三条正确性不变量

1. **文本承诺的集合 ⊇ 实际可调用的集合**（反之绝不允许）—— 只能宣传真能调通的能力；
   经 `delegate_capability` 中转 ⇒ 名字非法可报错 ⇒ **路由判据仍可执行**（C 相对 B 的核心优势必须保住）。
2. **物化必须与压缩摘要「同一次写入」**。分两步做 ⇒ 摘要可能丢"加载"留"卸载" ⇒ **静默状态丢失**。
3. **物化后回到"干净基线"**（形态 == init 的形态），否则每次压缩换一种写法 ⇒ 又成一个改写源。

### 验收口径（可测）

用 `dump-request-tools.mjs` 扫多轮会话，断言 **`tools` 数在无压缩轮里恒定**
（指纹 `1789|69~71` → `1789|N`，N 不跳），`(system 字符数 | tools 数)` 只在压缩处变化。
⚠️ 诚实边界：本方案**只**消除"能力增删"这一改写源；④ 冷启动/空闲过期是结构性的，不受影响。

## 2026-09-15 傍晚（续）：§6.2 —— 「不进 surface」优于「进去再剔除」

用户追问：*给工具的指令带一条**不显示在上下文中的标记**，由工具去手动合并和剔除，不行吗？*

**行，且 DSH 原生有全套机制 —— 但要把"藏起来的标记"与"根本不写进去"分开。**
已写入 `docs/capability-registry-evolution.md` **§6.2**。

### 关键事实（核到类型定义）

```ts
export type SurfaceEventType = 'user/message' | 'assistant/message' | 'tool/result'
```

⇒ **`surface` = 「产生模型消息」的那三类事件**（不是 UI 层面）。
`dsh-session/lib/types/surface.js` 有 `isSurfaceEvent` / `isAppendSurfaceEvent` /
`isReplacementSurfaceEvent` / `foldSurface` / `deriveEventMessage`。
**不属于这个三元联合的事件类型，按构造就不可能成为模型消息** —— 只在日志里。

⇒ 所以能力增删可以写成一个**自定义非 surface 事件** → **0 token、0 前缀影响**。
（自家先例：`packages/tool-evolution` 已注册自定义会话事件 `tool/review`。）

### 「手动合并和剔除」的现成机制：`surfaceOp` + `sourceEventSeqs`

```ts
SessionEvent = { type, seq, time, data, ignorable?: true }
             & (K extends SurfaceEventType
                  ? { sourceEventSeqs?: number[]; surfaceOp?: SurfaceOp } : object)
```
`surfaceOp` = `'append'` | replace 变体；`sourceEventSeqs` = 本事件取代/派生自哪些更早事件
（= 精确剔除的载体）。非 surface-eligible 事件携带 `surfaceOp` 会**直接抛错**。

### ★ 但别用中途 replace —— 我们踩过

`replace` = 事后改写。实测：`dsh-compaction-tool-result-pruner` 用 `surfaceOp: replace`，
**161 次改写里占 72 次** ⇒ 已 `disabled`（`prompt-cache.md` ② "已消除"）。

### ★★ 最优形态：不靠 replace，靠「搭已有 append 的车」

把"剔除"升级为"**从未进入**"，代价从"一次重写"降到 **0**：
① 能力增删 → 非 surface 事件（0 成本）；
② 折叠**搭在本来就要发生的 append 上**（下次 user/message 或 tool/result），
   作为**该次 append 的内容**写出 —— append 在尾部 ⇒ **前缀一字未动** ⇒ 只付新增那几行；
③ 模型提前需要知道 → `list_capabilities()` 按需（pull 兜底）；
④ 幂等记账 → 记「已折叠到哪个 seq」。

**"从未进入"严格优于"进入后剔除"** —— 标记的真正作用**不是"藏起来"，而是"幂等记账"**。

### 一处纠正

`SessionEvent.ignorable?: true` 易被误读成"不显示在上下文"。实际是**日志前向兼容**：
读日志遇到本 build 不认识的类型，未标 `ignorable` 就**拒绝解释整份日志**
（"likely written by a newer harness"），标了则可跳过。**与模型上下文无关。**

### 合并后的完整方案（§6.2.6）

| 层 | 承载 | 变化 |
|---|---|---|
| `tools` 段 | `delegate_capability` + 核心角色工具 | **恒定**（指纹 `(system\|tools)` 不跳） |
| 能力增删 | **非 surface** 自定义事件 | 随时，**0 成本** |
| 模型可见的当前集合 | 折叠行（搭 append 的车）/ `list_capabilities` | 低频，仅新增行未命中 |

⇒ 上一轮"先定核心 vs 长尾切分判据"的建议可**再放宽**：
**默认全部走 dispatcher**，只有当"经中转真不够用"时才升级成专属工具槽
（判据 = 是否需要 schema 级确定性调用；一旦占槽，改它就要重写 header）。

## 2026-09-15 傍晚（再续）：§6.3 架构决策 —— 自建插件，不加深上游补丁

用户问两件事：① 我们依赖这个不稳定版本的内部实现挺多，要不要**自建插件**或**改它**？
② 它现在的上下文管理是 append-only（只追加），**能做到我们说的那个吗？**

已写入 `docs/capability-registry-evolution.md` **§6.3**。

### 答②：能 —— 而且 append-only **是我们的朋友**，不是障碍

关键是把两层分开：

| 层 | 是否只追加 |
|---|---|
| **会话日志**（`session.jsonl`） | **严格只追加**，从不改写 |
| **surface 投影**（`foldSurface` → 模型可见消息） | 可收缩/可替换 |

`surfaceOp: replace` **不是"改日志"**，而是**追加一条「替换意图」**；`foldSurface` 在**投影时**折叠掉。
⇒ 日志仍只追加。而 §6.2 的方案（非 surface 事件 + 搭车折叠）**全是纯追加** ✓。

**唯一与 append-only 语义相冲的是 `replace` —— 而那恰恰是我们不能用的那条**
（事后改写 ⇒ 击穿前缀，§6.2.3）。⇒ **用户的担心正好指向我们要走的反方向。**

### 答①：自建插件，且**不需要改它**

已核实的**扩展点**（全是公开面，不是内部实现）：

| 需要的能力 | 机制 | 性质 |
|---|---|---|
| 观察每次追加 | `ctx.on('session/event', (id, event))` + `session/flush` | 公开 firehose |
| 写自己的能力变更 | `ctx.session.append(type, data, ...opts)` | 公开方法 |
| 自定义事件类型 | 支持（**自家先例**：`tool-evolution` 已注册 `tool/review`） | 既有扩展点 |
| 非 surface ⇒ 不进上下文 | `SurfaceEventType` 是固定三元联合，其它类型**按构造**不进 | 类型系统保证 |

⇒ 这正是"写插件"的用法，不是"改内核"的用法。P4 这部分应做成**我们自己的插件**
（或并入 `capability-bridge`），而不是继续给 `dsh-compaction-basic` 加深补丁。

**理由是可维护性，不是洁癖**：上游是移动靶，且已证实 —— 2026-09-14 上游把 boot 重构成
`profile-resolution/*`，`patch-app-boot-bom.mjs` 引用的行号**当场失效**（见 `upstream-defects.md` §U2）。
我们已有 5 个补丁脚本 + 1 个 500 行 patch-package 补丁，每加一处都是"上游一改就坏且不告诉你"。
且补丁打的是**编译产物**，上游重构后行号/函数名全失效。

### ★ 顺带松开了不变量 2：折叠写「快照」不写「diff」

**内部记账**用 diff（哪些变更还没进模型）；**写出去的是完整当前集合快照**。带来：

1. 幂等且可丢（可重复写、可丢）；
2. ★ **丢掉的后果是「不知道」，不是「以为错」** —— §6.1.4 不变量 2 担心的
   "摘要丢加载留卸载 ⇒ 静默状态丢失"，**在快照形态下不会发生**（快照里没有"卸载"这种相对量）；
   丢了最多是模型不掌握当前清单，由 `list_capabilities` 兜底。
   ⇒ **不需要 patch 压缩插件保证"同一次写入"，这条约束自然消失。**

### ★ 查出一个同类"假绿"（待拍板）

`scripts/patch-*.mjs` **没有任何 `process.exit`** —— 锚点找不到时只打印
`FAIL` / `⚠️ anchor not found` 然后**继续**。而它们挂在 `postinstall`
⇒ **上游一变，补丁静默失效，无人被告知**。与我们反复修的"假绿"同类。
建议：锚点未命中 ⇒ 非 0 退出（`DSH_PATCH_STRICT=0` 可显式降级）。
**待用户拍板**（影响 `npm install` 行为）。

## ② P4 折叠内核（离线可验）

`packages/capability-bridge/src/notice.ts`（纯函数）+ `scripts/test-capability-notice.mjs`（**27 项**）。
