### 答「洪水填充为什么还有缝隙」

用户的模型**对了一半**：拼图的"形状"确实是一次划定的，但拼图存的是**内容**（符号/边），
而内容的**新鲜度**会漂 —— 缝隙不是"形状没画对"，而是三类**时间性**问题：

1. **圈定之后才出现的文件**（新文件不在任何块里）；
2. **上次填充被预算截停**（`maxFiles`/`maxMs` 撞上限 ⇒ `noExpand` 终点）；
3. **块内内容过期**（文件被改，块的"形状"没变但"内容"旧了）—— 这才是最主要的，
   也是五层保障（L1a/L1b/L2/L3①②/L4）在解的事。
⇒ 所以"缝隙"分两种：**覆盖缝**（边界扩展要解）与**时效缝**（保鲜五层要解）。别混。

### 答「能力自述」

= P10：工具要**如实说清自己对每种语言能解析到什么粒度**。
例：TS/JS 能给出"函数/类/方法/import/call"级；Go/Python 有 import 边 + 调用；
C/C++/C# 刚进 AST 闭包与 include/using 解析；某些语言只能到"文件级"。
若不说，LLM 会把"**解析不到**"当成"**不存在**"（漏报），或把"解析到但粒度粗"当成精确结论。
落地形态：按语言给一张"可解析粒度表"，并让结果里带 `解析粒度: xx` 标注。**未做**。

## ★★ 本轮最重要的发现：一次排查修掉 6 个既有测试红

### 排查方法（可复用）

**逐工具计时 + 边跑边落盘 + 单工具超时**：
之前一把梭跑全工具循环，一挂就什么都看不到；改成每跑一个就 append 到 jsonl，
被 kill 也留证据。这一步直接把"神秘 5 秒"定位到具体工具。

### 根因 ①：Windows 上 spawn **不在 PATH 上**的命令 = 白等 ~5.1 秒（不是"立刻失败"）

实测（逐工具）：`run_tests` 120103ms（无参=跑全量套件，工具自身职责）/
`harvest_from_url` 5183 / `harvest_decisions` 5169 / `find_references` 5189 / `move_symbol` 5171。
后四者共同点：`resolveProjectRoot` → `gitRootOf` → `execSync('git rev-parse ...')`。
单独测 `resolveProjectRoot(cwd)` = **5112ms**，其余原语 10~35ms ⇒ 铁证。

**修法**：新增 `src/tools/exec_guard.ts`
- `findOnPath(cmd)`：**纯 fs 查 PATH**（微秒级，一次 spawn 都不发）
- `commandAvailable(cmd)`：确认存在才 spawn 一次 `--version` 复核；结论**每进程记忆化**（含否定结论）
- `gitRootOf` 改 **① 向上找 `.git`（目录或文件，O(深度) existsSync）→ ② 走查落空才 spawn**
- `harvest_decisions.gitLogEntries` / `harvest_from_url.gitOk` 同样过闸
实测：`resolveProjectRoot` **5112ms → 1ms**；三个工具 ~5.2s → ~0ms。
★ 踩坑：`exeExts()` 在 Windows 上多了个空扩展名 ⇒ `path.join(dir,'')` === dir 本身
⇒ `findOnPath('')` 把**目录**当成"命令存在"。空串只能给 POSIX 用。

### 根因 ②：`find_references` 的**召回回归**（跨语言引用静默漏报）

`indexCandidateFiles` 只走 import 反向闭包；"没有 import 边的引用"——最典型是**跨语言**
（Go/Python 直接调 TS 导出函数名，磁盘上不存在任何 TS import 边）——**永远进不了候选集**。
零前置冷启让索引从"空"变"非空"之后，快路径接管、原先的"全闭包回退"被绕过 ⇒ 漏报。
代码注释还写着"绝不再回退全闭包逐文件即时解析"（性能取舍），**不该以静默漏报为代价**。

**修法**（正是已设计好的"两级索引"）：
候选集 = import 反向闭包 **∪ 文本提及补召回**（`refs_text.scanTextMentions`，
有界 `TEXT_SCAN_MAX_FILES=3000`）；真引用仍由细层（AST/文本探针）判定；
**召回边界如实上报**：`candidateScan = {closureFiles, textAdded, textScanned, textBounded}`，
截断时绝不假装完整（对应"不撒谎"不变量的"标注"半边）。

## 教训（可复用）

1. **"测试红"必须先定位根因再动手** —— 两个都是真 bug（性能/召回），不是测试坏。
   若当初按"环境问题"忽略，就一直带着 5 秒/次的隐性成本和跨语言漏报。
2. **逐工具计时 + 边跑边落盘** 是定位"哪个调用慢"的唯一可靠手段（一把梭看不到）。
3. **Windows spawn 不存在命令 ≈ 5 秒**：所有 `execSync` 都要过 `exec_guard`。
4. **测"注入型逻辑"必须给它单测**（exec_guard 的 `findOnPath('')` bug 就是测试抓出来的）。
5. **改测试超时/排除表要写明理由**（run_tests 无参=跑全量是它的职责，不该由注入用例驱动；
   排除表还加了"必须真实存在"的断言，防用它掩盖坏工具）。

## 03:00–04:20 L3① 结构性精确化（用户选了先做三）

### 方案：不在 11 个同步入口逐个改 async，而是**结构性**解决

原计划是给 17/11 个"直接开库没保鲜"的读工具逐个加 ensureProjectIndex —— 但它们多数是**同步签名**
（diff_impact / extract_contracts / harvest_closure / language_concepts / query_feature / function_outline /
analyze_monolith / derive_mind_map），改成 async 会波及大量直接调用的测试。

**改法**：在 `registerAllTools` 的**唯一入口**，调 handler 之前：
若入参带项目根 && `hasLiveIndex(root)` && `!def.noAutoFresh` ⇒ `await ensureProjectIndex(root, {bootstrap:false})`
全部 60 个工具自动精确，**以后新增工具也不用记得**（结构保证，不是自觉）。ready 态实测 ~35ms/次（390 文件）。

三条纪律（写进注释）：
- bootstrap:false —— 绝不因一次调用就冷启建索引（hasLiveIndex 双保险）
- 失败静默不阻断 —— staleIndexWarning 仍兜底标注
- **noAutoFresh 逃生口**（ToolDef 新字段）：
  - index_integrity：refresh:false 必须纯只读 —— 若被自动保鲜，它报告的是"修完之后"而非
    "LLM 马上要读到的"现状，**那是另一种撒谎**
  - import_project：自己做全量导入，前置保鲜纯属浪费

### 测试（3 项，tests/server_registry.auto_fresh.test.ts）

- 绕过写闸改文件 ⇒ 调**任意**带 project_dir 的工具 ⇒ 索引自动跟上（断言 db 的 size === 磁盘 size
  —— 这是"结果精确"，不再只是"标注可能旧"）
- noAutoFresh：index_integrity({refresh:false}) 报告的是**调用前**现状（索引没被动过）；refresh:true 才修
- 没索引 ⇒ 不冷启（绝不因一次调用凭空建索引）

★ 踩坑：连接池持有 cache.db 句柄 ⇒ Windows rmSync 报 **EBUSY** ⇒ 清理前必须 `closeAllProjectCacheDbs()`
