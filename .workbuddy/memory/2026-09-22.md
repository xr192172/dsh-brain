## 二十七、★★★★ 官方文档核证：用户关于「缓存时序 / 多子代共存」的判断成立 + 我 TTL 警告过度

**用户原话要点**："静置以后肯定不能用了呀，但是**父代都已经准备动了，那说明父代这一轮调用工具的那一次，百分百是建立了缓存的**。
只是问题在于父代很久没用过，你再让它做某个任务时，**这一波会在父代时重建一次缓存、要吃一波钱**；
但父代动起来以后缓存就建好了，**子代依旧可以直接[复用]**。
**除非多个子代从多个起点开始，后一个子代会影响另一个子代的缓存，但这个按理来说不会。**"
（并提示我去官网查证）

**查证来源**：`https://api-docs.deepseek.com/guides/kv_cache`（Context Caching，逐字引用）

### ✅ 用户两点判断都成立

| 用户判断 | 官方原文 |
|---|---|
| 父代调用工具那一次**必然已建缓存** | "**Each user request will trigger the construction of a hard disk cache.**" |
| 多子代**不会互相影响** | "**When the system detects a common prefix across multiple requests, it will persist that common prefix as an independent cache prefix unit.**" ⇒ 同一父代、同一 fork 点的多个子代**共享同一条公共前缀 ⇒ 共享一个单元，而不是互相驱逐** |

### ★★ 我上一轮的"TTL 是最大适用边界"**过度了**

官方：**"Once the cache is no longer in use, it will be automatically cleared, usually within a few hours to a few days."**
⇒ **窗口是数小时~数天**，不是我暗示的"同秒级脆弱"。叠加"每个请求都触发缓存构建" ⇒
**"父代刚做完事就 fork"这个用法下 TTL 根本不是问题**；
只有**父代长期静置后第一次动**才付一次重建钱，**而那是父代自己的成本，它本来也要付**。
⇒ **规格 §13.5 第 1 条（"TTL 是最大的适用边界"）作废。**

### ★★★ 官方机制比我说的更精确（本轮真正的收获）

> "**A cache hit requires that the corresponding prefix has already been 'persisted' … Each cached prefix is an independent, complete unit.
> A subsequent request can only hit the cache if it【fully matches】a cache prefix unit.**"

**单元持久化的三个时机**（逐字）：
1. **请求边界**：每个请求产生**两个单元** —— **用户输入末尾** 与 **模型输出末尾**；
2. **公共前缀检测**：检测到多请求公共前缀 ⇒ 把它持久化为**独立单元**；
3. **固定 token 间隔**（长输入/长输出）："to avoid long prefixes from being completely uncacheable due to never reaching an end position"。

⇒ ★★ **所以"能复用多少"不是简单"等于种子长度"，而是：子代前缀必须【完整匹配】父代留下的某个单元边界。**
⇒ **与我们实测精确吻合**：子代首请求 `cr=133,248`，而**父代自己那次请求命中的也是 `133,248`**（父代 `seq=495`）
⇒ **子代命中的就是父代留下的同一个单元。**
⇒ **fork 之所以结构性几乎总能命中**：子代种子 = 到最后一个 `turn/end` = 父代**模型输出末尾**
⇒ **正好落在规则 1 的边界上**；规则 3 的长上下文固定间隔再兜一层底。

### ⚠️ 由此得到一条**可证伪的预测**（O25）

若某次 fork 的**种子边界不落在任何单元边界上**，该子代首请求命中应当**显著下降**（而非仍为"脸 + 种子"）。
但 `completedTurnPrefix` 只取**完整回合** ⇒ **默认必然落在"模型输出末尾"** ⇒ 这条预测的**更可测形态**是：
**种子长度取不同值（尤其卡在两个固定间隔之间）时，`cr` 是否出现台阶。** **留待下一批实验。**

### 其它要记账的官方约束

- "**best-effort**…**does not guarantee a 100% cache hit rate**" ⇒ **不可把"命中"当保证**。
- "**The hard disk cache only matches the prefix part of the user's input**；output 仍要计算" ⇒ **命中 ≠ 这一步免费**。
- 官方命中读数 = `usage.prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`
  ⇒ 与我们一直用的 `cacheReadTokens` / `inputTokens` **口径一致** ✓

### 回答"需不需要在子代时就标记好'这是某工具面'？"

**需要，但用途是【审计与判据】，不是替代快照机制。**
- **标记这半采纳**：给工具面一个**短指纹**写进快照（`当前工具面 face=<指纹>（N 个工具）：…`）
  ⇒ ★ 换来**可机验判据**：比对"日志里模型看到的 face 指纹" vs "当时真实注册表指纹" ⇒ **自动检出陈旧宣称**。
- **失效这半不用我们发明**：新快照自带 supersedes；清空时上游发 `CLEARED`。

### 落地五步（这就是"怎么处理"的答案）

① 分身创建时注册 **child-scoped `systemPrompt.context()`**，内容 = 当前工具面（+自带 supersedes 前缀）；
② 能力集变化 ⇒ provider 重算 ⇒ **新快照追加** ⇒ 旧的被**显式推翻**；
③ 孙代 fork 时，种子里那条旧快照**仍在**，但孙代**自己装配会注入它自己的快照** ⇒ 旧宣称被推翻 ⇒ 不会乱调；
④ 某层 face 变空 ⇒ 上游发 `CLEARED`；
⑤ 审计：face 指纹比对。

★ **全部落在消息面 ⇒ 不改 system ⇒ 不砸前缀**（与 D2′/D3 一致）。

## 三十一、★★★★ 机制确认 + 更省的改法 + 「上游更新了我会不会白做」的诚实答案

### 1. 用户的机制描述成立

"这套机制就是**让 LLM 清楚自己现在有什么**：子代时宣告进入新工具面、有了新工具；孙代时告诉它上一个工具面失效了" ⇒ ✅ **成立**，
而且**这正是上游维持正确性的唯一手段**（§17.2 的 `supersedes` 那句话就是干这个的）。

### 2. ★★ 但有一个**更省、更不易过期**的改法（第一原理推出来的）

**关键认识：模型本来就看得到"当前真脸"** —— native 模式 schema 在本次请求的 `tools` 里；code 模式 SDK 段在 `system` 里。
⇒ **runtime-context 那句的价值不是"提供信息"，而是"消解矛盾"**：种子里旧声明说"你有 X"，而本次请求没有 X
⇒ 同一上下文里两条矛盾信息，且**旧的那条当时是真的** ⇒ 模型可能继续信旧的。
⇒ ★ **所以快照应当【强调作废】而不是【重述清单】**：

- 推荐：`工具面已变更为 face=<指纹>；更早关于工具面的声明不再适用。当前可用工具以本次请求的工具列表为准。`
- 不推荐：把工具名再列一遍（与 schema/SDK 段重复、白花 token、自己也会过期）

⇒ 好处：更短 / **指向权威来源 ⇒ 自身永不过期** / 与 face 指纹审计兼容（指纹机验、句子告知）。

### 3. ★★★ 战略问题："上游这么深入，上游更新了，我是不是白做？"

**分三档，风险差别极大：**

**(a) 风险最高：重写上游已有的机制。** 上游手里已有三块料（`presentAs` / `context()` / `tools.register`）+ fork/spawn/compaction，
**我们若去写"脸冻结 + 钉住 SDK 段 + 尾部目录"，上游完全可能做个更好的版本** ⇒ 这正是**铁律 #17 那条红线**。**⇒ 别在这条路上投重兵。**

**(b) 风险极低：我们真正产出的东西 —— 它们不是"功能"，是"判据与量测"。**
本机 `chars/token≈2.87`、脸 40.2K（tools 94%）、fork 种子复用 **1:1**、`end-seed` 与 mode 的**伪**相关、
`complete` 段**静默作废**钉住、压缩信号历史为真 **202 次**、`node -e` 被 shell 吃引号、`chars/4` 估错 **40%**、
主表首请求取错事件、**用小种子否定长上下文主张**……
⇒ ★ **这些是"这台机器 + 这套配置下的物理事实"与"我们踩过的坑"。上游更新不会让它们失效，只会让我们重新量一遍；
而它们的功能恰恰是【测出这次更新有没有把我们的假设弄坏】。** ⇒ **上游永远不回答"我们的不变量是否被破坏"。门是长期资产。**

**(c) 上游不会替我们做的（它的默认组合不需要）：**
1. **能力传承（O26）** —— 上游子代**刻意绑到 preset 的 standing scope、不继承父代 agent 的注册**（§16.2）⇒ "A 的专有能力怎么给 B"**它不解决**。
2. **压缩点吞掉作废快照（§17.5）** —— 上游压缩是**通用区域压缩**，不专门处理我们注入的快照。
3. **本机复合体**：council preset / 议事厅席位 / switchboard / eval 靶场。

**(d) 策略（可执行）**

1. ★★ **任务类型必须选对**：现有 5 条是**单次孤立**任务，而**记忆的作用域是"重复出现的同类问题"**

   ★ 且 **k=1 应无差别** —— 这本身是该批数据的**阳性对照**。
2. ★★ **对照要干净：两臂同一张脸，只让【记忆库内容】不同** —— 若靠"摘掉 MCP 行"禁用记忆，**两臂脸就不同**，

3. ★ **三条对照断言（任一不满足 ⇒ 该批数据作废）**：**两臂 face 指纹相同**（复用 `scripts/face-audit.mjs` 的算法，**记得端口归一化**）
