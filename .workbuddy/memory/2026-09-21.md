
## 07:10 用户重启后仍 502 → 真根因是"31 个包缺失"（我的判断失误）

### 现场（用户【确实】重启了）

- 前门 3080 → **502**；`activeGen = gen-3082`；`freezeSeq = -1`
- 启动日志 mtime **07:09:59**，前门/控制面换了**新进程（PID 17360，原 9544）** ⇒ 重启动作是发生了的
- 启动器做了 `lease recovery` ⇒ **把很旧的 gen-3082 当活跃代恢复** ⇒ 它立刻 `EXIT code=1`

### ★★ boot.log 这次的错【变了】⇒ 证明上一轮的 sharp 修复生效了

```
failed to import loader entry llm-pi-ai (@deepseek-ai/dsh-llm-pi-ai):
  Cannot find package '@earendil-works/pi-ai'
```
**不再报 `@img/colour`** ✓ ⇒ 那一步是对的。

### ★ 我的判断失误（诚实记录）

`audit-partial-packages.mjs` **早就报了**「① 缺失（非 optional 的要留意）：`@anthropic-ai/sdk` /
`@aws-crypto/…`」—— **我却以为"非-optional 缺失可能不需要"而没管**。
⇒ 实测：**非-optional 且可按 lock 重取的缺失包共 31 个**，gen 就是被它们**一个个**绊住的。
⇒ **教训：「① 缺失」里非-optional 的那部分就是【必须修】的**，不是"可能不需要"。
⇒ 更上一层的教训：**我明明有扫描器报了，却没把它的输出当判据用** —— 有工具不用，等于没有。

### 修：一次补齐（不再被 boot.log 一个个牵）

按 lock 的 resolved + integrity **批量重取 31 个包**（国内镜像、不用 npm、不动 P2）：
`@anthropic-ai/sdk` · `@aws-crypto/*` · `@aws-sdk/*`（17 个）· `@aws/lambda-invoke-store` ·
`@babel/*`（3 个）· **`@earendil-works/pi-ai`** · `@google/genai` · `@hono/node-server`

### 验证（全部实测）

- 非-optional 缺失：**31 → 1**（剩的是 `@dsh-brain/conveyor-context`，**有意删除**，不该补）
- `@earendil-works/pi-ai` 可加载 ✓
- **`@deepseek-ai/dsh-llm-pi-ai` 可加载** ✓（gen 报的那个 loader entry）
- `web --dump-config` exit=0 ✓ · `check-all` 15/0 ✓

### 另修

`refetch-lock-packages.mjs` 的 files 对账里有同类假红（`dist-*/*` 是 glob）⇒ 只查字面项。

### ⏭ 下一步

**再次重启栈**（用户终端）：`cd D:\project_develop\dsh-brain` + `node scripts\relaunch-switchboard.mjs`
⇒ 若 gen 起来，靶场线即可连走：端口修复真机验证 → 第一对能力开关实验 → 接 `verifyCmd`（M2 闭环）。

## 07:15 ✅ 栈起来了（但跑的是旧代；发现 lease pid 过时）

用户第二次重启 ⇒ **前门 3080 → 200，返回真内容**（HTML + `__ModuleLoader__`）。

### 证据

- `gen-3082/boot.log`（mtime 07:15:01）尾部是**完整正常启动序列**：
  design-canvas-bridge 各工具已注册 → `[design-canvas v0.1.3] MCP server started (stdio)` →
  `dsh web: http://127.0.0.1:3082` ⇒ **无错误** ✓
- `check-all` **15/0** ✓

### ⚠️ 但它跑的是【旧代】

`verify-drain-after-swap.mjs` 的 **R0c**：**"这次 build 之后换过代吗" ⇒ 没有**
⇒ **今天所有代码修复（端口跳号 `allocGenPort` / B3 原子写 / B4 删前判存在 / conveyor 摘除）
都还没在真机上跑过**。栈是"用旧代可用"，不是"新代码生效"。

⇒ **下一步 = 一次【非 fast】换代**（那正是靶场线回执 §D 的第一步）：
```
node scripts\check-session-integrity.mjs --all      # 换代前体检
curl.exe "http://127.0.0.1:31808 … 实际是 31800/?cmd=handover"
```
⚠️ **换代会让当前会话迁移** ⇒ 时机由用户定。

### ★★ 新发现的隐患：`lease` 的 pid 是【过时的】

```
lease.activeGen = { gen: gen-3082, port: 3082, pid: 14424 }   ← 14424 那次已 EXIT code=1
netstat: 3082 在听的是 pid 23232                              ← 实际服务的是另一个进程
```

⇒ **lease 记的 pid 与实际不符**（`lease recovery` 恢复的是旧记录，之后 gen 又被重启了一次，
但 lease 没跟着更新；`freezeSeq=-1` 是同一现象的另一面）。

**为什么这要紧**：**`drain` 判"谁在写"依赖 lease 的 pid** ⇒ lease 说 14424（已死）、实际 23232 在写
⇒ **换代时 drain 可能认为"无活跃写者"而不等待就切** ⇒ 那是 **M0 那个写入竞态的形态**
（`seal: keep-old` 应当兜住，但这属于"判据读到过时数据"这一类，值得单独立案）。

⇒ 归口 **switchboard（P2，只报不修）**；已记入待办。

### 今天的依赖事件小结（三次同族）

| 次序 | 缺的东西 | 谁发现的 |
|---|---|---|
| 1 | `@deepseek-ai/*` ~200 个（整个树） | 靶场会话的子代理（离线按 lock 补齐） |
| 2 | `@img/colour` + `@img/sharp-win32-x64` 缺 `index.cjs` | 我（从 gen-3082 的 boot.log 定位） |
| 3 | **31 个非-optional 缺失包**（含 `@earendil-works/pi-ai`） | 我（这次用扫描器**一次**列全） |

★ 教训：**"① 缺失"里非-optional 的那部分就是【必须修】的**；更根本的是
**我有扫描器报了却没把它的输出当判据用** —— 有工具不用等于没有。
★ 已沉淀两个脚本：`audit-partial-packages.mjs`（只读扫描）+ `refetch-lock-packages.mjs`（按 lock 重取）。
