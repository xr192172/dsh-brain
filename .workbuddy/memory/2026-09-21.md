### 二、接口（决定我们能不能用）

- **两条后端**：**`command`（语言无关 ⇒ 可以是本地 Node/CLI，不用容器）** vs **Harbor（target 必须是可导入 Python 包 ⇒ 语言锁死）**。

## ★ WSL 卡死的诊断（**不需要重装**）+ POSIX 底座这一步怎么走

> 背景：VeRO 与上游 `minimal` **都卡在"需要一个 POSIX 底座"**（见 `docs/vero-integration-findings.md`）。
> 用户反馈 WSL 服务重启失败（"不在计算机上"）⇒ Docker Desktop 报 `Unexpected WSL error`
> （`wsl.exe -l -v --all: context deadline exceeded`）。我做了一轮**只读诊断**。

### 一、诊断结论：**根因是一个卡死的进程，不是缺组件、也不是发行版坏了**

| 项 | 实测值 | 判读 |
|---|---|---|
| Windows | 10 专业版 **19045** | — |
| 上次启动 | 2026-09-20 11:41 | 机器没重启过（用户只重启了**服务**） |
| **`WSLService`** | **State=`Stop Pending`／Status=`Degraded`／PID=6552**，且 `wslservice.exe` **进程还活着** | ★★ **卡死点**：SCM 说"正在停止"，而进程没死 ⇒ 任何 `wsl.exe` 调用都会**挂住** ⇒ `context deadline exceeded`；此时"重启服务"也必然失败 |
| 服务二进制 | `C:\Program Files\WSL\wslservice.exe` | Store 版 WSL（**2.7.14.0** 已安装） |
| `Microsoft-Windows-Subsystem-Linux` | **InstallState=1（已启用）** | ✅ 不用重装 |

⇒ **结论：不要重装 WSL、不要重置 Docker Desktop、不要重装 Ubuntu。**

### 二、修复顺序（从最省开始；**都要管理员**）

```powershell
# ① 先掐掉卡死的进程（wslservice.exe 可能对 /PID 抗拒，用 /T 连子进程）
taskkill /F /IM wslservice.exe /T
# ② 再启动服务
sc start WSLService            # 或： net start WSLService
# ③ 清干净并验证
wsl --shutdown
wsl --status
wsl -l -v                      # 应能看到 Ubuntu-24.04 与 docker-desktop
wsl -d Ubuntu-24.04 -- echo ok # 应打印 ok
```
- **②起不来 ⇒ 直接重启机器**（Stop Pending 状态几乎必被重启清掉）。**这是最可靠的一步**，别在服务上纠缠。
- 机器起来后：先 `wsl -d Ubuntu-24.04 -- echo ok`，**再**启动 Docker Desktop（它会自动恢复）。
- ⚠️ **别点 Docker Desktop 的 "Reset to factory defaults"** —— 那会删掉 WSL 里的 docker-desktop 数据，而这里根本不是数据问题。

### 三、底层是好的 ⇒ 修好后**不要**做的三件事

2. 不要删/重装 `Ubuntu-24.04`（**发行版与数据都在**）。
3. 不要 `wsl --unregister docker-desktop`。

| | **审批流**（AGENT/ch12 的 auto/soft/hard/type_name） | **危险度度量**（六维 0–100） |
|---|---|---|
| 回答的问题 | *"要不要停下来问人？"* | *"这个动作有多危险？"* |

- ⇒ **其余全部自动化**：L0 机械门 / L1 不变量门 / L2 能力门 / L3 holdout 都是**机器判**，**不进人工审批**。
- ⇒ **人的位置在"改门"与"最终采纳"**，不在"逐动作确认"。

## ★★★ 更正：**"改工具面"不是不能，而是"能且能免费"**（用户反驳后我改口，2026-09-21）

> 用户：「**为什么不能改工具面呢？** 变成子 Agent 时**先 fork 父上下文**，**后面注入一条提示**告诉他
> 『你现在是子代的上下文，你后续能用的工具集是 X』；**在下一次压缩时才把前面父类上下文的工具面清掉**
> —— 那时候就不重要了。**子类只需要知道当前实时的自己能用什么不就 OK 了吗？**」

### 一、我上一轮错在哪

我说*"改工具面 = 改请求头 = 必付一次 prefill"* —— **对，但只在"不在重算点改"的时候**。
而 **压缩本身就是一个前缀改写源**（我们自己的文档原文：*"命中率不是被「压缩质量」拖低的，是被「**前缀改写频率**」拖低的"*；
*"prune 的剩余收益只是延迟压缩，而**它自己每次都是一次前缀改写**"*）；**换代同理**。
⇒ ★★ **用户的机制 = 把 header 的变更【对齐到"本来就要重算的时刻"】** ⇒ **额外代价 ≈ 0。**

### 二、两段式时间线（可实施形态）

```
T0  父代（宽面）
T1  委派：fork 父上下文 ＋ 【尾部注入】"你现在是子代；当前可用工具是 X"   ← 在 messages ⇒ 【保前缀】、立刻生效
T2  子代执行（header 仍是父代的面 ⇒ 前缀未断）
T3  【压缩点】（本来就要重算）⇒ 此时才真裁剪 header ＋ 清旧工具面指引   ← 代价 ≈ 0
T4  此后 header = 窄面（与父代不同头，但前缀刚被重置过）
```
⇒ **答案：能改，且能不以额外代价改** —— **改动对齐到压缩/换代点，在那之前用"尾部告知"顶着。**
⇒ ★ **这一点是用户机制真正聪明的地方**：**"立刻的引导"与"最终的真裁剪"可以【都要】，且不额外付。**

### 三、⚠️ 但两条必须说清（否则会误以为"告知"能替代"裁剪"）

**① "告知" ≠ "限制"**：`tools[]` 没变 ⇒ **模型仍【能】调用未授权的工具**。
| 手段 | 治什么 | 不治什么 |
|---|---|---|
| **尾部"告知"**（messages） | **行为引导**：少选错、少越界 | **不减少暴露**（父代 schema 仍在请求里，占 token/注意力） |
| **header"硬裁剪"**（`toolFilter`） | **真的减少暴露** | 不提供"为什么少了"的语义 |
⇒ **自进化（要信噪比）告知够用；防误用（安全）不够。**

**② ⚠️ 实现前提（本轮新核实的）**："压缩时清掉旧工具面指引"要求**压缩器能改 `system` 段** ——
**我们现役 compaction 补丁处理的是 `input.messages`**（`_foldChunks(input,…)` 遍历 `input.messages`），
**而工具面指引在 `system` 里**（今天实测：改一次使父会话 system 少 365 字符 ⇒ 它在 system）
⇒ **"压缩时清 system 段"这个能力目前【没有】** ⇒ 要么扩展压缩器、要么换清法。**列为前提。**

### 四、连带修正：§9.2 的"硬冲突"有解了

原判断：**token 级前缀复用 与 子代自有工具面 互斥** —— 仍然成立（作为"同时性"的约束），
**但用户的机制让它们【不必同时】**：**先用 header 不变（保前缀）+ 尾部告知**，

## 四、★★★ 本轮最硬的产出：**"fork 省一笔"被实测了，且发现真正的决定因子**

**仪器（新，零运行时改动）**：`scripts/measure-delegation-reuse.mjs`
数据源 = 真实会话日志 `assistant/message.usage`（服务端读数 `cacheReadTokens`；
`dsh-llm-deepseek/lib/index.js:933` 把 `prompt_cache_hit_tokens` 映射进来）。
**样本：181 会话 / 15 对父子**。归因靠子会话的 `subagent/descriptor` 事件（逐字记 `provider:"fork"|"spawn"` + `mode`）。
辅助探针：`out/probe-tools-insert.mjs`（父子 request/header 工具清单逐位比对）。

**结论 1：决定复用的不是 fork/spawn，是"前缀是否逐字一致"。**
- `system` 与父代**逐字完全一致** ⇒ 6/6 高命中（`cacheReadTokens` 24576–41088，命中 98–99.6%）
- 不一致 ⇒ 8 例里 6 例中/低
- 工具数**相同** ⇒ 8 高 / 1 低；**不同** ⇒ **0 高 / 5 中低**
- **provider=fork 也有 1 例低（2.8%）；spawn 也有 3 例高（99%）** ⇒ **fork/spawn 非决定因子**

**结论 2：因果链闭合 —— 一个 `report` 工具，把 98.6% 打成 2.8%。**
| 子 | 工具 | `report` 位置 | system 公共前缀 | 子首请求 |
|---|---|---|---|---|
| `1df6c839` one-shot | 102=102 | 无 | **100%** | 缓存读 40576（**98.6%**）|
| `436fde97` continuable | **103 vs 102** | **第 88/103 位** | 89.6% | 缓存读 1152（**2.8%**），未缓存 40103 |
| `b7327cc6` continuable | **103 vs 102** | 第 88/103 位 | 90.1% | 缓存读 1152（**2.8%**）|

`report` 被 ① 写进 system（断点原文就是 "Deliver your result with the report tool before you finish…"）
② 按**字典序插进工具列表中段第 88 位** ⇒ 严格前缀缓存在**首个差异处截止** ⇒ 其后 15 项 schema **+ fork 继承来的整段父代历史**全部重算。

**★ 强反证**：`8ac9ffef`(d2←d1) / `8314ffa9`(d3←d2) 都是 continuable，但**父子都 103（都带 report）**⇒ 命中 **99.6% / 99.0%**。
⇒ **代价不来自"多一个工具"，来自"与父代不同"。**

**⇒ 设计规则（= 用户"子类是父类的增加而非裁剪"的【物理原因】）：append 保前缀，crop/shadow 砸前缀。**

- 新增工具**插中段** ⇒ 其后 schema + 全部 messages 一起作废
- ⇒ 子代的脸应是父代脸的**逐字前缀扩展**：人格走尾部（上游 `subagent:delegation` 就是对的形态）；新工具**排到列表末尾**（`toolOrder` + `<unlisted-tools>`，`dsh-system-prompt/README.md:14`）

**未闭合**：① agnes 两例 system 公共前缀仅 2% 却命中 89.6/89.8% ⇒ **严格 LCP 对 agnes 不成立**，说明"前缀一致"是**必要但可能不充分**；
② 本表是**假设生成非受控实验**（15 对、因子共线）；且我算的"父末请求→子首请求间隔"取错（取了父会话最后一条消息，父代委派后还继续跑 ⇒ 负值），**需修**；
③ 下一步受控 A/B：同父同题，只改一变量（脸一致 / 多一个 report 插中段 / 多一个 report 排末尾）⇒ 直接看 `cacheReadTokens`。

## 七、★★★ 用户第七次口述模型 + 本轮裁决：**"调 skill ⇒ 我获得新工具"在机制上成立**（`docs/skill-as-agent-feasibility.md`）

### ★★ 三档定价（"零失效"必须精确到【注入位置/形态】）

### 判定：合理（三条理由）

1. **把"不稳定"隔离到短命对象里**：主体永不变脸 ⇒ 主体前缀永远稳定；长尾能力全在短命分身上 ⇒ 重算只发生一次且随分身消亡。
2. **主体脸从"N 条委派工具行"降到"1 个入口"**：今天主体每个请求都付 `subagent`/`subagent_fork`/`council_architect` 三条常驻 schema
   （`dsh-tool-subagent/README.md:44` "each provider instance adds one schema"）⇒ **收成一条入口是今天就能做、立刻可量的瘦身。**
3. **天然不需要卸载**：分身用完即没 ⇒ 不需要上游 cordis 那套 `stop`/`dispose to quiescence`。**"短命"本身就是回收机制。**

### 三条前提（否则会以为"简化后什么都不用做"）

1. "主体只有小集合"= **preset 级改动**（委派入口收敛成一条），今天可做。
2. **"分身带增量工具"仍要补缺口 A**：skill 声明的工具要物化成 `ToolDefinition` 并注册到分身 scope；

   ⇒ **分身简化的是【概念与主体】，不是【那根要接的线】。**
3. 走**工具形态**时，分身每次重付 ~11.9K 消息段 ⇒ **分身不宜太短**，需要"最短寿命判据"（**未设计**）；
   走 **skill 指令形态**则无此约束，代价转移到"每次执行要模型自己用通用工具实现"。

### 关于"炸社区"的诚实判断（已写进文档 §7.7）

**担心是真的，但赌注押错了地方**：概念平凡的代价真实存在，但"分身 = 主体 + 增量"这个词组**把正确性变成可检验的**；

## 十二、★★★★ 用户提出**成本最低的一条路**：「上下文只暴露第一次的初始化，变动由工具内部知道」

### ★ 机制上通 —— 因为"能力面"是**投影**，不是权威

| 事实 | 出处（逐字，`dsh-tools/README.md`） |
|---|---|
| `code` 给的 = `run_code` + **`tools:sdk` 段** + "只有 run_code 可直接调" | `:16` |
| **SDK 段是 lazy section，每次装配【重新生成】** | `:122` "a **lazy prompt section regenerating** … **at each assembly**" |
| 内容 = **当前 scope 的可见工具集**（`ToolArgsMap`/`ToolOutputMap` 逐工具精确类型） | `:118`、`:122` |

| ★★ **装配层 listener 可替换注册表的贡献，且"其返回的装配是权威的"** | `:20` "A `system-prompt/assemble` listener **may replace the registry's contributions**; its returned assembly is **authoritative**" |

### 回答两个直接问题

- **"能不能改 `run_code`？"** ⇒ **改不了**：`:16` "The **reserved transport cannot be registered, shadowed, restricted, or removed**"。

- **"Tool 字段有必要限制那么严吗？"** ⇒ **那不是权限限制，是"声明面 = 可调面"的一致性保证**：
  `:120` under `code` "a model-direct call naming any other tool resolves to **`UNKNOWN_TOOL`** … before `tools/pre-execute`, approval `ask`, and guards"，
  且拒绝信息会**指路**。`:22` 亦明文 "This is **live visibility composition**, not an authority boundary"。
  **我们替换 SDK 段并不破坏它** —— 一致性只是从"逐工具"变成"**逐能力名**"。

### ★ 落地三段（零 patch）

1. **脸固定**：child-scoped 的 `system-prompt/assemble` listener 把 `tools:sdk` 段替换成**固定的通用调用面** ⇒ **工具集变化不再改 system ⇒ 前缀永不失效**。
2. **能力活在运行时**：真实可用能力集由我们插件解析，模型通过那个稳定入口调用（"工具内部知道"）；
   与 `:118` "每个 binding 重入完整工具管线"的语义一致。
3. **告知只追加消息**：需要让模型知道"现在有什么"就往**消息尾端**追加（skill catalog 形态：durable user-role 消息、只带 name+description、变化时追加完整替换）⇒ 代价 0。

### ⚠️ 代价必须成对量

| 换来 | 付出 |
|---|---|
| **前缀永不变**（能力可随时长/缩而不付一次重算） | **放弃逐工具精确类型**（`ToolArgsMap` 块实测约 27350 chars）⇒ 失去"写错就调不通"的保护 |
| 上下文变小 | **错误率可能上升**（参数错要靠运行时校验才发现） |

⇒ **必须成对报的判据：「零失效省下的 token」 vs 「类型缺失带来的错误率/返工次数」。拿到这一对之前：机制可行、账未结。**

### 其他硬约束（会卡住实现）

1. **一个 agent 内不能 native/code 混**（`:196` "within one agent no tool can be native-only while another is code-only"）⇒ 分身要么整张脸 native、要么整张脸 code。
2. **`presentAs` 每 agent 只能声明一次**，从普通 context 调用会抛，同 scope 第二次声明也抛（`:21`）。
3. **替换 SDK 段后，"保住可用的 Code Mode 协议"是我们的责任**（`:20` 明文）—— 这条账要认。
4. **`code` 模式要求 `ctx.codeRuntime` 有对应语言的 SDK renderer**，否则**拒绝装配**，`dsh-agent-presets` 还会**拒绝挂载并点名该 id**（`dsh-agent-tool-presentation/README.md:15`）。
5. ★ **"通用调用面"具体长什么样、运行时解析怎么接进 `run_code` 的 binding 管线 —— 未设计。**

### ★ 关键发现 1：`PromptSection.text` **可以是函数**，且按 **scope** 求值

> "The generated-SDK prompt section, **registered globally by a code-mode deployment and per scope by `presentAs`**.

### 1. 压缩**确实是一次带标记的模型调用**（实测 payload，扫 181 会话）

⇒ `compaction/summary` 的 `llmStreamCall` 注释原文："Identifies exactly one call through this context's `ctx.llm.stream()`"

### 3. ★ 订阅 API：`session/event`

`dsh-session/README.md`：`:11` "plugins **subscribe to `session/event`**"；`:91` 同；
`:33` "publishes **post-commit append notifications** with **per-listener containment**"；
`:39` `session.append` "commits synchronously, then **notifies observers** with independent failure containment"。
⇒ ★ **per-listener containment ⇒ 我们的刷新逻辑抛错不会拖垮持久化。**（签名与 scope 在生成区，未逐字读）

### 4. ★★ 上游那句话**证成了"压缩点免费"**

> **"A `replace` operation invalidates reuse from the first shadowed message even though the underlying event log stays append-only."**

⇒ **压缩本来就让"从第一个被遮蔽的消息起"的复用失效 ⇒ 在那里刷脸不额外付费。** 这不再是推演，是上游机制陈述。

### 5. ★ 触发判据（补上 §13.5 的缺口）

**判据 = `compaction/end`（无 error）或 `compaction/prune`**（两者都是"历史被重写过"的事实）。

- ★ **不要挂 `compaction/start`**：实测 **132 start vs 130 end** ⇒ 有没正常收尾的 ⇒ 挂 start 会在失败压缩上白刷一次脸。
- ★ **`prune`（72 次）也必须触发**：它不走模型，但**同样 replace 历史节点 ⇒ 同样改前缀** ⇒ 漏了会造成"prune 了但脸没刷"。
- ★ **判据要能报"历史为真次数"**（铁律 #11）：本机为真 **130 + 72 = 202 次** ⇒ 不是假绿；落地时把两个计数打进日志，为 0 就报警。
- 次选：`compaction/summary.shadowedSeqs`（直接告诉你被替换掉的是哪些节点）。
- 兜底：`text` 闭包比较"上次装配的工具集指纹"——⚠️ 它测的是"脸变了没"，**不是"压缩发生没"，两者不可互替**。

**未闭合**：① `session/event` 订阅的准确签名/scope（**能否只订阅某个子代的事件，未验证**，否则会收到全库压缩）；
② `end` 带 `error` 时刷不刷，未定；③ 压缩的 `usage` 可纳入成本账，未做。

## 十七、★★ 规格补全（D9 + O8–O12 + "分身持久化"澄清）—— 用户问"会不会被并发掉"

### ★★ D9（新增裁决）：我们的注册必须是 **host-plane 单例 + scope 感知**，**禁止"每分身/每 preset 各挂一份"**

**依据（上游原文，`~/.dsh/.agent-presets/council/agent.cordis.yml:169-172`）**：
> "`tool-subagent-report` is host-plane for the same reason as the registry … it registers a **CONTINUABLE SETUP** on that singleton
> rather than a tool this agent calls, and **the setup list is not scope-aware — one copy per mounted preset means every child gets
> `report` registered once per live session, which throws on the second.**"

⇒ ★ **这就是"并发"的真实雷**：**分身的会话不会互相覆盖**（独立 session + 独立 UUID），
**但"按 preset 各挂一份"的注册会重复 ⇒ 第二个就抛错**。上游的 `report` 正是因此被挪到 host plane。
⇒ **施工含义：桥（S2）与任何 setup 类注册，必须注册在 host plane 一次、按 scope 分派。**

### D4 细化：`end` 带 `error` 时刷不刷 ⇒ **不看 `error`，看"历史是否真被 replace 过"**

判据写成 **`shadowedSeqs.length > 0` ⇒ 刷**；`error` 只记日志。理由：`error` 是"这次尝试的结果"，而我们要的是"**surface 动没动**"
（132 start vs 130 end ⇒ 有未正常收尾的，而**未收尾 ≠ 没动过**）。⇒ 把**不可靠的状态信号**换成**可验证的事实信号**。
